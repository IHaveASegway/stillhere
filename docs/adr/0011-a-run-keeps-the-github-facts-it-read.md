# ADR 0011: A run keeps the GitHub facts it read

Status: Proposed · 2026-10-15 · Deciders: Joseph Peterson · Amends the run model's "forge facts are not per run" ([codebase.md](../spec/codebase.md#run-model)) and the watermarks-only decision of #48

## Context

GitHub is the system of record for pull requests and reviews ([ADR 0004](0004-github-behind-sync-boundary.md)). facts.db holds a replica of them that outlives runs: a sync replaces a pull request as a whole whenever it sees it updated. Until now a scan run kept only when each of its forge repositories was synced (the watermarks, with the names and the join it read them under, #48), and the values and ranks it computed. That was enough while every number from GitHub data was computed at scan time and stored: `reviews_given@1`'s values and ranks.

#38 adds reviews to two metrics, and one of them cannot be stored. `knowledge_loss@1` counts a review as activity; it is computed at scan time and stored like any value. `who_knows@1` lists recent reviewers for any path a user asks about, down to one file, so it is answered per query from a stored run and never stored: a value for every directory of every repository would outnumber the facts. Its reviewers therefore have to come from somewhere when the run is read, and the replica is the wrong place:

- **Two snapshots in one answer.** The owners, top authors and landers of the answer are the run's, at its HEADs; reviewers read from today's replica would be another state of GitHub, and the answer's `provenance.forge` would date neither honestly. #48 rejected exactly this for ranks.
- **A later sync rewrites a stored run.** A sync that adds a review submitted before the run's `--now`, as an incremental sync of a stale replica does, would change a stored run's who-knows answer. The run model says a later sync moves nothing a stored run shows.
- **A newer metric version has no GitHub data.** The run model listed as "not built yet" that a metric version newer than a run, computed over its stored facts, gets no forge facts.

A run's git facts already solve the same problem by being a snapshot per run. What a run read is part of that snapshot (Pat Helland, "Immutability Changes Everything", CIDR 2015).

## Decision

- **A scan run keeps its own part of the replica, whole.** Its GitHub data is the replica cut by the one join of its forge repositories to the repositories it collected (`domain.ForgeJoin`): those forge repositories as the replica listed them, their watermarks, and every pull request of them updated in the 365-day history window, with its labels, reviews and commits. That is `FactSet.Forge` at scan time, so the metrics compute over exactly what the run keeps. Another organization's repositories, and a repository whose collection failed, are none of the run's.
- **The join is kept too, and is the one the metrics count by.** The scan joins once; the watermarks record the join (their `Keys`, #48), and `FactSet.Forge.Join` carries the same join to the metrics, at scan time and when `RunForge` reads it back. So the join has one owner, the run's record: a later stillhere whose `ForgeJoin` reads origins differently (an Enterprise host or a host alias, #44) moves neither a stored run's numbers nor its dating. Only GitHub data no run joined, the replica itself, is joined again.
- **It is stored with the run**, while the run is running, by `ForgeStore.PutRunForge`, in migration 4's `forge_snapshot_*` tables, one row per list item numbered by position as migration 1 stores git facts, each row deleted with its run (`ON DELETE CASCADE`) by retention or as a crash's leftover.
- **Readers read it back** with `ForgeStore.RunForge` into the stored run's `FactSet.Forge`, and never read the replica. A run stored before migration 4 kept its watermarks and no pull requests: its pages date the GitHub numbers it stored by those watermarks, as #48 made them, and `who-knows`, which computes reviewers from the pull requests when the run is read, says nothing about GitHub for it rather than list no reviewers as if there were none; the log says to scan again.
- **The run's GitHub data stays a copy, never a second owner.** Nothing updates it after the run is published; the replica remains the only mutable copy, and GitHub the only source. Readers need it exactly as consistent as the run's git facts, which a snapshot gives.

The pattern is a periodic snapshot per run, as Maxime Beauchemin's "Functional Data Engineering" (2018) keeps a full dimension snapshot per partition at Facebook, Airbnb and Lyft: storage is cheap, reproducibility comes free, and nobody has to reason about which version of a row a past computation saw.

## Alternatives considered

- **Read today's replica at query time, dated by today's watermarks.** No storage at all, and a stored run's reviewers always as current as the last sync. Rejected: one answer would mix the run's git snapshot with another GitHub snapshot, its "as of" would have to be two dates, and every sync would change a stored run's who-knows answer. It is the option #48 rejected for ranks, for the same reason.
- **Store only who_knows@1's reviewers.** Impossible as stated: the answer is per path prefix, so the run would have to precompute every directory, which is why `who_knows@1` is never stored. Its smaller cousin, storing per run only the derived review facts the metrics need (each landed pull request's landings and its counted reviewers as subjects), saves about three rows in five: a pull request's commits and labels, and its title. Rejected: it stores derived values, with today's login resolution and review filters baked in, so a newer metric version, `explain` of `reviews_given@1`, or a corrected login rule cannot recompute from it. Facts, then versioned metrics ([ADR 0003](0003-facts-metrics-views-sqlite.md)).
- **Store the run's joined pull requests, whole (chosen).** About 1 KB per pull request per run (below), and nothing derived.
- **Deduplicate the per-run copies by pull request version.** Store each pull request once per `(id, updated)` it was read at, and have a run reference the versions it read through a table of its own, as restic and borg store a chunk once and let every snapshot that holds it point to it. Sync and readers are unchanged, and the copies stay immutable, at roughly one copy per version of a pull request instead of one per run: most stop changing once merged, so about a tenth to a twentieth of the chosen copy at 20 runs, as for a versioned replica below. Its cost is deletion: a version that a newer run still references must outlive the run that first read it, so `ON DELETE CASCADE` from the run can no longer remove the rows, and retention needs a reference count kept in step with every run's references, or a sweep of the versions no run references after each deletion, as restic's `prune` is. Rejected for now, since the plain copy is measured within budget; it is the first move if the copies grow, because it changes only `internal/sqlite` (see Revisit if).
- **Version the replica instead of copying it** (a slowly changing dimension of type 2, or time travel as Delta Lake and Apache Iceberg tables offer it): keep every version of a pull request a sync replaced, and have a run reference the versions it read. One copy of each version instead of one per run: most pull requests stop changing once merged, so at about 20 runs it would store a tenth to a twentieth as much. Rejected for now: the sync's "replace a pull request as a whole" becomes "append a version and close the old one", every reader becomes an "as of" query, and versions that no run references need collecting. The port hides the difference, so this is the move to make if the copies grow too large (see Revisit if).

## Consequences

- **Storage, measured** (2026-10-15, through `PutRunForge` into a real facts.db): 20,000 pull requests updated in the window, with 4 commits, 3 reviews and 2 labels each, are 200,000 rows per run and 20.8 to 21.3 MB, about 1.05 KB per pull request. The window holds every pull request updated in it, open and closed ones and older ones touched again included, so an organization that merges 20,000 a year holds more than 20,000. Retention keeps, per run kind, at most 21 runs (the one just finished, the newest 8 and the newest of each of the 12 most recent months), about 19 in steady state with daily scans: up to 4.2 million rows and 450 MB for such an organization, against the replica's one copy of 21 MB.
- **Sensitivity to the shape of a pull request.** Heavier ones, 12 commits, 8 reviews, 3 labels and 70-character titles each, are 480,000 rows and 46.9 MB per run for the same 20,000, 2.35 KB per pull request: about 985 MB across 21 runs, at the 1 GB line below. Reading one run's back (`RunForge`) takes 0.13 s and allocates 114 MB, 35 MB of it live while a reader holds it, for the first shape, and 0.28 s, 221 MB and 81 MB for the heavier one (Apple M4 Max).
- **Next to the git facts it is small.** One run of Homebrew/brew (2,384 landings in a year, 2,149 blamed files) is 16.5 MB of git facts, about 6.9 KB per landing; the forge snapshot adds about 1.1 KB per pull request, a sixth of that per change. The store is disposable: deleting facts.db and scanning again loses nothing GitHub and git do not still hold.
- **Time to write and read.** Writing the 20,000 pull requests takes 0.4 to 0.5 s, 1.1 s for the heavier shape, on an Apple M4 Max shared with two other builds, where that scan of Homebrew/brew took 93 s. Every reader of a stored run that computes from it reads the snapshot once per command: `identities`, which only dates the run's GitHub data, reads its watermarks alone. The MCP server caches what a run read, its watermarks and its pull requests, with its facts (`cachedStore`), so an agent's calls about one run read the snapshot once, not twice per call (once for the run's names, once for the answer).
- **Time to compute per query.** `who_knows@1` computes its reviewers when it is asked, so its cost per question matters as much as the read. Over an in-memory run of 20,000 merged pull requests (Apple M4 Max), indexing the run's GitHub data once per question, rather than joining and scanning every pull request once per repository, takes `who-knows` over the whole run from 56, 268 and 763 ms to 19, 37 and 45 ms for 100, 500 and 1,000 repositories, and a path no repository holds from up to 736 ms to 13 ms; without GitHub data the same questions take 8 to 20 ms. A reader that ranks (`report`, `me`, the MCP server's `highlights`) also computes `reviews_given@1`'s clusters in each rank scope over the run's GitHub data, one call per scope; where every repository is a scope of its own (repositories named directly rather than as a group), resolving only each scope's own pull requests takes that from 1.6, 7.7 and 15.1 s to 41, 119 and 250 ms for 100, 500 and 1,000 repositories, and one group scope takes about 20 ms either way.
- **#48's two follow-ups are answered.** A newer metric version computed over an old run gets that run's own GitHub data. `explain` of `reviews_given@1` could now list the pull requests behind a person's value from the run; this decision does not build that, and explain says it lists none of them yet (`pulls-not-listed`).
- **A run says the same thing forever.** A later sync, a rename or a review submitted before `--now` and synced after it, changes no stored run's numbers, reviewers or dates.

## Door

Two-way. facts.db is disposable and migration 4 is additive; the snapshot sits behind `ForgeStore`, so moving to a versioned replica changes `internal/sqlite` and nothing that reads the port.

## Revisit if

- The forge snapshots grow beyond a fifth of facts.db on a real organization, or past 1 GB: deduplicate the copies by pull request version first, which leaves sync and every reader as they are, and version the replica only if that is not enough (above).
- Reading the snapshot shows up in the latency of `report` or of a command-line answer (over 0.5 s; the MCP server already caches it): load it only for the use cases that compute from it, `who-knows` and `explain`, once a newer metric version that reads GitHub data, which a report ranks from the run's own data, is handled there too.
- A use case needs GitHub data the scan did not read, such as pull requests older than the history window: widen what a scan reads, rather than reading the replica from a stored run.

## Amendment: the links of older pull requests (2026-10-15, #103)

The last "Revisit if" came true. Identity's `same-forge-account` rule reads GitHub's attribution of each pull request commit to an account, and that evidence does not age with the history window: on the go-chi organization's replica, the 255 pull requests updated in the run's year make 2 identity candidates high, all 970 synced ones 8, and the group's `knowledge_loss@1` with the high ones merged is 56.6% (unmoved) against 52.1%. So a scan widens what it reads, as this record says to, by the least the use case needs: of the pull requests updated before the history window, only their commits' links (`ForgeFacts.Links`: repository, SHA, the email GitHub read and the account), never their reviews, labels or titles, which no metric's window reaches; and of those, one for each repository, address and account (`identity.KeptLinks`), since the rule reads only which of the run's addresses a repository's links tie to which accounts. A run keeps them with the rest of its GitHub data (`forge_snapshot_links`) and its readers read them back, so the identities answer of a stored run never reads today's replica.

- **Cost.** 134 bytes per link in facts.db (measured on cli/cli, 2026-10-15: `dbstat` gives 1,744,896 bytes for 13,039 rows, an average payload of 105 bytes: the node id, the 40-character SHA, the email and the login), against about 1 KB per pull request kept whole. A link per commit, as the first version kept, grows with the replica's age, every year of synced history adding its links to every run: cli/cli's 13,039 are 1.7 MB a run, and an organization with 50,000 older pull requests of 4 commits each would keep about 200,000, some 27 MB a run and about 560 MB across 21 retained runs, on top of the snapshot's own budget above. One link for each repository, address and account is bounded by the people the history shows instead: cli/cli keeps 438 links a run (59 KB), go-chi 232 instead of 1,481, go-git 179 instead of 2,374, and the identities answer and the scan's JSON are byte for byte those of every link kept (both checked on go-chi and cli/cli).
- **Rejected: a link per commit.** What the first version kept. It gives the rule nothing the reduced set does not, and costs what the line above says.
- **If the reduced copies grow too.** Keep one copy of each link in facts.db, referenced by the runs that read it, which leaves every reader as it is: the move this record already names for the snapshots.
- **Rejected: keep every pull request whole.** A one-line change to the scan's `since`, and no metric's value moves, since each window bounds its reviews; but the copies would grow with the replica's age, every year of synced history adding a year of whole pull requests to every run.
- **Rejected: read the replica's links when a stored run is read.** The identities answer could, since candidates are computed when asked, but the scan's numbers that count candidates (`knowledge_loss@1`'s and `knowledge_concentration@1`'s unmerged-identities `Detail`, #104) would rest on another snapshot than the answer that lists them.
- **Door.** Two-way: the links are evidence for suggestions, a run stored before has none, and the reduction is the scan's alone, so a later version can keep more without a migration.

# Git invocation

Status: carried over from the 2026-10-07 plan, updated 2026-10-14 (offline/sync split, credentials, `--source` floor; then by #13: the repository settings and attributes that changed facts, pinned in the prefix or where the command is built, and no `.gitattributes` for the history logs and blame; then by #72: the port as built, and the identity rules for shared names and GitHub logins) · analysis commands become tests in M0, sync commands in M2

Every git process goes through one port, `domain.GitRunner`, which the `gitcli` adapter implements: `Run(ctx, GitCmd)` returns git's stdout buffered, for small outputs, and `Stream(ctx, GitCmd, fn)` hands it to `fn` while git writes it, for large ones such as `log -p` and blame. A `GitCmd` names the directory git runs in (`-C`), the git arguments, stdin, the timeout, the exit codes that are not errors, the profile (analysis or sync) and, for sync only, the credential variables. Call sites spell out the git arguments themselves, so a reader and a test can see the exact command. A `GitRepository` type whose `Blame()`/`Log()` methods hide the flags is the weaker design: one method forgets the mailmap flag and nobody can see it.

## Analysis commands (offline)

```
git -C <repo> --no-optional-locks \
  -c core.hooksPath=/dev/null \
  -c core.fsmonitor= \
  -c core.attributesFile=/dev/null \
  -c diff.external= \
  -c log.showSignature=false \
  -c core.bigFileThreshold=512m \
  -c diff.default.binary=auto \
  -c core.commentChar=# \
  -c trailer.separators=: \
  -c core.ignoreCase=false \
  -c core.precomposeUnicode=false \
  [-c mailmap.file=<org-mailmap>] \
  <args>
```

Environment: `GIT_TERMINAL_PROMPT=0`, `GIT_CONFIG_NOSYSTEM=1`, `GIT_CONFIG_GLOBAL=/dev/null`, `GIT_ATTR_NOSYSTEM=1`, `GIT_NO_LAZY_FETCH=1`, `GIT_ASKPASS=` (empty). Every inherited `GIT_*` variable, `SSH_ASKPASS` and `SSH_ASKPASS_REQUIRE` are removed first. Elsewhere in these specs, `git <common>` means this prefix plus this environment.

| Setting | Why |
| --- | --- |
| `core.hooksPath=/dev/null`, `core.fsmonitor=` | A clone must not run its hooks or a filesystem monitor as a side effect of being measured. |
| `diff.external=` | A repo-local external diff program must not run. The empty value does not switch external diff off: git tries to run an empty command and fails (verified on 2.50.1). `log` and `show` never run an external diff without `--ext-diff`, so the value matters only for `git diff`, which must pass `--no-ext-diff` (see call-site rules); one that forgets fails closed instead of running the repository's program. |
| `log.showSignature=false` | A repo-local `log.showSignature=true` makes `log` and `show` run `gpg.program`, which the same config names, for every signed commit (verified). |
| `core.bigFileThreshold=512m`, `diff.default.binary=auto`, `core.commentChar=#`, `trailer.separators=:`, `core.ignoreCase=false`, `core.precomposeUnicode=false` | Each is git's default, and a repository's own value changes facts that no subcommand option can pin: see [repository settings that change facts](#repository-settings-that-change-facts). |
| `GIT_CONFIG_NOSYSTEM=1`, `GIT_CONFIG_GLOBAL=/dev/null` | Reproducibility: a machine-wide mailmap or config would make two laptops emit different reports. Repo-local `.git/config` still applies, but it cannot override command-line `-c`. |
| `core.attributesFile=/dev/null`, `GIT_ATTR_NOSYSTEM=1` | Reproducibility again: attributes are not config, so the two variables above leave the per-user file (`$XDG_CONFIG_HOME/git/attributes`, git's default `core.attributesFile`) and `/etc/gitattributes` in force. Either one can mark a path `-diff` (numstat then counts it as binary) or `linguist-generated` (verified). The repository's own `.gitattributes` and `info/attributes` still apply, in work trees and bare clones alike (verified). |
| `GIT_NO_LAZY_FETCH=1` | Blocks promisor lazy fetch on Git 2.45+ (`git --no-lazy-fetch`, 2.45.0 release notes): a partial clone's missing blobs read as missing, so classification degrades as [classification.md](classification.md) says instead of failing. The promisor remote comes from the repo's own config, the same place a credential-bearing URL lives. Git 2.44.0 ignores the variable (CI saw two connections to a fake promisor on 2026-10-14), which is why the floor is 2.45. |
| `GIT_ALLOW_PROTOCOL=none` | Defence in depth: an allow list naming no real protocol refuses every transport, including remote helpers, overriding the repository's own `protocol.<name>.allow` (git 2.12+). Whatever would make a read-only command fetch, today's lazy fetch or a path a later git adds, fails with `transport '<name>' not allowed` instead of connecting (verified on 2.50.1 with lazy fetch left on). Sync never sets it. |
| `--no-optional-locks` | Read-only commands must not take optional locks that contend with the user's own git. |
| `GIT_TERMINAL_PROMPT=0`, `GIT_ASKPASS=` | Analysis must never block on a credential prompt. `GIT_TERMINAL_PROMPT=0` covers only the terminal: git first tries `GIT_ASKPASS`, then `core.askPass` from repo-local config, then `SSH_ASKPASS`, which desktop sessions and IDE terminals often export. An empty `GIT_ASKPASS` ends that search (verified). Sync leaves `GIT_ASKPASS` to its credential mechanism. |

**Call-site rules.** The prefix cannot fix these, because a more specific setting or an option of one subcommand wins over a `-c`:

- `--no-color` on every `log -p`, `show`, `diff` and `grep` whose output is parsed. A repo-local `color.diff=always` or `color.grep=always` puts ANSI escapes in that output, and `-c color.ui=never` does not override the more specific keys (verified).
- `--no-ext-diff` on every `git diff`.
- `--no-ignore-revs-file` before any `--ignore-revs-file` on `blame`. A repo-local `blame.ignoreRevsFile` otherwise adds its list to stillhere's, and blame fails outright when that file is missing; `-c blame.ignoreRevsFile=` does not clear it (verified).
- `--attr-source=<empty tree>` ahead of every `log` that can print a diff and of `blame`, so they read no `.gitattributes` file: neither the scanned commit's, nor the checked-out one, nor the tree `attr.tree` names ([week-collector.md](week-collector.md#attributes-none-from-any-tree) says why). The empty tree is `4b825dc642cb6eb9a060e54bf8d69288fbee4904` in a SHA-1 repository and `6ef19b41225c5369f1c104d45d8d85efa9b057b53b14b4b9b939dd74decc5321` in a SHA-256 one, which git holds in every repository whether or not it stores it. It is not in the prefix because the ID depends on the repository's object format, which the call site knows from Head. Classification reads the linguist attributes at the scanned commit with `check-attr --source` ([classification.md](classification.md#gitattributes)).
- `--no-textconv` on every `log` that can print a diff and on `blame`; `--indent-heuristic` and `--encoding=UTF-8` on `blame`. The history logs' diff options are in [week-collector.md](week-collector.md#repository-config).

Analysis never writes into a scanned repository: no fetch, no `gc`, no config writes, no index refresh. Temporary files, such as an extracted ignore-revs file, go in stillhere's own temp directory. Only sync writes, and only into the mirrors it owns.

Timeouts per command: blame 120 s per file, a repo's log 300 s. On timeout the child is killed, the file or repo records an error, and the group continues: a repository is a bulkhead.

- **What is killed.** git runs in its own process group, and a timeout or a cancellation signals the whole group. Once git is reaped, whatever is left in the group is killed too, so a helper that ignored SIGTERM (Sync) does not outlive the command. A helper that left the group with `setsid` is out of reach; it cannot hold the command either, because the runner closes its end of stdout 5 s after the timeout.
- **What is reported.** A timeout is reported as a timeout (`errors.Is(err, context.DeadlineExceeded)`), even when the reader fails first on the output the kill truncated. A cancellation is reported as one (`context.Canceled`), so a Ctrl-C stops the run while a repository's failure does not.

**Residual risk, named rather than papered over.** No collector runs a textconv or filter program that a repository names: every `log` that can print a diff and `blame` pass `--no-textconv`, and git runs clean and smudge filters only when it moves content between a work tree and its object store, which analysis never does. Verified on 2.50.1 with a committed `*.py diff=tc filter=f` whose textconv, clean and smudge programs recorded each run: History, Blame and ClassifyPaths ran none of them, where Blame without `--no-textconv` ran the textconv. `TestAttributes` keeps it so, with marker programs as textconv drivers (one named in `info/attributes`, and the default driver's `diff.default.textconv`) and as a filter. The history logs and blame read no `.gitattributes` file, but `$GIT_DIR/info/attributes` still applies to them, so a `-diff` there, or a `diff=<driver>` there with `diff.<driver>.binary`, still decides what is binary: a deliberate setting in a clone its user controls. `gpg.program` from repo-local config still runs for any command that verifies signatures on purpose (`--show-signature`, the `%G?` placeholders); no collector does. Three kinds of local state still change facts, and are left for issues of their own because closing them changes what every collector reads: replace refs, grafts and the mailmap, the last rows of the [table below](#repository-settings-that-change-facts). A mirror has neither replace refs nor grafts, because sync fetches `refs/heads/*` only, and reads its mailmap at HEAD. This is defence in depth, not a sandbox: stillhere analyses clones its user already trusts, and never analyses repositories uploaded by other people.

### Repository settings that change facts

A fact must not depend on where or how a repository is checked out, on the machine, or on its local config. Each row was checked on git 2.50.1 (macOS) by setting the value in the repository's own config, or making the checkout so, and comparing both collectors with and without the pin: on a scratch repository built to exercise it, and on both fixtures. "Changes" means a stored fact changed without the pin; with every pin, no row changes a fact of either collector, on the scratch repositories or the fixtures. `TestAttributes` sets every pinned row at once, in a work tree and a bare clone, and fails when any one pin is removed. The last three rows are not pinned yet: they are repository state rather than settings, and each needs a decision of its own.

**Where a pin goes.** A setting that a subcommand option overrides is pinned by that option where the command is built: the option sits next to the output it shapes, and it also beats the more specific config a `-c` cannot reach (`submodule.<name>.ignore` beats `-c diff.ignoreSubmodules=none`, and `--ignore-submodules=none` beats both). A setting that no option overrides goes in the prefix as a `-c` with git's default, so every command gets it, including commands added later; none of the six changes the output of a command that does not read it (`git grep -a` ignores `core.bigFileThreshold` and `diff.default.binary`; `ls-tree`, `cat-file` and `check-attr` print a decomposed path unchanged under `core.precomposeUnicode=true`; all verified). The attribute source is an option at the call site, because the empty tree's ID depends on the repository's object format. Until #13, three of the `-c` settings were per call, on the four logs that print a diff or trailers, and `core.ignoreCase=false` was set on classification's `check-attr` alone; the prefix pins every command alike by construction.

**What changed nothing.** For blame, also checked and left unpinned: `diff.renames=false` and `diff.algorithm=patience` (blame reads neither), `diff.noprefix`, `log.showRoot`, `blame.markIgnoredLines` and `blame.markUnblamableLines` (the parser ignores their marks), `blame.showRoot`, `blame.blankBoundary`, `blame.showEmail`, `blame.date`, `blame.coloring`, `color.ui`, `color.diff`, `color.blame.repeatedLines`, `core.quotePath`, `core.autocrlf` and `core.eol`; and `diff.default.algorithm`, which neither collector applies. History's own list is in [week-collector.md](week-collector.md#repository-config). `$GIT_DIR/info/attributes` still applies under `--attr-source`: it belongs to the repository, not to a checkout, it is the same in a work tree and a bare clone, and the prefix's `core.ignoreCase=false` makes its patterns match case-sensitively.

**What the attribute source costs.** Almost nothing. git looks each `.gitattributes` up in the source tree anew, the cost that made git 2.45.3 and 2.46.0 revert 2.43's use of HEAD's tree in bare repositories ("severe performance implications", their release notes), and the empty tree holds none. Over a year of Homebrew's `brew` repository (2,459 landings, 3,696 non-merge commits, a bare clone, 2.50.1, best of three runs), the landing log took 1.34 s with no source, 1.39 s with the empty tree and 1.87 s with HEAD's tree, and the own-patch log 1.56 s, 1.62 s and 2.25 s. Blaming 150 of its files took 15.9 s, 15.6 s and 16.0 s, which is noise.

## Version floors

| Git | Needed for |
| --- | --- |
| 2.31 | `--diff-merges=first-parent`; `GIT_CONFIG_COUNT` (a sync credential candidate) |
| 2.40 | `git check-attr --source=<rev>`, required for bare mirrors ([classification.md](classification.md#gitattributes)) |
| 2.41 | `git --attr-source=<tree-ish>`, so the history logs and blame read no `.gitattributes` file ([repository settings](#repository-settings-that-change-facts)) |
| 2.45 | `GIT_NO_LAZY_FETCH`, so a partial clone's missing blobs are never fetched |
| 2.46 | `commitGraph.changedPathsVersion=2`, for the changed-path filters in a mirror's commit-graph; not a floor: on 2.45 a mirror's graph has no filters ([sync commands](#sync-commands-network)) |

The 2026-10-07 plan let the tool run on 2.31–2.43 with a weaker guarantee. `--source` now makes 2.40 a hard floor, so the recommendation is one floor, below which stillhere exits 2. It was 2.44 until CI on git 2.44.0 showed that release does not read `GIT_NO_LAZY_FETCH` (the variable and `git --no-lazy-fetch` arrived in 2.45.0), so the floor is 2.45. The Homebrew cask depends on Homebrew's git, and the Docker image ships Alpine's, both well above it. CI runs the floor version and the latest.

## Sync commands (network)

Analysis never touches the network. Only `stillhere sync github` does, and it is the only code path allowed to run these:

```
git clone --bare <https-url-without-userinfo> <mirrors>/<owner>/.stillhere-clones/<repo>.git-<random>
git -C <that clone> config stillhere.forgeId <node id from the GitHub API>
                                   (then renamed to <mirrors>/<owner>/<repo>.git)
git -C <mirror> config remote.origin.fetch '+refs/heads/*:refs/heads/*'
git -C <mirror> fetch --prune origin
git -C <mirror> symbolic-ref HEAD refs/heads/<default branch from the GitHub API>
git -C <mirror> -c commitGraph.changedPathsVersion=2 commit-graph write --reachable --changed-paths
                                   (git 2.46 and later; on 2.45, commit-graph write --reachable)
git -C <mirror> log --format=%H%x00%ae HEAD
                                   (after the pull requests: the author emails GitHub is asked about)
```

Before any of these, once per sync, `git config --file <dir>/config --get stillhere.forgeId` reads the node id of every mirror under `<mirrors>` (it follows no include and needs no repository around it), and mirrors move to match the listing; see below.

- `--bare` with an explicit refspec, not `--mirror`. A mirror's refspec is `+refs/*:refs/*` (verified), which copies every ref the server advertises. On GitHub that includes `refs/pull/<n>/head` and `merge` for every pull request: verified 2026-10-14 with git 2.50.1, `ls-remote` of `cli/safeexec` advertised 13 `refs/pull/*` refs beside 1 branch and 2 tags. A plain `--bare` clone has no fetch refspec at all (verified again in M2), hence the `config` line. No collector needs tags.
- The first clone goes into `<mirrors>/<owner>/.stillhere-clones/` (mode 0700), is marked with its node id, and is renamed into place only when complete. `scan <mirrors>/<owner>` reads that group's immediate children only ([discovery.md](discovery.md#rules-in-order), rule 3), so an interrupted clone is never scanned, as it would be beside the mirror: `git clone` writes `HEAD`, `objects/` and `refs/` before it fetches, which makes a directory look like a bare repository. The directory is on the mirror's own file system, so the rename is atomic. A later clone in that owner's directory removes a leftover older than the clone timeout plus ten minutes, which no clone still running can be, so two syncs never delete each other's clone in progress.
- A mirror is its repository's by node id (`stillhere.forgeId`), not by path. An existing directory is fetched only when it is a bare repository that carries the repository's node id, or carries none and fetches from the expected URL (it then gets the id); anything else at that path is reported and never changed. A mirror that carries the id gets the URL the API reports as its `remote.origin.url` (one `git config`), so it follows a rename.
- Once per sync, before any fetch, the mirrors follow the repositories the sync mirrors (`ForgeSource.ReconcileMirrors`). The mirror of a repository that was renamed, transferred, or changed only the case of its name moves to the repository's path. Under `<mirrors>/<owner>`, the mirror of a repository the owner no longer lists (deleted, transferred to an owner this sync does not list, or hidden from the token) or that this sync leaves out (archived without `--include-archived`, a fork without `--include-forks`, #110), and a second mirror of a listed one, move to `<mirrors>/.stale/<owner>/`, outside every group directory, and back once the repository is mirrored again. So the mirrors directory holds what the last sync was asked to mirror, and `scan <mirrors>/<owner>` reads no archived repository unless the sync was asked for them; marking archived repositories in scan instead would leave them in every number with a label. `sync github --repo OWNER/NAME` speaks for the repositories it names only, so it moves no other mirror (#111). Nothing is deleted. Without this, a renamed repository would be cloned again under its new name and its history scanned twice, because discovery keys repositories by origin URL. The moves are renames, made one at a time; two repositories that swapped names pass through `<mirrors>/.stale/.moving`. A repository whose mirror cannot be moved is not mirrored that sync, so that no second copy is cloned.
- `symbolic-ref HEAD` on every sync: `fetch` never moves a bare repo's HEAD, so a renamed upstream default branch would leave HEAD dangling. The GitHub API is the system of record for the default branch. `symbolic-ref` itself refuses a name that is not a valid branch (verified on 2.50.1).
- `commit-graph write` after every fetch (#56): git's own index of the commits, which the history logs and blame read instead of parsing each object, and with changed-path Bloom filters, which let blame skip the commits that did not touch its file. On 30 public repositories (360,692 commits, 30,155 blamed files) a cold scan took 297 s without a graph, 208 s with one and 104 s with filters, with every stored fact identical by SHA-256 per table; writing the graphs took 9.8 s the first time and 1.9 s when nothing was new. Only version 2 filters are written (`commitGraph.changedPathsVersion=2`, git 2.46): version 1 hashed path bytes above 0x7f differently where `char` is signed, so a graph written on one platform and read on another could tell a path-limited walk that a commit did not touch a path it did. On 2.45, the floor, the graph is written without filters. The file is git's, kept consistent by git and safe to delete; a failed write, such as a lock another sync holds, is logged and the mirror is used without it.
- **Scan never writes a commit-graph into a user's clone**, which it reads only. When a repository's blame took 30 s or more and the clone has no commit-graph with changed-path filters, scan logs a hint that names the command sync runs in a mirror: on git 2.46 and later `git -c commitGraph.changedPathsVersion=2 commit-graph write --reachable --changed-paths` (3.7 to 4.5 times faster blame on a 52,000-commit repository), never plain `--changed-paths`, which writes version 1 filters while `commitGraph.changedPathsVersion` is unset (verified on 2.50.1: `BDAT` hash version 1 without the setting, 2 with it), the version above that a graph moved between platforms can misread. On 2.45, which writes only version 1, a clone without any graph gets `git commit-graph write --reachable` (about 1.4 times faster), and one with a graph gets no hint. So the mirrors sync keeps get none. It finds out with `git rev-parse --git-path objects/info/commit-graph --git-path objects/info/commit-graphs/commit-graph-chain` and reads the chunk table at the start of the graph file, the newest one of a chain, for the `BIDX` chunk (gitformat-commit-graph(5)): the one place a scan reads a file inside a repository's git directory itself, a few hundred bytes, never written.
- Never `--depth` or `--filter`: shallow and partial clones break line facts ([discovery.md](discovery.md#clone-health)).
- `log --format=%H%x00%ae HEAD` after the pull requests (#103, [ADR 0013](../adr/0013-sync-reads-bounded-passes-and-checks-the-replica.md)): every commit reachable from the mirror's HEAD with its author email as the commit holds it (`%ae` follows no mailmap, `%aE` would), which is the email GitHub resolves to an account. Sync asks GitHub about each email it has not asked about before, through its newest commit, and stores the answer; the output never leaves the process otherwise. A mirror that failed to fetch this sync is not read.
- Timeouts: one hour for `clone`, 30 minutes for `fetch`, ten minutes for `commit-graph write` and for `log`, one minute for the other local commands. The analysis default of 300 s would cut off the first clone of a large repository.
- The whole analysis prefix and environment apply to sync commands too, with two exceptions. `GIT_NO_LAZY_FETCH` is not set, because these commands fetch on purpose. `GIT_ASKPASS` is set by the credential mechanism below (to empty); `SSH_ASKPASS` is still removed, so no prompt path is left.
- The prefix changes one thing a mirror stores. git on macOS probes a new repository's file system and writes `core.precomposeunicode=true` into its config, but skips that probe when the setting is already given, as the prefix's `core.precomposeUnicode=false` gives it. So a mirror cloned since #13 has no such line, where one cloned before has it (verified on 2.50.1). `core.ignorecase=true` is still written: that probe does not look at the setting. Nothing stillhere runs reads the stored value, because every command pins it, so old and new mirrors give the same facts. Only a user's own git in a new mirror behaves differently: it does not compose the path arguments it is given.
- `clone` and `fetch` get the credential variables; the local commands (`config`, `symbolic-ref`, `rev-parse`, `commit-graph`, `log`) get none. All of them run on the Sync profile, whose SIGTERM lets git remove its lock files when a sync is interrupted.
- Two syncs may run at once (a scheduled one and a manual one). Every move and publish is a rename, so each repository's mirror is whole or absent, and a conflict fails that repository in one of them; the next sync heals it.

## Credentials

A token is never written to a remote URL, `.git/config`, command-line arguments (visible in `ps`), logs, or reports. Clones that keep credentials in their remote URLs are a common way tokens leak, and analysis would otherwise copy them into every warning.

The candidates were two environment-only mechanisms:

1. `GIT_ASKPASS` pointing at the stillhere binary, which answers git's username and password prompts from an environment variable only it reads.
2. Environment-scoped config: `GIT_CONFIG_COUNT=1`, `GIT_CONFIG_KEY_0=http.https://github.com/.extraheader`, `GIT_CONFIG_VALUE_0=AUTHORIZATION: basic <base64 of x-access-token:TOKEN>`. Never pass this with `-c`, which puts it in argv.

**Chosen in M2 (#14): mechanism 2**, plus `GIT_ASKPASS=` (empty), so that a rejected token fails at once instead of reaching for a prompt, and `http.followRedirects=false` (`GIT_CONFIG_COUNT=2`). It is the header `actions/checkout` sends, without the config file `actions/checkout` writes it to. It needs git 2.31, below the 2.45 floor. Mechanism 1 would work too, but it gives the binary a second mode, answering git's prompts from inside git's child process: more code on the credential path, and harder to test.

The key is scoped to the GitHub URL (`http.<url>.extraheader`), but that scope alone does not keep the header on GitHub. git matches the key once, against the URL it was given, and by default (`http.followRedirects=initial`) it follows a redirect of the first request and sends the rest of the command to the new location with the header still attached. Verified on 2.50.1 (Apple Git-155, curl 8.7.1): with a server on 127.0.0.1 redirecting to one on localhost, curl dropped the header from the redirected `GET info/refs`, but git's next request, the `POST git-upload-pack`, carried it to the other host. GitHub does not redirect git across hosts, but an Enterprise host behind an SSO proxy can. Hence `http.followRedirects=false`: sync always clones and fetches the URL the API reports, which needs no redirect, and a repository renamed between the listing and the clone fails once, until the next sync lists its new name. `TestGitHubSync` checks that a redirecting server's target gets no request at all.

The same OS user can still read a process environment. That is the accepted boundary. `TestGitHubSync` verifies the mechanism end to end: it clones and fetches a mirror from a local git server (git's own `http-backend`) that refuses any request without the token, then asserts that `remote.origin.url` has no userinfo and that neither the token nor its base64 form is in any file of the mirror, its config, the logs, the facts or an error. A refused token fails the clone without a prompt and leaves no directory behind. The same code also cloned and fetched a public repository (`cli/safeexec`) from github.com with the header on 2026-10-14, which shows GitHub accepts its form; a public repository cannot show that the header is what authenticates, which is the local server's part.

## URL scrubbing

Applied before any remote string is stored, logged or printed, and to git stderr before it is stored:

- Remove userinfo: `https://user:TOKEN@github.com/o/r.git` becomes `https://github.com/o/r.git`; the same applies to `ssh://user:password@host/…`.
- Remove the query and the fragment. A remote needs neither, and a query can carry a token (`?access_token=…`).
- The scp form `git@host:path` carries no password and is kept as git printed it, as are `host:path` and local paths. A leading `user:password@` on a remote without a scheme is removed. Any other string without a scheme that contains an `@` is not kept: `https:/user:TOKEN@host` and `https//user:TOKEN@host` are malformed URLs, not scp remotes.
- If parsing fails, store `<unparsed-remote>` and never write the raw string. `<unparsed-remote>` is never a dedupe key ([discovery.md](discovery.md#rules-in-order)): a repo whose remote does not parse is keyed like one without a remote.
- In free text (git's stderr), every URL is scrubbed as above, and a `user:password@` prefix is removed from scp-like tokens too, as in `fatal: 'user:pw@host:o/r.git' does not appear to be a git repository`, and from a segment of a path. So are the userinfo, the query and the fragment of a URL whose `//` a path cleaner collapsed: a URL given where a path is expected becomes `/cwd/https:/user:TOKEN@host/r.git` or `/cwd/https:/host/r.git?access_token=TOKEN` once made absolute, and the messages about it would otherwise carry the token. Only a scheme of two characters or more counts there, because a one-letter one is a Windows drive, as git itself reads it: `C:\src\C#\app` is a path, and keeps its `#`.
- Stored git error messages are truncated to 180 characters after scrubbing, never between a character and its combining marks. Arguments kept for errors and debug logs are scrubbed the same way but not truncated.
- A repository's own path is never scrubbed: it is where git runs. A PATH, or a directory found in a group, whose path the scrubber would change is refused where it enters, in discovery, and reported with its path scrubbed, so no stored, printed or sent path holds a credential ([discovery.md](discovery.md#rules-in-order), #93).

## Identity: mailmap and bots

Git mailmap is the only identity store. stillhere never parses mailmap itself.

- Every analysis command gets `-c mailmap.file=<org-mailmap>` when `--mailmap FILE` is passed, or when `./.mailmap` exists in the directory the command started in. That directory is often a clone's root, where a clone can commit a symbolic link to `/dev/zero` or a FIFO, so a `./.mailmap` that is a symbolic link is a usage error (exit 2) that says to pass it with `--mailmap`; a file `--mailmap` names may be a link. A mailmap that is not a regular file is a usage error too (#71). The same holds for `./stillhere.toml` and `--policy` ([classification.md](classification.md#deny-list)). Git also applies the repository's own mailmap (`gitmailmap(5)`): a work-tree clone reads the checked-out `.mailmap`, and a bare mirror reads `HEAD:.mailmap` through the default `mailmap.blob` (verified). Entries from `mailmap.file` take precedence. So a work tree's identities follow its checkout, not the scanned commit: a `.mailmap` checked out from another branch, or edited and not committed, changes names and emails in the facts, and so do a repository's own `mailmap.file` (when no `--mailmap` is given) and `mailmap.blob` (verified, [repository settings](#repository-settings-that-change-facts)). Reading the mailmap at the scanned commit only is left for its own issue.
- Canonical key: the mailmapped email, lowercased.
- Display name: the mailmap's canonical name when it supplies one. Otherwise, the name seen most often with that email in this scan; ties go to the newest committer timestamp among commits using that exact name, then to UTF-8 bytes ascending.
- No fuzzy merging on names: different people share names and surnames. Display names that more than one email shares are not merged. The reports say so with the `unmerged-identities` caveat ([report-json.md](report-json.md#caveats)), and `stillhere identities` suggests `.mailmap` lines with their evidence, which a person reviews and adds.
- Bots: after mailmap, a case-insensitive substring match of the canonical name and email against `[bots].fragments`, or an `[ai]` agent: an email in `[ai].coauthor_emails`, or a name or email that contains an `[ai].agent_authors` fragment. Agents are never ranked rows ([ADR 0007](../adr/0007-ai-assisted-attribution.md)), so they count as bots even when no `[bots]` fragment names them. Defaults: `copilot`, `gpt-engineer`, `dependabot`, `renovate`, `github-actions`, `[bot]`, and `noreply@github.com`, GitHub's own address, which workflows and GitHub's automation commit with and no person has (2026-10-15: landed@2 credits a merged branch's commits to their authors, so a workflow's commit on a pull request's branch was a person's row). `users.noreply.github.com` is not a bot marker, because people use it, and the fragment `noreply@github.com` matches none of those (`ID+login@users.noreply.github.com`). A mailmap line that maps a bot email onto a person is the user's decision. Bots are separated in every table, never deleted.
- AI-assisted changes are a tag on a person's change, not a bot ([week-collector.md](week-collector.md#ai-assisted-changes)). An agent's commit is credited to its first human co-author, and a commit is tagged AI-assisted only when the person credited is human: an agent's commit without a human co-author stays the agent's, a bot commit ([metrics.md](../metrics.md#change-facts-shared-by-durable1-and-simplifying1)).
- GitHub logins are linked to people when a run is read, not by sync, and the link is never stored: a login is the person who, after the mailmap, authored the run's commits that GitHub attributes to it, and any other login stays `@login` ([ADR 0004](../adr/0004-github-behind-sync-boundary.md); package `identity`, #38).

## Logging

stderr only. Info level: repo names, counts, durations, skip reasons. Never emails, remotes with userinfo, tokens, or AI request bodies. Debug, off by default, may print emails.

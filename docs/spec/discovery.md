# Discovery

Status: carried over from the 2026-10-07 plan, updated 2026-10-14 (bare mirrors accepted, clone health checks added; #4 settled which commit a work tree's default branch names, unusable `.git` directories, group suffixes, directories reached twice and how failures are reported) and 2026-10-15 (#71: a directory with no repository among its children is an error that says what to pass, not an empty group; #93: a path that holds a credential is refused where it enters; #74: a window after a shallow boundary is counted) · tests in M0: `TestDiscover`, `TestCloneHealth`

Repositories are named by positional paths only. There is no config file listing repositories.

```
stillhere scan PATH [PATH ...]
stillhere week PATH [PATH ...]
```

Managed mirrors written by `stillhere sync github` are passed the same way, for example `stillhere scan <mirrors>/<owner>`.

## Rules, in order

1. **Work tree.** `PATH/.git` exists (as a file or a directory) and `git rev-parse --is-inside-work-tree` prints `true`, with an empty `--show-prefix` (PATH is the top of the work tree): one repo. Children are not walked, so a checkout that contains nested clones is one repo and the nested clones are not added. When `PATH/.git` names a bare repository instead, PATH is that bare repository: one repo, whose default branch is read as rule 2's, and the worktrees beside it are not added. That is the bare-clone-plus-worktrees layout, where `PATH/.git` holds `gitdir: ./.bare`, or a bare clone made into `PATH/.git` itself; `git rev-parse --resolve-git-dir PATH/.git` must name the repository git found. A PATH with a `.git` that git cannot use is an error (rule 4), not a group: git either fails or walks up and answers for an enclosing repository, which the prefix or the git dir shows.
2. **Bare repository.** `git -C PATH rev-parse --is-bare-repository` prints `true` and `--absolute-git-dir` is PATH itself: one repo. Managed mirrors are bare. This check must run before rule 3, because a bare directory has no `.git` child. It replaces the 2026-10-07 rule that warned and skipped bare repos. git is asked only about a directory with git's own layout (`objects/` and `refs/`) or a name ending in `.git`, the convention for bare repositories. One that git does not take for a repository, such as a bare clone without `HEAD` or the empty directory of a mirror whose clone died, is an error (rule 4), not a group. In a directory inside a repo, git answers for that repo, which the git dir shows.
3. **Group.** Otherwise, a directory is a group named by its basename. Its members are the immediate children that satisfy rule 1 or 2. There is no deeper walk. A child that cannot be read, such as `lost+found` at the root of a mount or a folder the operating system protects, is not a member and is not reported. A symbolic link counts as the directory it points at. A directory none of whose immediate children looks like a repository is no group: a group of nothing would read as one that was read and found empty, so it is an error (rule 4), takes no group name, and its message says what to pass instead. That is usually a near miss, checked in this order, the more specific first:
   - its subdirectories hold repositories one level deeper, as a mirrors root holds an owner's directory of mirrors, or a parent holds group directories: the message says groups are one level deep and names two of those subdirectories, in name order, hidden ones (such as `.stale`) left out. A link among them is followed only to a directory, never opened otherwise: a link to a FIFO would block the open for good;
   - the directory is inside a work tree, as `stillhere week .` in a repository's subdirectory is: `git rev-parse --show-toplevel` names the top of the innermost one, and the message reads `inside repository <top>: pass <top>`. This comes second because a directory of groups inside an enclosing work tree, such as a home directory or a workspace kept in git, means the groups, not the enclosing repository;
   - otherwise: `no repository among its immediate children, so neither a repository nor a group`.

   A group whose members all fail (rule 4) or are duplicates (rule 5) is still a group: each of those has its own message.
4. Otherwise, the slot is an error, and so is a repo, named or a group's member, that git cannot read or whose default branch has no commit (an empty repo). Other paths still run. Each error is reported once, however many ways its path was reached. The use cases record each as a run-level `path-failed` warning, the path and then the reason, and mark the run `partial` ([codebase.md](codebase.md#errors-and-logging)).
5. **Duplicates.** After expansion, the key is the scrubbed `origin` URL string ([git-invocation.md](git-invocation.md#url-scrubbing)) and nothing else. There is no case folding and a trailing `.git` stays. The `origin` URL is the one git fetches from: the first `remote.origin.url` after the last empty one, because an empty value clears the list before it (git 2.46 and later; 2.45 keeps an empty URL as one of its own). `git@github.com:o/r.git` and `https://github.com/o/r.git` are two repos; equating them would be a later behaviour change with its own test. A scan, once it has collected them and read the GitHub data in facts.db, also skips a clone whose origin names a repository by an old name GitHub resolves to it (a sync's recorded alias, joined only by shared history) while another repository of the run names it by its current name, with the same warning on the kept one (wave 11's review: the old name's clone and the new name's mirror counted one repository's commits and pull requests twice). A repo without `origin`, or whose `origin` scrubs to `<unparsed-remote>`, is keyed by `local:` and its directory basename, so `<unparsed-remote>` alone never makes two repos one. The lexicographically first path wins, and each skip is a `duplicate-repo` warning naming both local paths and the scrubbed URL. A work-tree clone and a managed mirror of the same HTTPS remote are duplicates. One directory reached twice is one repo, with no warning, because it is not a second clone. It may be named directly and through its group, through a symbolic link, or in another letter case on a case-insensitive file system. It stays in its group if it is a group's member; otherwise it keeps the lexicographically first spelling.

   Known limitation, an open decision for the owner (#4 review): two unrelated repos without a usable `origin` that share a basename (`clientA/api`, `clientB/api`) share the key `local:api`, so the second is skipped with a `duplicate-repo` warning that names both paths. An scp-like remote on an ssh host alias named `local` (`local:api`) keys the same way. Keying such repos by path would separate them, at the cost of a key that changes when a directory moves and that carries an absolute path wherever keys go.
6. Two groups with the same basename get a numeric suffix in path order (`src`, `src-2`), and both are kept. A suffix skips a name another group already has, so a third group whose own basename is `src-2` pushes the second `src` to `src-3`.

Worktrees, whose `.git` is a file, are repos. Submodules are not auto-discovered: a submodule is included only when its path is itself a selected repo or an immediate child of a group.

**A path that holds a credential** (#93). Before any rule, a PATH whose absolute path `redact.Scrub` would change, and a group's child whose path would, fail (rule 4) with a message that quotes the path scrubbed and says it holds what looks like a credential: a remote's userinfo or token, or a query, as a remote pasted where a directory was made leaves it (`…/https:/x-access-token:TOKEN@github.com/acme`), or a `user:password@` segment. Nothing of it is read, so no stored, printed or sent path holds the credential: not facts.db (`run_repos.path`, `run_groups.path`), not a report, and not the MCP server's answers. The path is refused, not scrubbed, because a run's `Repo.Path` is where git runs and what the MCP server maps a path to its repository by; a scrubbed path names no directory. The command line already refuses such a value for `--db`, `--mirrors` and `STILLHERE_HOME` (#71); this covers a directory that already has such a name.

## Default branch

Resolved locally, never fetched.

| Repo | Resolution |
| --- | --- |
| Work tree | The first of: `git symbolic-ref --short refs/remotes/origin/HEAD` with a leading `origin/` stripped, if that ref exists; `main` if `refs/remotes/origin/main` exists; `master` if `refs/remotes/origin/master` exists; `main` if `refs/heads/main` exists; `master` if `refs/heads/master` exists; the current `HEAD`. An `origin/HEAD` whose target does not exist is an error (rule 4), not a fall-through to a branch upstream no longer has. That happens when upstream renamed or deleted its default branch and a `fetch --prune` deleted the old one, as git 2.47 and older left it. `git remote set-head origin --auto` repairs it. |
| Bare | `git symbolic-ref --short HEAD` (verified). Sync re-points a mirror's HEAD at the upstream default branch every run ([git-invocation.md](git-invocation.md#sync-commands-network)). |

The branch name and its resolved SHA are recorded per repo, and every later command names that SHA, or, when the branch holds landings at or after `--now`, the newest first-parent commit below it committed before then, which a run reads instead (#70, [run model](codebase.md#run-model)). The SHA is the commit the chosen ref points at. A work tree whose clone has a remote-tracking ref for the branch (`origin/HEAD`'s target, `refs/remotes/origin/main` or `refs/remotes/origin/master`) is therefore measured at upstream's commit as of the last fetch. It is not measured at a local branch of the same name, which may lag behind it, hold commits that never landed, or not exist (`git clone -b`). So two clones in the same state get the same SHA whether or not they have `origin/HEAD`, which `git init` followed by `git push -u` leaves out ([ADR 0009](../adr/0009-default-branch-as-upstream-last-fetched.md)). Only a clone with none of those refs (no `origin`, or never fetched) is measured at its local `main`, `master` or `HEAD`. A detached `HEAD` records the branch as `HEAD`. Every report states that analysis did not fetch: a stale clone produces a stale report. A repository's card says beside the branch whose default it is (wave 11, round 3's org F10, `repos[].forge_default_branch`): GitHub's, when the run's GitHub data records the same default branch, else the clone's, with GitHub's beside it when the two differ, as a clone whose `origin/HEAD` predates a change of default leaves them; so an agent reading a feature branch's name on a repository whose default branch that is does not call the clone wrong.

## Clone health

Run per repo, before any collector.

| Check | Detection | Warning | Effect |
| --- | --- | --- | --- |
| Shallow | `git rev-parse --is-shallow-repository` prints `true` (verified) | `shallow-clone` | No blame facts, because blame credits every line older than the shallow boundary to the boundary commit. When a boundary commit is inside the window the history collects, or a landing in it brought one in, the facts carry warning `shallow-window`, which names the boundary. A metric's window that lies wholly after every boundary commit the history holds, and holds no landing that brought one in, is still counted, exactly; any other window of the repository has no value, never a partial count ([metrics.md](../metrics.md#values-what-every-metric-returns), #74). The boundary is a commit with no parent in a shallow clone (`domain.Repo.Boundary`), whose diff is its whole tree, so it has no change facts. |
| Partial | `git config --get-regexp '^remote\..*\.promisor$'` reports `true` for any remote, or `extensions.partialClone` is set | `partial-clone` | No line facts: no week numstat and no blame. Commit facts (landings, authors, trailers, subjects) are still collected with `git log` without `--numstat`. |

Verified on 2.50.1: a `--filter=blob:none` clone sets `remote.origin.promisor=true` and `remote.origin.partialclonefilter`, but not `extensions.partialClone`, so detection must not rely on the extension alone. Under `GIT_NO_LAZY_FETCH=1`, both `git log --numstat` (even `-1` at HEAD) and `git blame` fail fatally on the first missing blob, while plain `git log` succeeds. Without this check, a partial clone would surface as a wall of per-file errors rather than one clear warning.

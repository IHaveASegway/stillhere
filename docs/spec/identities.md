# Identity candidates

Status: M2 (#26) · 2026-10-14, rules tightened after the review of PR #49 · `identity.Candidates`, `app.Identities`, `stillhere identities` and the MCP server's `identity_candidates` · oracles in [SPEC.md](../../testdata/fixture/SPEC.md#identity-candidates-m2-26)

stillhere suggests `.mailmap` lines for addresses that may belong to one person, each with the evidence for it, and applies none. git's mailmap stays the only identity store ([ADR 0004](../adr/0004-github-behind-sync-boundary.md), [git-invocation.md](git-invocation.md#identity-mailmap-and-bots)): a candidate becomes a merge only when a person writes its line into a reviewed file.

## Why

Identity is the weakest joint of an authorship report. One person with several addresses splits into several people, and every metric that groups by person splits with them: without the fixture's mailmap, Ada's 10 surviving lines become 7 and `knowledge_loss@1` goes from 4/34 to 11/34 ([SPEC.md](../../testdata/fixture/SPEC.md#knowledge_loss1-main-fixture)). A wrong merge is worse: it invents a person who does not exist, with two people's work. The report's `unmerged-identities` caveat says where a line may be missing, but not which line; this command writes the line and the evidence a person needs to decide, so the fix lands where the data lives.

## Data ownership

| Data | System of record | Writes it | Reads it | How it crosses |
| --- | --- | --- | --- | --- |
| Email aliases | `.mailmap`: each repository's own, and the organisation's file `--mailmap` names | People, in reviewed commits | git, at every analysis command | git applies them while a scan runs (`-c mailmap.file=`) |
| Candidates | None: derived when asked from one stored run, never stored | `identity.Candidates` | `stillhere identities`, the MCP server | In memory, as a `report.Identities` |
| Blocks | None: derived when asked from one stored run, never stored | `identity.Blocks` | the AI-share floor (`app.AIShares`) | In memory; never printed |
| GitHub logins | GitHub | GitHub | `sync github` | The forge replica (`ForgeCommit`) |

No second owner: stillhere writes no mailmap and keeps no people table ([architecture.md](../architecture.md)). The candidates read one run, so one HEAD set and one mailmap; a line added since takes effect at the next scan, which every answer says in its `mailmap-at-scan` caveat.

## Prior art

- **`git shortlog -sne` and a hand-curated `.mailmap`** is the baseline, and the store this command feeds. The Linux kernel keeps a reviewed `.mailmap` in its tree, and gitdm, which LWN uses to count kernel contributions, keeps an alias file of its own.
- **GrimoireLab SortingHat** (CHAOSS) is a full identity database with merge tooling. Its `recommend_matches` matches email, name or username by exact equality, merges overlapping match sets, so A–B and B–C become one group, and leaves out terms in an exclusion table. It is not reused: a Python service with its own database would be a second owner of identity, and its overlapping-set merge chains, which this spec allows only at low confidence.
- **Research.** Bird et al., "Mining email social networks" (MSR 2006), gave the name-and-address heuristics later work builds on; Goeminne and Mens, "A comparison of identity merge algorithms for software repositories" (Science of Computer Programming 78(8), 2013), compare such algorithms. Amreen et al., "ALFAA" (arXiv 1901.03363), found commits from different environments, misspellings, organisational ids, default values and anonymous ids to be the main sources of identity errors over a billion commits, and separate people by behavioural fingerprints such as the files they modify; the default-name lists and the hand-off's shared files below are small pieces of that. Fellegi and Sunter's model of record linkage ("A Theory for Record Linkage", JASA 64(328), 1969) adds up the evidence of fields compared independently, which is why a local part made from the name is not counted as a second field here.
- **GitHub** links commits to accounts by verified email, and by the ID-based noreply address, `ID+USERNAME@users.noreply.github.com`, whose id survives a rename ([GitHub Docs](https://docs.github.com/en/account-and-profile/reference/email-addresses-reference)); an account made before 18 July 2017 may still commit as the old form, `USERNAME@users.noreply.github.com`. The `same-github-account` rule reads the id; a rule over the forge's own commit-to-login links is a follow-up.

## Options

1. **Suggest, with evidence, as mailmap lines for review (chosen).** Nothing is stored or written, so it is a two-way door: rules can change in any release.
2. **Apply confident merges at scan time.** Rejected: an alias table beside `.mailmap` is a second identity store (ADR 0004), and a wrong merge would silently invent a person in every stored number.
3. **Learn identities (ALFAA's approach).** More recall, but it needs labelled data and its reasons are opaque to the person who must sign off a merge. Revisit if the rules miss too much.

The decision is wrong if reviewers often reject high suggestions or accept most commented-out ones unchanged (move the line between written and commented), or if people stay split in ways a forge link would have caught (add that rule).

## Rules

A wrong merge invents a person, which is worse than a missed one, so every rule leans to precision, and `identity.Rules` publishes how each can be wrong; every answer carries those definitions.

| Rule | Links | Confidence | How it can be wrong |
| --- | --- | --- | --- |
| `same-name` | Display names (`identity.Directory.Name`) equal once case, spacing and punctuation are ignored: the words, runs of letters, marks and digits, lowercased (`identity.Directory.NameKey`, which the report's `unmerged-identities` caveats ask too, so a caveat names a name exactly when this rule compares it, #69) | medium for two words or more; low for one; high only with a `same-local-part` that is not made from the name | Different people share names, the more often the shorter and commoner the name, and the facts cannot tell two people of one name apart: organisations make addresses from names, so two Alex Kims at two employers are both `alex.kim`. A name written without spaces, as Chinese, Japanese and Korean names often are, counts as one word and stays low. A name spelt two ways is missed. |
| `same-local-part` | The same local part on different domains, or one that differs only by a `+tag`; a GitHub noreply address counts as its login (`12345+login@users.noreply.github.com` is `login`) | low alone; with `same-name`, high when the local part is not made from the name's words, medium when it is | A first name or a common login as a local part belongs to many people, and git makes up `user@host` addresses from a machine's login name. A local part made from the name says no more than the name. |
| `same-github-account` | GitHub noreply addresses with the same account id, such as `12345+old@` and `12345+new@` after a rename | high | A forged address: anyone can write any address into a commit. |
| `hand-off` | One address's last commit at most 30 days before another's first, both in a file of the same repository, when the first has no commit in the 90 days before the run's as-of time | low, always, and a guess | A teammate who takes over someone's code when they leave looks exactly like one person changing address. |

**Made from the name.** A local part is made from a name when it is some of the name's words, in the name's order or reversed, each whole or as its initial, whatever the separators and with any number after them: `ada` and `ada.example` for Ada Example, `alex.kim`, `kimalex`, `akim` and `akim2` for Alex Kim. A letter outside ASCII matches itself or any run of ASCII letters, so `jose.garcia` is made from José García and `zhangwei` from 张 伟: when in doubt, the local part is the name's. Such a local part is what two people of that name would both have, so it raises nothing: Ada's two addresses are medium, not high. One that is not, such as a handle (`darkstar@` at two employers) or an employee number, is evidence the name does not explain.

A key is no evidence when the facts show it to be several people's:

- **Defaults.** Names a machine, a tool or a tutorial fills in match nothing: a name made only of generic words (`root`, `Unknown User`, `Build User`, `Your Name`, `Firstname Lastname`, and the like), git's own test author `A U Thor`, and `John Doe`, the name the Pro Git book's first-time setup types into `user.name`. Role or default local parts (`admin`, `dev`, `info`, `noreply`, `team`, `you` and the like) match nothing, nor does a local part shorter than 3 characters.
- **Shared by many.** A name or local part that more than 10 addresses share is a default someone's tooling wrote, not a person's.
- **Shared addresses.** An address whose local part is a role or default one, or whose commits carry author names that differ (the rule below), is several people's mailbox, as `team@` with Alice's and Bob's commits is. No rule compares it, so it is in no candidate and is never suggested as canonical, and the answer counts it (`shared`). A line mapping it would give every commit on it to one person; a line for each of its people needs git's name-and-address form, a follow-up. A GitHub noreply address is one account's by construction, so it is never shared.
- **Two GitHub accounts.** A group holding two GitHub accounts links nothing: GitHub's terms allow one person one free personal account, so they are usually two people. An id-form address's account is its id; an old-form address's is its login, which is the same account as an id-form address of that login.
- **Different names.** A local part used under names that differ (neither's words all among the other's, so `ada` and `Ada Example` agree and `Ada Example` and `Ada Lovelace` do not), or by a shared address, links nothing. A name that is only the address's own local part, as GitHub names a commit by a login when the account has no profile name, agrees with any name; `John Doe` on `john.doe@` is a name and counts.

Bots and agents (`identity.Directory.Bot`: `[bots]` fragments and `[ai]` agents, ADR 0007) never appear; the answer counts them.

## How candidates form

- **Groups and components.** Each rule groups the addresses by its key (the normalised name, the local part, the account id), and the groups that are evidence are joined where they share an address. Each component is one candidate, so an address is in one candidate at most: git keeps the last of two lines for one alias, silently (verified on 2.50.1), so two candidates must never both map it. A component of more than 10 addresses, or a hand-off chain that long, is several people's linked through one another; it is left out, and the answer counts it (`oversized`).
- **Confidence is the weakest pair's.** For each two addresses of a candidate: the same account id, or a full name with a local part not made from it, is high; a full name of two words or more is medium, with or without a local part made from it; a one-word name or a local part alone is low. Two addresses that share no key at all are linked only through a third (chained), and make the candidate low however strong each link is: chaining multiplies the chances of being wrong.
- **Hand-offs** are looked for only among addresses no other rule links and no shared address, in time order. An address that stopped long enough ago is compared with each that began within 30 days after its last commit, and a pair needs a file both touched (by a file change of a commit they authored or co-authored, a rename's source included) or hold blamed lines in, in the same repository. A merge's file changes are its first-parent diff, the work of the commits it brought in, so they are not the merger's. An address with two possible successors, or two possible predecessors, gets none, so what is left are chains, each address followed by the one that took over from it. Once a run's other candidates are merged, a later run looks for hand-offs between the merged addresses. The search never lists the pairs the times allow, which a burst of new addresses (an organisation moving everyone to a new domain) would make quadratic: an index from each file to its addresses in time order finds an address's successors by binary search and stops at the second, so the work grows with the facts times a logarithm.
- **Evidence** for each address: its display name, the kind of its domain, the commits it authored and those whose `Co-authored-by` trailers name it (a SHA counted once across repositories), the first and last author time of those commits, and the repositories it appears in. Commits are the run's history and the older commits blame attributes lines to, which is how an author whose only commit is older than the 365-day history still appears. The kind of domain (`identity.DomainKind`) is `main` for the domain most of the scope's addresses use (GitHub's noreply and machine domains aside; none on a tie), `noreply` for GitHub's, `machine` for one git makes up from a machine's name (no dot, or `.local`, `.localdomain`, `.lan`, `.home`, `.internal`), and `other`.
- **The canonical address** suggested is, in order: not a GitHub noreply address, which is an alias by design; for a hand-off, the newest, which the person moved to; the one at the domain most of the scope's addresses use, the organisation's convention; then the most commits, the most co-authored, the latest activity and the smallest email. **The suggested name** is the canonical address's when it has two words or more, else the fullest name another address carries, else the canonical address's own. A default name, or one that gives away one of the candidate's addresses (below), is never suggested: with no other name the suggestion is `""`, which keeps each commit's own name.

Candidates are sorted by confidence, guesses after the rest, then by suggested name and first address. They are not versioned like metrics: they are computed when asked, never stored, and only a person acts on them, so a newer binary may suggest differently for the same run.

## Output

`app.Identities(ctx, d, IdentitiesRequest{RunID, Scope})` reads a stored run (the latest unless a run id is given) with its own policy, whose `[bots]` and `[ai]` tables tell bots apart, and never its metric values. Display names come from the whole run, as on every other page; candidates from the scope's repositories (all of them, a group, or one repository by key, scrubbed as `who-knows --repo` is). A scope that names no group or repository of the run is a usage error.

**A display name that gives an address away** is withheld everywhere but in the mailmap form: one that holds an `@`, as an address typed as a name does, or that is a local part of any person's address in the run (the whole local part, the part before a `+tag`, or a noreply address's login, ignoring case), as GitHub names a commit by the account's login when it has no profile name. Printed beside the kind of the address's domain, or read by someone who knows the organisation's domain, such a name is the email. The rule is every answer's ([report-json.md](report-json.md#rules-that-carry-forward-whatever-the-format), "Where emails go", #52), decided per name by the run's directory (`identity.Directory.Withheld`, which `report.IdentitiesInput.Who` carries), so a name withheld here is withheld in every table, and so is a name that is the local part of an address outside the candidate. Without a directory, `NewIdentities` checks a name against the candidate's own addresses (`identity.RevealsAddress`).

### JSON, and the MCP server

`report.Identities`: `provenance`; `scope`; `addresses` (people), `bots` (left out), `shared` (of the people's addresses, those no rule compares) and `oversized` (groups left out); `candidates[]` of `{confidence, guess, commented, chained, rules[], name, addresses[], links[], mailmap}`; `rules[]` of `{id, matches, confidence, risk}`; `caveats`. An address is `{email, name, name_withheld, domain_kind, canonical, commits, co_authored, first, last, repos[]}`, with repositories by key. A link is `{rule, addresses[], name, from_name, hand_off}`: the indexes it links, the shared display name for `same-name`, whether a `same-local-part`'s local part is made from the name, and for a hand-off `{gap_days, shared_files, files[]}`, the first five shared files as `{repo, repo_key, path}`. `commented` is true for every candidate but a high one.

Emails appear only in fields named `email`, and a name that gives an address away is `""` (with `name_withheld` true on an address), so no other field holds a person's address or a part of one; a link names no local part or account id, and the rule texts quote no whole address. The one exception is `mailmap`, a candidate's suggested lines exactly as the mailmap form writes them (`report.MailmapLines`, which the form writes through too, so the two cannot drift): it is `null` unless the reader may see emails and asks for the lines (`app.IdentitiesRequest.Mailmap`). The MCP server serves the value as it is and drops the email fields without `--allow-emails`; with it, it asks for the lines (#69), so an agent can hand the user the line it suggests. The caveats are every answer's (`not-fetched`, and the repository caveats: a shallow clone's short history hides addresses), plus `mailmap-at-scan`, which also says that git follows no chain of lines ([Limits](#limits)).

### Text and Markdown name no address

They keep [report-json.md](report-json.md#text-and-markdown)'s rule, although the answer is about emails, and go one step further: they print no address and no part of one. A candidate pairs a person's addresses, such as a work address with a personal one, which is the most sensitive fact stillhere prints, and text and Markdown are what people paste into issues and chats. Each address is shown by its number and the kind of its domain: `main domain`, `GitHub noreply`, `machine` or `other domain`, with a letter (`other domain A`, `other domain B`) when a candidate has two addresses of a kind that can differ, the same letter for the same domain. A withheld name is `(name withheld)`.

The first version printed each address as its domain and the first six hex digits of its SHA-256 (`…@example.com (b5fc85)`), as the no-name placeholder does. Three flaws dropped it: beside a login used as a name, the domain completes the email; the domain alone says which personal provider or other employer a person uses; and an unsalted hash beside a name and a domain confirms a guessed address with one computation. A letter matches nothing outside the page. Printing emails in this one command's text was the other alternative; it would publish them the first time a page is pasted, while the person who edits the mailmap has `--format mailmap` and `--format json`.

### `--format mailmap`

The suggested lines, with the evidence above each candidate's lines as `#` comments. Each line maps one alias to the canonical address and the suggested name, `Name <canonical> <alias>` ([gitmailmap(5)](https://git-scm.com/docs/gitmailmap)), which replaces both for every commit with the alias, whatever its name; a line `Name <canonical>` comes first when the canonical address's own name differs from the suggested one. Only a high candidate's lines, which rest on evidence the display name does not explain (one GitHub account, or a local part not made from the name), are written as lines. Every other candidate's, medium included, are commented out, so that adding the output to a `.mailmap` unread merges nobody whom the facts cannot tell from someone else: two people of one name look exactly like one person with two addresses. Git's parsing, verified on 2.50.1 with `git check-mailmap`, sets the rest:

- A line is a comment only when `#` is its first character: an indented `# Hank Split <hank@…> <gina@…>` maps `gina@…` to a person named `# Hank Split`. Every comment starts in the first column.
- A `#` inside a name is part of the name, and text after a line's last `>` is ignored; addresses and names match case-insensitively.
- A line whose name or address holds `<` or `>`, a control or format character or a byte that is not UTF-8, or whose name starts with `#`, cannot be the mapping it means, so it is written commented out, escaped, with the reason: its bytes must not reach a terminal either.
- git applies one line per commit and never follows a chain, which the header says ([Limits](#limits)).

The fixtures' suggestions are their hand-written mailmaps byte for byte, commented out, and `git check-mailmap` over the printed form leaves every alias alone; with the `# ` removed from a suggested line, it maps the alias to the canonical identity ([SPEC.md](../../testdata/fixture/SPEC.md#identity-candidates-m2-26)).

## Counting people for a floor

The AI-share floor ([ADR 0007's amendment](../adr/0007-ai-assisted-attribution.md#amendment-the-shares-that-leave-the-machine)) counts people with `identity.Blocks`, which reads the same keys the other way. A block holds the addresses a candidate holds, those of every hand-off chain however long (one longer than a candidate may hold included), and every two that share the words of any name seen with them, as author or co-author (a default name such as John Doe included), a local part (without its `+tag`, a noreply address's login) or a GitHub account id, with none of the vetoes above, through any number of links. The rules lean to precision because a wrong merge invents a person; a floor leans to recall because a missed link lets one person's own share out, while a wrong one only lowers a count, so it never lets out a share of fewer than three people; only a missed link can ([Limits](#limits)). Record linkage draws the same line between blocking and classification (Christen, *Data Matching*, Springer 2012, ch. 4). A block merges no one on any page and is never suggested as a line.

## Limits

- **No chains through existing lines.** git applies one `.mailmap` line per commit and never follows a chain (verified with `git check-mailmap` on 2.50.1). The facts are already mailmapped, so a suggested alias can be the canonical address of existing lines: appending `Name <new> <alias>` then remaps only the commits made as the alias, the older addresses stay at the alias, and the next scan suggests the same line again. The mailmap form's header and the `mailmap-at-scan` caveat tell the person to change those lines to the new canonical address too. The proper fix is for a run to record the mailmaps git applied, as it records its policy, so the suggestions can rewrite such lines and drop those already present (#53).
- **No fuzzy names.** Edit distance, nicknames (Bob, Robert) and transliteration (José, Jose) would add recall and false merges; the core has no Unicode normalisation (it imports the standard library only), so a name spelt in two Unicode forms is two names.
- **A changed name.** An address whose owner changed name in a way the subset rule cannot see (Ada Lovelace, then Ada King) looks like a mailbox two people share, so it is compared with nothing: a missed merge, never a false one.
- **GitHub only.** Only `users.noreply.github.com`, the documented form, is read as a noreply domain; an Enterprise host's form is unverified (#44).
- **No forge links yet.** The forge replica's commit-to-login links (`ForgeCommit`) are the strongest evidence there is, GitHub's own; a rule over them needs forge facts on the read side (#13).
- **The floor's blocks** join only addresses that have something in common: a name's words, a local part, a GitHub account, a candidate or a hand-off chain. One person's addresses with nothing in common count as several people, so a share of two people can leave as three until a `.mailmap` line merges them (ADR 0007's amendment, #86). An empty author address is a missing fact: beside other people it may be any of them and adds no one, and alone it is one person (`app.aiShareCount`), while the run takes it for a person's rather than a bot's, which it decides once per run by the name most often seen with it (#74).
- **Hand-offs** need the earlier address quiet for 90 days, so a change of address shows up 90 days after the old address's last commit, and only between addresses no other rule links.

# Identity candidates

Status: M2 (#26) · 2026-10-14, rules tightened after the review of PR #49 · 2026-10-15: GitHub's own links (`same-forge-account`, #103), the lines git already applies (#53), and what unmerged identities do to knowledge loss (#104), with the findings of PR #114's review · 2026-10-16 (wave 10): GitHub's link high whatever names an address carries, the account's login in its evidence, hand-off guesses last and apart, and a reviewer linked by every link (#117) · `identity.Candidates`, `app.Identities`, `stillhere identities` and the MCP server's `identity_candidates` · oracles in [SPEC.md](../../testdata/fixture/SPEC.md#identity-candidates-m2-26)

stillhere suggests `.mailmap` lines for addresses that may belong to one person, each with the evidence for it, and applies none. git's mailmap stays the only identity store ([ADR 0004](../adr/0004-github-behind-sync-boundary.md), [git-invocation.md](git-invocation.md#identity-mailmap-and-bots)): a candidate becomes a merge only when a person writes its line into a reviewed file.

## Why

Identity is the weakest joint of an authorship report. One person with several addresses splits into several people, and every metric that groups by person splits with them: without the fixture's mailmap, Ada's 10 surviving lines become 7 and `knowledge_loss@1` goes from 4/34 to 11/34 ([SPEC.md](../../testdata/fixture/SPEC.md#knowledge_loss1-main-fixture)). On a real organisation the effect is a headline's: the go-chi group's `knowledge_loss@1` is 56.6% as keyed, 52.2% with the high-confidence lines merged (6 of the 20 candidates that hold lines there have some) and 17.6% with every candidate merged (#103, measured 2026-10-15). A wrong merge is worse: it invents a person who does not exist, with two people's work. The report's `unmerged-identities` caveat says where a line may be missing, and, on every value of `knowledge_loss@1` and `knowledge_concentration@1`, how far merging the candidates would move it ([below](#what-unmerged-identities-do-to-knowledge-loss)); this command writes the line and the evidence a person needs to decide, so the fix lands where the data lives.

## Data ownership

| Data | System of record | Writes it | Reads it | How it crosses |
| --- | --- | --- | --- | --- |
| Email aliases | `.mailmap`: each repository's own, and the organisation's file `--mailmap` names | People, in reviewed commits | git, at every analysis command | git applies them while a scan runs (`-c mailmap.file=`) |
| What git rewrote (#53) | git, while the scan ran, in each repository: each email a commit or a trailer was written with, the name written beside it, and the canonical email the mailmap gave it | the collectors (`%an` and `%ae` beside `%aN` and `%aE`, `git check-mailmap`) | the identities answer's `.mailmap` lines | `RepoFacts.Aliases`, kept with the run (`repo_aliases`) |
| Commit-to-account links (#103) | GitHub: the account that verified a commit's author email, or whose noreply address it is | `sync github`, into the forge replica (`ForgeCommit`), and its links pass, which asks GitHub once about each author email of a mirror's history, through its newest commit (`forge_links`, ADR 0013) | `identity` (the `same-forge-account` rule, `Blocks`), through `app` | The run's GitHub data (ADR 0011): its window's pull requests and, of the older ones, their commits' links only, with the links pass's answers (`ForgeFacts.Links`) |
| Candidates | None: derived when asked from one stored run, never stored | `identity.Candidates` | `stillhere identities`, the MCP server; a scan, which counts and merges them in two metrics' `Detail` (#104) | In memory, as a `report.Identities`; as counts and numbers in the run's values |
| Blocks | None: derived when asked from one stored run, never stored | `identity.Blocks` | the AI-share floor (`app.AIShares`) | In memory; never printed |

No second owner: stillhere writes no mailmap and keeps no people table ([architecture.md](../architecture.md)). GitHub's links are evidence, not merges: a scan applies none of them, so `.mailmap` stays the one owner of the merges git applies; applying them at scan time would make stillhere a second one (the [options](#options) below). The candidates read one run, so one HEAD set and one mailmap; a line added since takes effect at the next scan, which every answer says in its `mailmap-at-scan` caveat. `identity` reads the links only through the fact set `app` hands it (the dependency rule: a core package reads no store).

## Prior art

- **`git shortlog -sne` and a hand-curated `.mailmap`** is the baseline, and the store this command feeds. The Linux kernel keeps a reviewed `.mailmap` in its tree, and gitdm, which LWN uses to count kernel contributions, keeps an alias file of its own.
- **GrimoireLab SortingHat** (CHAOSS) is a full identity database with merge tooling. Its `recommend_matches` matches email, name or username by exact equality, merges overlapping match sets, so A–B and B–C become one group, and leaves out terms in an exclusion table. It is not reused: a Python service with its own database would be a second owner of identity, and its overlapping-set merge chains, which this spec allows only at low confidence.
- **Research.** Bird et al., "Mining email social networks" (MSR 2006), gave the name-and-address heuristics later work builds on; Goeminne and Mens, "A comparison of identity merge algorithms for software repositories" (Science of Computer Programming 78(8), 2013), compare such algorithms. Amreen et al., "ALFAA" (arXiv 1901.03363), found commits from different environments, misspellings, organisational ids, default values and anonymous ids to be the main sources of identity errors over a billion commits, and separate people by behavioural fingerprints such as the files they modify; the default-name lists and the hand-off's shared files below are small pieces of that. Fellegi and Sunter's model of record linkage ("A Theory for Record Linkage", JASA 64(328), 1969) adds up the evidence of fields compared independently, which is why a local part made from the name is not counted as a second field here.
- **GitHub** links commits to accounts by verified email, and by the ID-based noreply address, `ID+USERNAME@users.noreply.github.com`, whose id survives a rename ([GitHub Docs](https://docs.github.com/en/account-and-profile/reference/email-addresses-reference)); an account made before 18 July 2017 may still commit as the old form, `USERNAME@users.noreply.github.com`. Its contributor graphs count a person by those links. The `same-github-account` rule reads the id from the address; the `same-forge-account` rule (#103) reads GitHub's own links, which `sync github` copies with every pull request's commits. SortingHat does the same from several sources at once (unique identities with manual overrides on top); here the overrides are `.mailmap` and the sources are suggestions.

## Options

1. **Suggest, with evidence, as mailmap lines for review (chosen).** Nothing is stored or written, so it is a two-way door: rules can change in any release.
2. **Apply confident merges at scan time.** Rejected: an alias table beside `.mailmap` is a second identity store (ADR 0004), and a wrong merge would silently invent a person in every stored number. Applying GitHub's links automatically (a forge identity layer under `.mailmap`'s precedence) is the same choice with better evidence, and stays rejected for now (#103): it is a second owner of the merge decision and a privacy-relevant change to who is who. Instead the high lines are one command away (`stillhere identities --format mailmap >> ~/acme.mailmap`, then `stillhere --mailmap ~/acme.mailmap scan ...`), and every `knowledge_loss@1` and `knowledge_concentration@1` value carries what it would be with them merged, so nothing waits on the step. Revisit if dogfooding shows people skip it.
3. **Learn identities (ALFAA's approach).** More recall, but it needs labelled data and its reasons are opaque to the person who must sign off a merge. Revisit if the rules miss too much.

The decision is wrong if reviewers often reject high suggestions or accept most commented-out ones unchanged (move the line between written and commented), or if people stay split in ways a forge link would have caught (#103 added that rule; its recall is bounded by the pull requests a sync copied, [Limits](#limits)).

## Rules

A wrong merge invents a person, which is worse than a missed one, so every rule leans to precision, and `identity.Rules` publishes how each can be wrong; every answer carries those definitions.

| Rule | Links | Confidence | How it can be wrong |
| --- | --- | --- | --- |
| `same-name` | Display names (`identity.Directory.Name`) equal once case, spacing and punctuation are ignored: the words, runs of letters, marks and digits, lowercased (`identity.Directory.NameKey`, which the report's `unmerged-identities` caveats ask too, so a caveat names a name exactly when this rule compares it, #69) | medium for two words or more; low for one; high only with a `same-local-part` that is not made from the name | Different people share names, the more often the shorter and commoner the name, and the facts cannot tell two people of one name apart: organisations make addresses from names, so two Alex Kims at two employers are both `alex.kim`. A name written without spaces, as Chinese, Japanese and Korean names often are, counts as one word and stays low. A name spelt two ways is missed. |
| `same-local-part` | The same local part on different domains, or one that differs only by a `+tag`; a GitHub noreply address counts as its login (`12345+login@users.noreply.github.com` is `login`) | low alone; with `same-name`, high when the local part is not made from the name's words, medium when it is | A first name or a common login as a local part belongs to many people, and git makes up `user@host` addresses from a machine's login name. A local part made from the name says no more than the name. |
| `same-github-account` | GitHub noreply addresses with the same account id, such as `12345+old@` and `12345+new@` after a rename | high | A forged address: anyone can write any address into a commit. |
| `same-forge-account` (#103) | Addresses whose commits GitHub attributes to one account (`ForgeCommit.AuthorLogin`, compared without case), in the run's GitHub data: the pull requests of its window, the links of the older ones a sync copied, and the account of each author email of the history that a sync's links pass asked GitHub about. A commit the run holds, in its history or blamed, names its address after the mailmap; another, such as a squashed pull request's own commit, names the email GitHub read, when the run shows that address (git's mailmap left it as it is, since an address it rewrote appears in no fact). A GitHub noreply address no commit links counts as its login's account when the run's GitHub data links that login to some address, since GitHub gives such an address to its account by construction: a co-author's noreply address, often the person's commonest one, is linked by nothing else. An address GitHub links to two accounts, an account more than 10 addresses link to, and an account whose addresses hold two GitHub account ids (a login renamed and taken again, or rows synced before and after) match nothing. | high, also for an address whose commits carry names that differ (a shared address, below; wave 10), whose evidence says so | GitHub links a commit by its author email, so a mailbox several people commit as, verified by one of them, links to that person, as GitHub's own pages do, and its line is written as a line: the evidence says the address's names differ, so a reviewer checks it before applying it. A noreply address whose login was renamed and later taken by someone else counts as the new holder's. One person's two accounts (a work and a personal one) stay two. An address links through its pull requests' commits, or through its newest commit on the default branch when a sync's links pass asked about it, so one seen only in direct pushes links too; an email GitHub attributes to no account through that commit (not verified when the commit was made, or an account deleted since) links nothing. |
| `hand-off` | One address's last commit at most 30 days before another's first, both in a file of the same repository, when the first has no commit in the 90 days before the run's as-of time | low, always, and a guess | A teammate who takes over someone's code when they leave looks exactly like one person changing address. |

**Made from the name.** A local part is made from a name when it is some of the name's words, in the name's order or reversed, each whole or as its initial, whatever the separators and with any number after them: `ada` and `ada.example` for Ada Example, `alex.kim`, `kimalex`, `akim` and `akim2` for Alex Kim. A letter outside ASCII matches itself or any run of ASCII letters, so `jose.garcia` is made from José García and `zhangwei` from 张 伟: when in doubt, the local part is the name's. Such a local part is what two people of that name would both have, so it raises nothing: Ada's two addresses are medium, not high. One that is not, such as a handle (`darkstar@` at two employers) or an employee number, is evidence the name does not explain.

A key is no evidence when the facts show it to be several people's:

- **Defaults.** Names a machine, a tool or a tutorial fills in match nothing: a name made only of generic words (`root`, `Unknown User`, `Build User`, `Your Name`, `Firstname Lastname`, and the like), git's own test author `A U Thor`, and `John Doe`, the name the Pro Git book's first-time setup types into `user.name`. Role or default local parts (`admin`, `dev`, `info`, `noreply`, `team`, `you` and the like) match nothing, nor does a local part shorter than 3 characters.
- **Shared by many.** A name or local part that more than 10 addresses share is a default someone's tooling wrote, not a person's.
- **Shared addresses.** An address whose local part is a role or default one, or whose commits carry author names that differ (the rule below), is several people's mailbox, as `team@` with Alice's and Bob's commits is. No rule compares it but `same-forge-account`, so it is in no other candidate and is never suggested as canonical while another address is, and the answer counts it (`shared`) unless that rule linked it. A line mapping it would give every commit on it to one person; a line for each of its people needs git's name-and-address form, a follow-up. A GitHub noreply address is one account's by construction, so it is never shared. GitHub gives every commit on an address whose names differ to the one account that verified it, so `same-forge-account` compares it: a name changed over the years (Ada Lovelace, then Ada King) looks exactly like a mailbox two people share. GitHub's link cannot tell the two apart either, since the one who verified the mailbox gets every commit on it. Until wave 10 that made the link between a shared address and another medium, its line commented out; it is high now, and the address carries `names_differ`, which the evidence says ("carries names that differ, as a name change or a mailbox several people commit as does"). The reason is the evidence: on the go-chi and cli/cli organisations every such address the dogfood found was one person whose name changed form, and on the encode organisation (round 2) the medium link left the top maintainer split three ways, the lines of the address under the former name counted as gone quiet, with an explanation that blamed a display-name match. GitHub's own contributor pages make the same attribution, and a line is still only a suggestion a person reviews: the decision is a two-way door, and is wrong if reviewers reject such lines often. A role address stays out even there: several people's by design, whoever verified it. A shared address's name is never suggested.
- **Two GitHub accounts.** A group holding two GitHub accounts links nothing: GitHub's terms allow one person one free personal account, so they are usually two people. An id-form address's account is its id; an old-form address's is its login, which is the same account as an id-form address of that login. A `same-forge-account` group holding two account ids links nothing either: an id never changes hands, so two ids are two accounts whatever login the replica holds for them, and no two addresses of different ids are ever high. Otherwise GitHub's links add links and veto none: most commits reach GitHub by direct push, or in pull requests older than a sync copied, so an address with no link, or with another account's, says less than one with the same account; using them as a veto is a follow-up, should dogfooding show two-account groups that same-name links wrongly.
- **Different names.** A local part used under names that differ (neither's words all among the other's, so `ada` and `Ada Example` agree and `Ada Example` and `Ada Lovelace` do not), or by a shared address, links nothing. A name that is only the address's own local part, as GitHub names a commit by a login when the account has no profile name, agrees with any name; `John Doe` on `john.doe@` is a name and counts. So does a name that is a GitHub login the run's GitHub data links the address to: `jdoe` beside `Jane Doe` on an address the account `jdoe` verified is one person who set `user.name` to their login, not two people (on cli/cli, 6 of the 22 addresses the rule without it called shared were this).

Bots and agents (`identity.Directory.Bot`: `[bots]` fragments and `[ai]` agents, ADR 0007) never appear; the answer counts them.

## How candidates form

- **Groups and components.** Each rule groups the addresses by its key (the normalised name, the local part, the account id), and the groups that are evidence are joined where they share an address. Each component is one candidate, so an address is in one candidate at most: git keeps the last of two lines for one alias, silently (verified on 2.50.1), so two candidates must never both map it. A component of more than 10 addresses, or a hand-off chain that long, is several people's linked through one another; it is left out, and the answer counts it (`oversized`).
- **Confidence is the weakest pair's.** For each two addresses of a candidate: the same account id, the same account in GitHub's links (a shared address's included, wave 10), or a full name with a local part not made from it, is high; a full name of two words or more is medium, with or without a local part made from it; a one-word name or a local part alone is low. Two addresses that share no key at all, or that hold two GitHub account ids, are linked only through a third (chained), and make the candidate low however strong each link is: chaining multiplies the chances of being wrong.
- **High lines in a weaker candidate** (`identity.Candidate.High`). A candidate's confidence is its weakest pair's, so one weak address would otherwise hide the lines that rest on GitHub's own links: on go-git, the top maintainer's four GitHub-linked addresses and his noreply one, and on go-chi, a maintainer's linked pair beside two older addresses that match by name only. The largest set of a candidate's addresses whose every pair is high (of sets that large, the one whose addresses come first in the canonical order below; every set is tried, which 10 addresses at most make cheap) is its high set: its lines are written as lines, the others' commented out, and the metrics' high merges count them ([below](#what-unmerged-identities-do-to-knowledge-loss)). A high candidate's high set is all of it; a candidate with no high pair has none, and every line is commented out (`commented`). The set is a clique, not each address's link to the canonical one, so that it is as sure as a high candidate is.
- **Hand-offs** are looked for only among addresses no other rule links and no shared address, in time order. An address that stopped long enough ago is compared with each that began within 30 days after its last commit, and a pair needs a file both touched (by a file change of a commit they authored or co-authored, a rename's source included) or hold blamed lines in, in the same repository. A merge's file changes are its first-parent diff, the work of the commits it brought in, so they are not the merger's. An address with two possible successors, or two possible predecessors, gets none, so what is left are chains, each address followed by the one that took over from it. Once a run's other candidates are merged, a later run looks for hand-offs between the merged addresses. The search never lists the pairs the times allow, which a burst of new addresses (an organisation moving everyone to a new domain) would make quadratic: an index from each file to its addresses in time order finds an address's successors by binary search and stops at the second, so the work grows with the facts times a logarithm.
- **Evidence** for each address: its display name, the kind of its domain, the commits it authored and those whose `Co-authored-by` trailers name it (a SHA counted once across repositories), the first and last author time of those commits, and the repositories it appears in. Commits are the run's history and the older commits blame attributes lines to, which is how an author whose only commit is older than the 365-day history still appears. The kind of domain (`identity.DomainKind`) is `main` for the domain most of the scope's addresses use (GitHub's noreply and machine domains aside; none on a tie), `noreply` for GitHub's, `machine` for one git makes up from a machine's name (no dot, or `.local`, `.localdomain`, `.lan`, `.home`, `.internal`), and `other`.
- **The canonical address** suggested is, among the high set's addresses when there is one (so the lines that rest on high evidence map to it), in order: not a GitHub noreply address, which is an alias by design; not a shared address; for a hand-off, the newest, which the person moved to; the one at the domain most of the scope's addresses use, the organisation's convention; then the most commits, the most co-authored, the latest activity and the smallest email. **The suggested name** is the canonical address's when it has two words or more, else the fullest name another address carries, else the canonical address's own. A default name, or one that gives away one of the candidate's addresses (below), is never suggested: with no other name the suggestion is `""`, which keeps each commit's own name.

Candidates are sorted with the guesses (hand-offs, a candidate whose only evidence is one address taking over from another) after every other whatever its confidence, then by confidence, suggested name and first address. Round 2 found most candidates of an open-source repository to be guesses between unrelated people (19 of 34 on encode/httpx, 72 of 122 on the pallets organisation), many through a changelog every pull request touches, which buried the few real ones: the headline counts them apart ("15 candidates, and 19 hand-off guesses"), and text and Markdown list them only with `--all`. JSON and the mailmap form hold every candidate, the guesses' lines commented out as before. They are not versioned like metrics: they are computed when asked, never stored, and only a person acts on them, so a newer binary may suggest differently for the same run.

## Output

`app.Identities(ctx, d, IdentitiesRequest{RunID, Scope})` reads a stored run (the latest unless a run id is given) with its own policy, whose `[bots]` and `[ai]` tables tell bots apart, and never its metric values. Display names come from the whole run, as on every other page, and so do the candidates, as the scan finds them for its `unmerged-identities` caveats: a scope (every repository, a group, or one repository by key, scrubbed as `who-knows --repo` is) lists the run's candidates with an address in its repositories, each with all its addresses, wherever they are, since a `.mailmap` line must name the person's other addresses too. So a scoped answer lists every candidate its card's caveat counts, the cross-repository ones (an old address in one repository, the active one in another) included, and also those whose addresses there hold no surviving line (on go-chi, `chi`'s answer lists 21 and its card counts 18). The answer's `addresses`, `bots`, `shared` and `oversized` are the scope's own. A scope that names no group or repository of the run is a usage error.

**A display name that gives an address away** is withheld everywhere but in the mailmap form: one that holds an `@`, as an address typed as a name does, or that is a local part of any person's address in the run (the whole local part, the part before a `+tag`, or a noreply address's login, ignoring case), as GitHub names a commit by the account's login when it has no profile name. Printed beside the kind of the address's domain, or read by someone who knows the organisation's domain, such a name is the email. The rule is every answer's ([report-json.md](report-json.md#rules-that-carry-forward-whatever-the-format), "Where emails go", #52), decided per name by the run's directory (`identity.Directory.Withheld`, which `report.IdentitiesInput.Who` carries), so a name withheld here is withheld in every table, and so is a name that is the local part of an address outside the candidate. Without a directory, `NewIdentities` checks a name against the candidate's own addresses (`identity.RevealsAddress`).

### JSON, and the MCP server

`report.Identities`: `provenance`; `scope`; `addresses` (people), `bots` (left out), `shared` (of the people's addresses, those several people use that no rule linked) and `oversized` (groups left out); `candidates[]` of `{confidence, guess, commented, chained, rules[], name, addresses[], links[], mailmap}`; `rules[]` of `{id, matches, confidence, risk}`; `caveats`. An address is `{email, name, name_withheld, domain_kind, canonical, commits, co_authored, first, last, repos[], high, aliases}`, with repositories by key; `high` says it is in the candidate's high set, so the lines that map it are written as lines; and `aliases` counts the emails git's mailmap already rewrote to it in the run's commits (#53), 0 for none and in a run stored before facts.db kept them. Those emails, which a `.mailmap` folded away, are in no field of the answer: only in the mailmap lines, which need them, and which only a reader that may see emails gets. A link is `{rule, addresses[], name, from_name, hand_off, login}`: the indexes it links, the shared display name for `same-name`, whether a `same-local-part`'s local part is made from the name, for a hand-off `{gap_days, shared_files, files[]}`, the first five shared files as `{repo, repo_key, path}`, and for `same-forge-account` the account's login as GitHub last showed it (wave 10: the evidence names GitHub's link, which no display name makes), `""` when the login is a local part of an address of the run (`identity.Directory.LoginWithheld`), as a noreply address holds its login, so printing it would give the address away. An address also has `names_differ`: its commits carry names that differ. `confidence` is the weakest pair's; `commented` is true when the candidate has no high set, so every line is commented out, and false for a high candidate and for a weaker one with a high set, whose other addresses' lines are commented out.

Emails appear only in fields named `email`, and a name that gives an address away is `""` (with `name_withheld` true on an address), so no other field holds a person's address or a part of one; a link names no local part or account id (a login that is a local part is withheld), and the rule texts quote no whole address. The one exception is `mailmap`, a candidate's suggested lines exactly as the mailmap form writes them (`report.MailmapLines`, which the form writes through too, so the two cannot drift): it is `null` unless the reader may see emails and asks for the lines (`app.IdentitiesRequest.Mailmap`). The MCP server's `identity_candidates` pages the candidates, most confident first, as its other lists are ([mcp.md](mcp.md#tools), #58): concise rows carry each candidate's confidence, rules, name and addresses, without `links`, and each address's repositories cut to the first 3 (10 when detailed) with `repos_total`; detailed rows add `links`. Without `--allow-emails` it replaces each email by its id (`p-…`, as every answer does); with it, it asks for the lines (#69), so an agent can hand the user the line it suggests. The caveats are every answer's (`not-fetched`, and the repository caveats: a shallow clone's short history hides addresses), plus `mailmap-at-scan`, which also says that git follows no chain of lines ([Limits](#limits)).

### Text and Markdown name no address

They keep [report-json.md](report-json.md#text-and-markdown)'s rule, although the answer is about emails, and go one step further: they print no address and no part of one. A candidate pairs a person's addresses, such as a work address with a personal one, which is the most sensitive fact stillhere prints, and text and Markdown are what people paste into issues and chats. Each address is shown by its number and the kind of its domain: `main domain`, `GitHub noreply`, `machine` or `other domain`, with a letter (`other domain A`, `other domain B`) when a candidate has two addresses of a kind that can differ, the same letter for the same domain. A withheld name is `(name withheld)`.

The first version printed each address as its domain and the first six hex digits of its SHA-256 (`…@example.com (b5fc85)`), as the no-name placeholder does. Three flaws dropped it: beside a login used as a name, the domain completes the email; the domain alone says which personal provider or other employer a person uses; and an unsalted hash beside a name and a domain confirms a guessed address with one computation. A letter matches nothing outside the page. Printing emails in this one command's text was the other alternative; it would publish them the first time a page is pasted, while the person who edits the mailmap has `--format mailmap` and `--format json`.

### `--format mailmap`

The suggested lines, with the evidence above each candidate's lines as `#` comments. Each line maps one alias to the canonical address and the suggested name, `Name <canonical> <alias>` ([gitmailmap(5)](https://git-scm.com/docs/gitmailmap)), which replaces both for every commit with the alias, whatever its name; a line `Name <canonical>` comes first when the canonical address's own name differs from the suggested one. Only the lines that rest on evidence the display name does not explain (one GitHub account, or a local part not made from the name) between their addresses are written as lines: a high candidate's, and those of a weaker candidate's high set. Every other line, medium included, is commented out, so that adding the output to a `.mailmap` unread merges nobody whom the facts cannot tell from someone else: two people of one name look exactly like one person with two addresses. Git's parsing, verified on 2.50.1 with `git check-mailmap`, sets the rest:

- A line is a comment only when `#` is its first character: an indented `# Hank Split <hank@…> <gina@…>` maps `gina@…` to a person named `# Hank Split`. Every comment starts in the first column.
- A `#` inside a name is part of the name, and text after a line's last `>` is ignored; addresses and names match case-insensitively.
- A line whose name or address holds `<` or `>`, a control or format character or a byte that is not UTF-8, or whose name starts with `#`, cannot be the mapping it means, so it is written commented out, escaped, with the reason: its bytes must not reach a terminal either.
- git applies one line per commit and never follows a chain, which the header says. So the lines follow the ones git already applied (#53): for an alias that is itself the canonical address of lines git applied in the run's commits (its `aliases`), each of those emails gets a line to the candidate's canonical address too, in git's name-and-address form, `Name <canonical> Written Name <email>`, one for each name it was written with. git prefers a line that matches a commit's name and email over one that matches its email alone, whatever their order (verified on 2.50.1), so only that form replaces a name-keyed line as well as an email-only one; and it maps no commit the line it follows did not, where a line of the email alone would also take the commits a name-keyed line left out on purpose, as when one mailbox is split between two people. An alias git already rewrites to the canonical address wherever its commits are gets no line of its own: a repository's own `.mailmap` applies only inside it, so a line one repository holds is no line another has, and the alias gets its line unless every repository it appears in maps it there (and it appears there only as the target of other lines, the chain the line above follows). git keeps the last of two lines for one email and name, and reads the organisation's file (`mailmap.file`) after the repository's `.mailmap`, so a line added to either replaces one of the same form. The run knows only what its commits show git doing ([Limits](#limits)).

The fixtures' suggestions are their hand-written mailmaps byte for byte, commented out, and `git check-mailmap` over the printed form leaves every alias alone; with the `# ` removed from a suggested line, it maps the alias to the canonical identity ([SPEC.md](../../testdata/fixture/SPEC.md#identity-candidates-m2-26)). With GitHub's link between Ada's addresses, her line is written uncommented, and is the main fixture's mailmap byte for byte; with a `.mailmap` that already folds her second address into the first and, by name and address, another address into the second, the suggestion is the one line git still needs; and over two repositories, one whose `.mailmap` folds an old address that the other does not, the other gets its line ([SPEC.md](../../testdata/fixture/SPEC.md#pat-kim-and-alice-two-repositories-and-a-replica)).

## What unmerged identities do to knowledge loss

`knowledge_loss@1` and `knowledge_concentration@1` count each canonical email as a person, and their activity is the whole run's, so an older address of someone active elsewhere holds lines that look gone. Their values say how far that moves them (#104), a sensitivity analysis over the one uncertain input, so an agent or a lead can state a range rather than a point:

- **Where.** A scan computes the run's candidates (`identity.Candidates` over the whole run, `metrics.Input.Candidates`), and each value of the two metrics, about a repository, an area or a group, counts in its `Detail` the candidates with an address among the people holding lines there (`identity_candidates`, and `identity_candidates_high`), with the value they would have merged: their high-confidence lines, the high sets' (`if_merged_num` for knowledge loss's `Num`, `if_merged` for concentration's authors), which `--format mailmap` writes as lines, and every candidate whole (`if_all_merged_num`, `if_all_merged`), the most an unmerged identity can move it. `identity_candidates_high` counts the candidates with a high set. The metrics compute them with their own functions over the same lines, each address replaced by its candidate's canonical one, so the definition is applied once ([metrics.md](../metrics.md#knowledge_loss1-per-area)).
- **Shown.** The report's `knowledge_loss` and `concentration` carry them as `if_merged` ([report-json.md](report-json.md#the-objects)), and every section that shows either number, a card, an overview and `explain` of either metric at any scope, an area's included, carries an `unmerged-identities` caveat that names the count, the range and where the lines are (`stillhere identities --format mailmap`; over MCP, the candidates' `mailmap` field with `--allow-emails`), when merging would move one of them. A section where it moves neither carries `if_merged` and no caveat: on go-chi, 8 of the 17 cards whose candidates hold lines, whose range was the value three times over, so the caveats that matter are not buried (SR-14). The overview of every repository adds its repositories' values up, so it counts a candidate once per repository it holds lines in and says so, and names no count of high ones.
- **Bounds.** Merging only joins people, so `if_all_merged_num ≤ if_merged_num ≤ Num`; knowledge loss's `Den` does not move. On the main fixture without its mailmap, with GitHub's link between Ada's addresses: 11/34 as keyed, 4/34 with Ada merged, as with the mailmap, and 4/34 with Gina and Hank merged too, both quiet.
- **Not applied.** The values as keyed stay the run's numbers: merging on GitHub's word at scan time would make stillhere a second owner of the merges ([options](#options)). A run stored before has no such `Detail` and no such caveat.

## Counting people for a floor

The AI-share floor ([ADR 0007's amendment](../adr/0007-ai-assisted-attribution.md#amendment-the-shares-that-leave-the-machine)) counts people with `identity.Blocks`, which reads the same keys the other way. A block holds the addresses a candidate holds, those of every hand-off chain however long (one longer than a candidate may hold included), and every two that share the words of any name seen with them, as author or co-author (a default name such as John Doe included), a local part (without its `+tag`, a noreply address's login), a GitHub account id or an account GitHub's links attribute them to (an address linked to two accounts joins both), with none of the vetoes above, through any number of links. The rules lean to precision because a wrong merge invents a person; a floor leans to recall because a missed link lets one person's own share out, while a wrong one only lowers a count, so it never lets out a share of fewer than three people; only a missed link can ([Limits](#limits)). Record linkage draws the same line between blocking and classification (Christen, *Data Matching*, Springer 2012, ch. 4). A block merges no one on any page and is never suggested as a line.

## Limits

- **Chains through existing lines, as far as the commits show them.** git applies one `.mailmap` line per commit and never follows a chain (verified with `git check-mailmap` on 2.50.1). A run records what git rewrote, per repository (`RepoFacts.Aliases`, #53): the author and trailer emails and names of its history's commits and of the commits blame reached, read beside their mailmapped forms, so the suggestions follow those lines and drop the ones git already applies. stillhere never parses a mailmap, so a line no commit of the run used is unknown to it, and a run stored before facts.db kept them knows none: there, the mailmap form's header and the `mailmap-at-scan` caveat say that the run shows git rewriting nothing, and tell the person to change such lines to the new canonical address themselves.
- **A line that changes only a name.** A `.mailmap` line keyed by a name that keeps the address (`Ada <ada@x> Old Name <ada@x>`) leaves no record, since only an email git changed is one; the line suggested for that address names its email alone, which such a line beats for the commits with that name. A follow-up records names git changed too, should dogfooding show it.
- **No fuzzy names.** Edit distance, nicknames (Bob, Robert) and transliteration (José, Jose) would add recall and false merges; the core has no Unicode normalisation (it imports the standard library only), so a name spelt in two Unicode forms is two names.
- **A changed name.** An address whose owner changed name in a way the subset rule cannot see (Ada Lovelace, then Ada King) looks like a mailbox two people share, so only GitHub's link compares it: without one, a missed merge, never a false one.
- **GitHub only.** Only `users.noreply.github.com`, the documented form, is read as a noreply domain; an Enterprise host's form is unverified (#44).
- **GitHub's links come from what a sync read.** `same-forge-account` reads the commits of the pull requests a sync copied: on the go-chi organisation, the 255 pull requests updated in the run's year make 2 candidates high, all 970 synced ones 8, which is why a run keeps the older ones' links, one for each repository, address and account (`identity.KeptLinks`, [ADR 0011's amendment](../adr/0011-a-run-keeps-the-github-facts-it-read.md#amendment-the-links-of-older-pull-requests-2026-10-15-103)). A first sync copies a year of pull requests (#100), so a sync's links pass also asks GitHub about each author email of a mirror's history once, through its newest commit on the default branch (`ForgeSource.LinkAuthors`, `forge_links`, ADR 0013), and a scan reads those answers with the replica: over go-chi's emails it links 242 emails and 6 accounts of several, as many as every pull request ever synced did, where the window's pull requests link 34 and 2. An email is asked about through one commit, so one GitHub does not attribute there, as for a commit made before the address was verified, links nothing, even when an older commit of it is attributed.
- **The floor's blocks** join only addresses that have something in common: a name's words, a local part, a GitHub account (an id or GitHub's link), a candidate or a hand-off chain. One person's addresses with nothing in common count as several people, so a share of two people can leave as three until a `.mailmap` line merges them (ADR 0007's amendment, #86). An empty author address is a missing fact: beside other people it may be any of them and adds no one, and alone it is one person (`app.aiShareCount`), while the run takes it for a person's rather than a bot's, which it decides once per run by the name most often seen with it (#74).
- **Hand-offs** need the earlier address quiet for 90 days, so a change of address shows up 90 days after the old address's last commit, and only between addresses no other rule links.

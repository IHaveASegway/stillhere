# Report JSON

Status: v1 shape as emitted by `report.Build` and `report.JSON` (#11) · 2026-10-14 · `stillhere.report/v1`. No external consumer exists yet, so the shape may still change until the first tag; after it, the rules below hold.

`stillhere week`, `scan` and `report` print one `stillhere.report/v1` document with `--format json`. The read commands (`explain`, `who-knows`, `me`, `identities`, `validate`, `metrics`) print their own answers, described [below](#the-read-commands-answers). The Go types in `internal/report` are the same shapes, so the MCP server (#15) answers from them too.

## Rules that carry forward, whatever the format

- **Schema changes.** Adding a field does not change the version. Renaming a field, removing one, or changing what it means does. Reports can always be regenerated, so the old and new shapes are never written side by side.
- **Null and empty values.** An absent section is `null`; an empty list is `[]` and an empty map `{}`, never `null` and never omitted.
  - `null`: `run` in a week report (and in a scan that stored nothing); `still_here` for a repository without line facts (every week run, shallow and partial clones) and, with `week`, for a failed repository; `card.age` when the first commit is unknown; a share or a concentration whose metric gave no value; the numbers `surviving@1` gives (`size.prod_files`, `size.prod_lines`, `card.people`, `totals.prod_files`, `totals.prod_lines`, `totals.people`) and `card.bots` when the repository or scope has no line facts, so that "unknown" never reads as 0.
  - `[]`: `errors.blame` in a clean scan, `warnings` with none, `ranks` without `--rank`.
  - Each kind of error has exactly one list, never a second list under another name.
- **Strings and numbers.** Strings are UTF-8. git does not guarantee it: a commit written without an encoding header (by cvs2git, early git-svn or JGit) keeps its Latin-1 bytes, and `--encoding=UTF-8` leaves them as they are. Such bytes become U+FFFD in every format, as encoding/json v1 wrote them, so one odd commit cannot fail a report. A number that is not finite (NaN, an infinity) is `null`. The document is written only once it is whole, never cut off halfway.
- **Where emails go.** Emails appear in JSON, the machine output, only as the join key of a person row (`email`, and a person subject's `key`), and never in text or Markdown, which people read, paste and share. No other field prints a part of one either.
  - **A display name that gives an address away is withheld in every format**, JSON included: one that holds an `@`, as an address typed as a name does, or that is, ignoring case, a local part of any person's address in the run (the whole of it, the part before a `+tag`, or a GitHub noreply address's login), as GitHub names a commit by the login of an account without a profile name. `John Doe` on `john.doe@` is a name and stays. The rule is the name's, decided over every address of the run (`identity.Directory.Withheld`), not the row's own address alone: when `jdoe@corp.example` is named `jdoe`, the name is withheld on `john.doe@mail.example` too if he is also called `jdoe`, or the page would print on one row the local part it withholds on the other, and the caveats and the MCP server's name lookup would point from one to the other. The identities answer applies the same rule ([identities.md](identities.md#output)).
  - Such a row has `name` `""` and `name_withheld` `true`, so a reader that drops the email fields, as the MCP server does without `--allow-emails`, sends no address under another field's name. A person git records without a name has `name` `""` and `name_withheld` `false`.
  - **Bots.** A bot's or an agent's address is no person's, so its local part withholds no name: `dependabot[bot]` and `Copilot` are shown, though each is its own noreply login. A bot's name that holds an `@` is withheld like anyone's, so no text or Markdown page prints it.
  - **GitHub logins.** An account that no commit of the run links to an email is keyed `@login`, the login lowercased, as GitHub compares logins, and named by the login as GitHub last showed it (`@Zoe` for the key `@zoe`; `identity.Directory.Reviewer` and `Name`; a run stored before #69, which kept the case in its keys, is read with them lowercased), an app `@login[bot]` ([ADR 0004](../adr/0004-github-behind-sync-boundary.md)), even when the login is also the local part of an address in the run. A login is the account's public name, which GitHub shows beside every review the row counts, and the page ties it to no address: the forge could not link the two, which is why the row is keyed by login. Withholding it would hide it from text and Markdown only, since `email` and `key` hold it in JSON and over MCP, and a `name_withheld` on a login would tell an agent that the login is a local part in the run, which the login alone does not. Revisit if a rule ever links logins to addresses by their local parts.
  - **Addresses in repository text** are withheld in every format, JSON included, and printed as `(address withheld)`: a commit subject that thanks a teammate or quotes a customer, a git message, a directory's name. The rule is the one the MCP server's egress applies, `internal/redact`'s: an address of a person on the page wherever it appears, as a whole address, and in text that is not a path (`path`, `old_path`) whatever looks like an address (a domain that ends in letters, or an IP literal; not a version pin such as `lodash@4.17.21`, a metric id such as `durable@1`, or the `user@host:path` of an scp-like remote). A path keeps an address no one on the page has, so it stays the repository's path. The renderers apply it to every string of the document's published shape but the fields above (`report.Text`, `report.Markdown`, `report.JSON`), so a field added later is covered too; the model itself keeps the text, which the MCP server withholds by its own operator, an id. The label is fixed, and says nothing about the address, not even which of two it was. A page's people are its own: an address in a dotless domain (`root@buildbox`) of a person of the run who is not on the page is printed.
  - **Labels.** Text and Markdown show a person without a name as `(no name 1)` and one whose name is withheld as `(name withheld 1)`, numbered in the order the page first names them: the same person keeps one label everywhere on a page, two such people stay apart, and a label matches nothing outside its page. git records any name, so a name with a label's shape, or one that starts with a double quote, is printed quoted, as Go quotes a string (`"(no name 1)"`): no name reads as a label, and no two names print alike unless they are alike. A label is a counter, not a hash: the `(no name 1a2b3c)` of earlier versions, the start of the email's SHA-256, let anyone who guessed an address confirm it with one hash (ENISA, *Pseudonymisation techniques and best practices*, 2019, §7.2).
  - AI payloads never contain emails, absolute paths, warnings or errors; that is specified with the narrator in M4.
- **Overviews replace group rollups.**
  - `overviews` has one element per group, in `groups` order, with `scope: {"kind": "group", "key": <name>}`. A run with `--scope all`, or without groups (only repositories named directly), has one more, first: every repository, `scope: {"kind": "all", "key": ""}`.
  - Its person rows are the metrics' values for the overview's scope: counts for one email summed within the group, and `files_with_majority` summed per repository with the concentration walk re-run on the summed column ([blame-collector.md](blame-collector.md#reductions-the-fixture-asserts)). No metric walks every repository at once, so the every-repository overview's `concentration` is `null`.
  - A person in two groups is a row in each. Groups are kept apart as ranks are ([metrics.md](../metrics.md#ranking-rules)): there is no cross-group total unless `--scope all` asks for one, so in a run with groups a repository named directly has a card and is in no overview.
- **Joining.** People are joined on the canonical email after mailmap, never on a private person id. Repositories are joined on `key` (`groups[].repos`, `provenance.heads[].key`, `scope.key`).
- **Hotspot units.** `window_main_dev_ownership` is a 0–1 ratio and coupling `degree` is an integer percent ([hotspots-code-maat.md](hotspots-code-maat.md)). These fields exist only if hotspots ship.
- **Warning codes.** Warnings are `{code, message}`. A repository's warnings are on the repository (`repos[].warnings`) and its card's caveats: `duplicate-repo` (on the repository kept: another clone of its remote was skipped), `shallow-clone`, `shallow-window`, `partial-clone`, `ignore-revs` (its own `.git-blame-ignore-revs` was not used, or not whole), `head-after-now` (#70: the run read the newest commit on its branch's first-parent chain committed before `--now`, an older commit than the branch's head; the message names the commit read, when it was committed, the head, and how many landings came at or after `--now`), `dated-after-now` (#70's review, scan only, when blame ran: landings below the commit read are dated at or after `--now`, as a backdated commit or a clock that ran ahead leaves; the message names the commit read and counts them). The run's are in the top-level `warnings`: `excluded-repo` (one per repository `--exclude-repo` left out, which is how the report lists them), `path-failed` (one per path that gave no repository: a PATH that is neither a repository nor a group, a directory with no repository among its immediate children, whose message says what to pass instead ([discovery.md](discovery.md#rules-in-order), rule 3), or a repository git cannot read or whose default branch has no commit yet) and `no-commit-before-now` (#70: one per repository whose default branch has no commit before `--now`, which the run leaves out, as it leaves out an excluded one). A `path-failed` warning makes a scan `partial`; `no-commit-before-now` does not, since the repository did not exist yet at `--now`.
- **Determinism.** Two runs on the same inputs and `--now` render byte-identical JSON once `timings` is removed: object fields in a fixed order, map keys sorted, every list sorted. A second scan into the same facts.db also gets the next `run.id` (and `provenance.run_id`), so a comparison across one database removes those too.

Changes from the 2026-10-07 draft:

- `generated_at` is gone: a wall-clock field breaks byte-identical output. The run's start and finish are in `timings`.
- `group_rollups` became `overviews`, one per group, with totals, the people's breadth (repos), depth (majority files), survival and activity, bots, the AI-assisted and bot shares, knowledge loss, concentration, provenance and caveats.
- Every repository has a `card` (age, size, who it is made of, concentration, knowledge loss, AI and bot share, landings, caveats): what an agent or a lead reads first.
- `majority_owner_concentration` moved from `still_here` to `card.concentration` and the overview's `concentration`; `files_with_majority` went with it.
- `policy.weights_applied_to_headline` is gone with open decision #2's weights; `blame_ignore_revs` gained `revs`; `groups[].repo_names` became `groups[].repos`, the repository keys.
- `caveats` (what could make this wrong) are new at every level, and so are `kind`, `run`, `history`, `metrics`, `ranks` and `line_facts`. `timings` lost the cache and hotspot counters until those ship, and `hotspots` returns with M5.
- `provenance.forge.repos[]` gained `from` and `missing` (#101, [ADR 0013](../adr/0013-sync-reads-bounded-passes-and-checks-the-replica.md)), and `updated` now holds only with them: every pull request last updated from `from` until `updated` was in the replica, unless `missing` is not 0. Before, every replica was read from a repository's first pull request, which `from: null` still says, so `updated` read alone overstates a replica a bounded sync wrote. This narrows what `updated` means, which the rule above counts as a change of version; it stays `stillhere.report/v1` because no tag has been cut, so no consumer reads v1 yet (the status line), and a reader written from this page reads the three together.
- Narration, `geared_fp` and `geared_fp_estimated` stay out: narration is specified with the MCP and narrator work in M4, gearing only if open decision #2 is approved. The hotspot row shape lives in [hotspots-code-maat.md](hotspots-code-maat.md).

## The objects

| Object | Fields | Notes |
| --- | --- | --- |
| `run` | `id`, `status`, `tool_version`, `options` | `status` is `complete` or `partial` (a repository failed, or a path gave no repository). `options` are the effective scan options: `jobs`, `scope`, `rank` (comma-separated), `exclude_repo` and `paths` (newline-separated), `ignore_revs_file`, `history_days`, `policy` (the file read). `paths` are the PATH arguments as discovery resolved them, absolute: each group's directory and each repository named directly, never the argument as typed, which may be a URL with a token in it; a PATH that gave no repository is a `path-failed` warning instead. Every value is scrubbed ([git-invocation.md](git-invocation.md#url-scrubbing)): never a secret. |
| `window` | `days`, `days_from`, `sort`, `sort_from`, `since`, `until`, `date_field`, `walk`, `diff` | The landed@1 window: what "landed" means. `*_from` is `cli` or `policy`. |
| `history` | `since`, `until` | The landing window the history covers: 365 days for a scan, the window for a week run. |
| `provenance` | `run_id`, `as_of`, `policy`, `heads[]`, `metrics[]`, `forge` | On every overview, card, rank table and answer, so each reads on its own. `run_id` is 0 for a week report. `heads` are `{repo, key, branch, sha}`, where `sha` is the commit the run read: the newest first-parent commit of `branch` committed before `--now` (#70). `forge` dates the GitHub data the run read for the repositories in `heads` ([ADR 0004](../adr/0004-github-behind-sync-boundary.md)): `{as_of, repos[], metrics[]}`, where `metrics` are the section's metrics that read GitHub data (`metrics.Definition.Forge`, the registry's one declaration: `knowledge_loss@1`, `reviews_given@1`, `who_knows@1`), the numbers `as_of` dates and text and Markdown date in the section's header, `[]` when it shows none; each repository `{repo, key, updated, synced, from, missing}`, the forge repository (`owner/name`) and the run's repository key it joined, both as the run read them, so a later rename on the forge changes neither, and the replica's watermark as the run read it ([ADR 0013](../adr/0013-sync-reads-bounded-passes-and-checks-the-replica.md)): every pull request last updated from `from` (`null`: from the repository's first) until `updated`, when the last completed pass began on GitHub's clock, was in it, unless `missing` is not 0: the number of pull requests updated in the history window that GitHub counted and the replica lacked at the last sync's completeness check. `synced` is when the last sync that brought it up to date started (`null` until one finished). A repository the replica held no GitHub data for (neither a page nor a finished sync, as when a first sync stopped before its first page) is not listed; one listed with a `null` `synced` had pages of a first sync that stopped halfway. `as_of` is the oldest `synced`, since a number over several repositories is as current as its stalest one, and `null` while a first sync has not finished. On `me` and on `explain` of a metric that reads GitHub data, a value in a group or in every repository counts the reviews of each of its repositories, so `heads` and `forge` cover all of them. `forge` is `null` when none of those repositories had GitHub data, and in a week report. |
| `caveats[]` | `code`, `message`, `repos[]` | What could make the section wrong ([codes](#caveats)). `repos` names the repositories a caveat concerns. On a card it is empty, but for the caveats of GitHub data: `forge-not-synced` and `forge-incomplete` name the repositories whose GitHub data is missing, partly synced or incomplete, the card's own one (empty when the message says no repository of the section has any) or, for `forge-not-synced`'s second form, the run's others. |
| `overviews[]` | `scope`, `provenance`, `totals`, `people`, `week`, `concentration`, `knowledge_loss`, `ai_assisted`, `bot_share`, `caveats` | Every repository first, with `--scope all` or without groups; then one per group. `totals` are `repos`, `repos_ok`, `repos_failed`, `prod_paths` (paths with role prod at each HEAD, whether or not they hold a line), `prod_files` and `prod_lines` (prod files with surviving lines, and those lines), `people` (humans with surviving prod lines), `landers` (humans with a landing in the window), `bots` (bots with either), `landings_window` and `landings_history`. |
| `ranks[]` | `metric`, `question`, `scope`, `window`, `percent`, `min_n`, `provenance`, `ranked[]`, `below_min[]`, `bots[]`, `caveats` | One per metric named by `--rank` and scope: each group and each repository named directly, or one `all` scope with `--scope all`. A table in which nobody has a change the metric counts is still there, empty, with a `no-values` caveat. Rows are `{email, name, name_withheld, rank_lo, rank_hi, estimate, lo, hi, n}`; `lo`, `hi` and the ranks are 0 below the minimum. Bots are never ranked. |
| `repos[]` | identity, `status`, `error`, `line_facts`, `card`, `warnings`, `errors`, `skipped`, `blame_ignore_revs`, `week`, `still_here` | Sorted by group, name and key. `skipped` counts every classified path, at HEAD or touched by the history; a partial clone is classified too, so its paths count. |
| `card` | `provenance`, `age`, `size`, `made_of[]`, `people`, `bots`, `concentration`, `knowledge_loss`, `ai_assisted`, `bot_share`, `landings`, `caveats` | `size` is `{files, prod_paths, prod_files, prod_lines}`: paths and prod paths at HEAD, then the prod files that hold surviving lines and those lines. `made_of` is the top five humans by surviving prod lines, with their share of the repository's: `{email, name, name_withheld, prod_lines, share}`. |
| shares | `metric`, `num`, `den`, `value`, `if_merged` | `value` is `num / den`, a 0–1 ratio. A group's share is its own value when the metric gives one, else the ratio of its repositories' summed parts, which is exact because the parts are counts. `if_merged` (#104) is `knowledge_loss`'s alone, and `null` for every other share: when identity candidates hold lines in the scope, `{candidates, high, high_num, high_value, all_num, all_value}`, the candidates and those among them with high-confidence lines (a high candidate, or a weaker one's high set), and the share with the high-confidence lines merged and with every candidate merged, over the same `den` ([identities.md](identities.md#what-unmerged-identities-do-to-knowledge-loss)); `null` when none does, and in a run stored before. The overview of every repository adds its repositories' up, so a candidate in two of them counts twice in `candidates` and in `high`, while the lines add up exactly. |
| `concentration` | `metric`, `files_with_majority`, `authors_in_prefix`, `bots_in_prefix`, `label`, `if_merged` | `if_merged` (#104): when identity candidates hold lines in the scope, `{candidates, high, high_authors, all_authors}`, the authors in the prefix with the high-confidence lines merged and with every candidate merged; `null` otherwise, and in a run stored before. |
| `timings` | `started`, `finished`, `total_ms`, `discover_ms`, `collect_ms`, `metrics_ms`, `rank_ms`, `store_ms`, `load_ms`, `repos[]` | Wall clock: the only part two identical runs do not share. `report` gives the stored run's `started` and `finished`, and its own `load_ms` and `rank_ms`. |

## Where the numbers come from

The report computes no metric: it arranges the values `internal/metrics` computed, as `internal/report/values.go` lays them out, and counts facts that need no identity or policy rule. This table is that file for readers; a metric that lays its values out differently changes both.

| Report field | Source |
| --- | --- |
| `week` rows: `commits`, `lines_added`, `prod_lines_added` | `landed@1`, person subjects, in the repository's scope (`repos[].week`) or the overview's (`overviews[].week`): `Value` is the landings credited; `Detail` `lines_added`, `prod_lines_added` |
| `still_here` and `people` rows: `prod_nonblank_lines`, `majority_files`, `lines_by_role`, `repos`, `landings_365d` | `surviving@1`, person subjects, in the repository's or the overview's scope: `Value` is prod non-blank lines; `Detail` `majority_files` (else `majority_owner@1`'s value for the person), `lines_<role>` for every role, `repos` (breadth), `landings_365d` (activity) |
| `size.prod_lines`, `size.prod_files`, `card.people`, `card.bot_share`; the same in `totals` and an overview's `bot_share` | `surviving@1`'s value about the repository or the group itself (subject the repository or the group): `Value` is prod lines; `Detail` `prod_files` (prod files with surviving lines), `people` (humans with surviving prod lines), `bot_share` (bots' lines over prod lines; the share's `num` is that times `den`). surviving@1 is the one definition of these numbers, so the report counts none of them from facts. The every-repository overview, which the metric has no such value for, adds up its repositories' values (exact: they are counts per repository) and counts `people` among its own `people` rows, since one person can hold lines in several repositories. |
| `concentration` | `knowledge_concentration@1`, the value about the scope as a whole (subject the repository, or its root area `<key>:`; in a group scope the one value about neither a person nor a change): `Value` is `authors_in_prefix`; `Detail` `files_with_majority`, `bots_in_prefix`; `if_merged` from `Detail` `identity_candidates`, `identity_candidates_high`, `if_merged`, `if_all_merged` |
| `knowledge_loss` | `knowledge_loss@1`, the value about the scope as a whole: `Num` lines held by people gone quiet, `Den` lines held by people; `if_merged` from `Detail` `identity_candidates`, `identity_candidates_high`, `if_merged_num`, `if_all_merged_num` |
| `ai_assisted` | `ai_assisted@1`, the value about the scope as a whole: `Num` AI-assisted landings, `Den` landings in 365 days. A person's own share appears only in `stillhere me` (ADR 0007). |
| `made_of`, `card.bots` | the repository's `still_here` rows |
| ranks | `rank.Intervals` over the metric's own clusters, window and eligibility (`metrics.Ranked.Clusters`), with bots left out by the caller; intervals the run stored are used as they are |
| who-knows lists | `who_knows@1` for the path, per repository: the value about the path itself (subject the repository, or the area `<key>:<path>`: `Value` prod lines, `Detail` `prod_files`, `files_with_majority`), and one value per person (`Value` prod lines under the path; `Detail` `majority_files`, `recent_landings`, `top_author`, the place 1 to 5 among the top authors, and `recent_reviews`, the recent reviewers' pull requests, present only when the run has GitHub data for the repository). Without `top_author`, the top five are picked by the same rule: prod lines, then email. A reviewer the run cannot link to an email is the subject `@login`. |
| `size.files`, `size.prod_paths`, `totals.prod_paths`, `card.landings`, `card.age`, `totals` counts of repositories and landings, `skipped`, `files_blamed` | facts: path classes at HEAD, landings in each window, `FirstCommit`, blame errors |

A metric whose values are missing although the run has the facts it computes from gets a `no-values` caveat, so an empty section never passes for a real zero. So does a rank table asked for in which nobody has a change the metric counts, a who-knows answer whose `who_knows@1` gave nothing although the run holds surviving prod lines under the path, and one about a path that none of the collected repositories it asks about has (#71): each reads as missing, never as "nobody".

## Caveats

| Code | When |
| --- | --- |
| `not-fetched` | Always: analysis never fetches, so a stale clone gives a stale report. |
| `failed` | A repository failed and adds nothing. |
| `shallow-clone` | Blame did not run: its surviving lines, ownership and durability are missing. |
| `partial-clone` | No line facts: only its landings and commits count; where its blobs are absent, no path is skipped as too big or generated. |
| `shallow-window` | The shallow boundary is inside the history window. |
| `blame-errors` | Blame failed on some files; their lines are missing. |
| `no-ignore-revs` | A repository with at least 10,000 surviving prod lines has no `.git-blame-ignore-revs`: a formatting commit would take the credit for every line it touched. |
| `duplicate-repo` | Another clone of the repository's remote was skipped, so the repository is counted once; on the kept repository's card. |
| `head-after-now` | The run read the newest first-parent commit of the repository's default branch committed before `--now`, because its head is newer: the caveat names the commit read and how many landings came at or after `--now`, which no number counts (the repository's warning, as it stands; a section over several repositories says so once and names them). `provenance.heads` and `repos[].head` record the commit read. |
| `dated-after-now` | Landings below the commit read are dated at or after `--now`, as a backdated commit above newer ones or a clock that ran ahead leaves: blame counts the lines they hold, but no window counts them, so their authors can look inactive. The caveat names the commit read and counts them (the repository's warning, as it stands; a section over several repositories says so once and names them). Only a scan whose blame ran gives it. |
| `excluded-repo`, `path-failed`, `no-commit-before-now` | Run-level warnings, counted, with the first one's reason; `warnings` lists each one. |
| `unmerged-identities` | Display names that more than one email shares were not merged; a `.mailmap` line merges them if they are one person, and `stillhere identities` (over MCP, `identity_candidates`) suggests the lines with the evidence for each. Names are compared as `identities` compares them (`identity.Directory.NameKey`): case, spacing and punctuation never tell two apart, and a default name (`Your Name`), a bot's and a login's are no name to share, so the caveat names a name exactly when `identities` compares it; one written two ways is printed the first way in byte order. The report's sections, `explain` and `me` (another email has the person's name), and `who-knows` (two people it lists share one) carry it. A shared name that gives an address away is counted, never printed. It is also where `knowledge_loss@1` and `knowledge_concentration@1` are (#104), at every scope: a card, an overview, and `explain` of either metric about a repository, a group or an area. When identity candidates hold lines in the scope (`Detail` `identity_candidates`) and merging them would move either value, it says how many, the value as the run keys people, with the high-confidence lines merged and with every candidate merged (the `if_merged` fields), and where the `.mailmap` lines are (`stillhere identities --format mailmap`; over MCP, the candidates' `mailmap` field, sent with `--allow-emails`); where merging moves neither, the section carries the `if_merged` fields and no caveat. The overview of every repository counts a candidate once per repository it holds lines in, and says so. Activity is the whole run's, so an older address of someone active in another repository looks gone even where no display name is shared. A section that carries both says them in one caveat. |
| `mailmap-at-scan` | Every `identities` answer: its addresses are the run's, which git mailmapped when the run was scanned, so a `.mailmap` line added since takes effect at the next scan; git applies one line per commit and never follows a chain, so the suggestions follow the lines the run's commits show git applying, naming the name and the email each line matched, and leave out a line git already applies wherever the address's commits are (#53); when the scope's commits show git rewriting no email, either no line applied or the run was stored before facts.db recorded them, and the caveat says that the person then changes such lines themselves. |
| `no-values` | A metric the report reads gave no value although the run has its facts; a rank table asked for is empty; a who-knows answer is missing, as when its path is under no path of the repositories asked about, which the message says, with the run's other repositories that have the path, or else how the run's paths are written (#71). |
| `ai-lower-bound` | An AI-assisted share is shown: editor completions leave no trace. A person's own page (`me`) that holds their share, and `explain` of `ai_assisted@1`, carry it too. |
| `validity` | A ranked metric's validity note, such as unvalidated until the labelled-sample check, wherever its values, ranks or clusters are shown: its rank table and `explain` of it (`Validity: …`), and a page that shows several metrics, `me` and the MCP server's `changes` and `highlights`, once per note, naming the metrics that share it (`Validity of durable@1 and simplifying@1: …`, `report.ValidityCaveats`). |
| `unmatched-labels` | `validate` only: labelled changes that are not landings of the run. |
| `forge-not-synced` | A section shows the numbers of a metric that reads GitHub data (`metrics.Definition.Forge`: `knowledge_loss@1`, `reviews_given@1`, `who_knows@1`), and some of the repositories behind them that the run collected have no GitHub data in the replica the run read, or one's first sync did not finish: the metric counts none, or only some, of their reviews, and a value `reviews_given@1` lacks is absent, not 0. The repositories behind a number are its section's: a rank table's scope, a card's repository, an overview's members, the repositories a who-knows answer lists, and every repository of the run for `me` and `explain`. A card's or an overview's `knowledge_loss@1` also counts a review in any other repository of the run as activity, so, in a run that read GitHub data, a second `forge-not-synced` caveat names, in `repos` (on a card too), the run's other collected repositories on a forge whose GitHub data is missing or only partly synced: someone who holds lines in the section and reviewed there can look gone. A section about one such metric alone, its rank table or `explain` of it, says so even when the run read no GitHub data at all, naming `stillhere sync github` when one of those repositories has an origin on a forge to sync from. Any other section (a card or an overview, which show `knowledge_loss@1`, a who-knows answer, `me`) weighs only the repositories with an origin on a forge, whose GitHub data a sync could copy, and says nothing in a run that read no GitHub data, the git-only case each metric's definition describes, so a git-only user gets no GitHub caveat on every page; in a run that read some, it names the repositories on a forge without it. Never in the report's own `caveats`. |
| `forge-incomplete` | A section shows the numbers of a metric that reads GitHub data, and the last sync of some of its repositories, before the run read them, found pull requests updated in the history window that GitHub counts and the replica lacks, and could not fill them in ([ADR 0013](../adr/0013-sync-reads-bounded-passes-and-checks-the-replica.md)): the metric counts only the ones the replica holds, so a review count can be low. The message counts the pull requests missing, `repos` names the repositories, and the next sync reads their window again. It stands where `forge-not-synced` would, for the same sections; such a repository elsewhere in the run is named in `forge-not-synced`'s second form, on a card's or an overview's `knowledge_loss@1`, as one whose GitHub data is only partly there. |
| `pulls-not-listed` | `explain` of `reviews_given@1`: the changes behind the values are pull requests, which explain does not list yet, although the run keeps them ([ADR 0011](../adr/0011-a-run-keeps-the-github-facts-it-read.md)). |

Text and Markdown print `not-fetched` and `ai-lower-bound` once, at the top; JSON repeats them in every section, so a section handed to an agent carries them.

## The read commands' answers

Each answer starts with `provenance` and ends with `caveats`. Values print as `{metric, scope, subject, window, value, num, den, n, detail}`, where `subject` is `{kind, key, name, name_withheld, bot}`, `key` is a person's canonical email (or `@login`), and `name` and `name_withheld` follow [the rule above](#rules-that-carry-forward-whatever-the-format) ("Where emails go").

| Command | Answer | Fields |
| --- | --- | --- |
| `explain METRIC --person EMAIL` | `Explain` | `metric` (the definition: `id`, `question`, `unit`, `ranked`, `forge` (it reads GitHub data), `ratio` (its values are shares, `num` of `den`, printed as a percent), `eligibility`, `blind_spots`, `gaming`, `oracle`, `validity`), `subject`, `values[]` (one per scope and window), `changes[]` (a ranked metric's clusters for the person that are landings: `{repo, repo_key, landing, time, merge, title, num, den}`; `title` is the landing's commit subject, local output only and never sent to an AI, with each address in it printed as `(address withheld)` ("Where emails go"); `reviews_given@1`'s are pull requests, which are not listed yet, with a `pulls-not-listed` caveat). `ai_assisted` about a person is a usage error: a person's own AI-assisted share is on their own page only (ADR 0007). So is a metric about a kind of subject no scan stores its values about (`metrics.Definition.Subjects`: `knowledge_loss@1` about a person), in every run, one that holds no value of it included, which would otherwise answer with nothing: the message names the kinds its values are about and what answers instead (`stillhere report`); and `who_knows@1`, which no scan stores, with `stillhere who-knows PATH`. A person is named by canonical email, or by `@login` for a reviewer the run links to no email. |

A reviewer the run cannot link to an email has the `@login` in `email`. `recent_reviewers` is `[]` also for a repository without GitHub data, which `provenance.forge` then does not list, and text and Markdown print its reviewers line only for a repository with GitHub data or a reviewer. A first row that names a change with a misspelt label is an error, as on any other row.

## Text and Markdown

- **Text** is for a terminal, read top to bottom: the provenance header, what could make the report wrong, the overviews, the ranks, then each repository's card and tables. No line is wider than 100 columns, except one that holds a single unbreakable word such as a URL: headers wrap like prose, and a table too wide for the line cuts its widest text columns (names, titles, details) with `…`, none below 8 columns; numbers are never cut. Untrusted text (names, paths, subjects, git messages) is printed with control and format characters escaped as Go quotes them, so an escape sequence in an author name cannot reach the terminal.
- **Markdown** is GitHub-flavoured, with the same sections, for pasting into an issue or a pull request. Untrusted text is backslash-escaped and `&` becomes `&amp;`, so `<img src=x>` and `Frank & Sons` render as text; paths, SHAs and remotes are code spans. GitHub would link `@name` as a mention, which notifies that account, and `#12` as a reference, which posts a back-link on issue 12, so `@` and `#` in untrusted text are followed by a word joiner (U+2060): the text reads the same and links nobody. A repository's local path is left out, though a warning that concerns a path still names it.
- **Neither** prints an email. Ranked metrics appear only as rank tables, with their 95% intervals, the people below the minimum listed and not ranked, and bots apart ([ADR 0001](../adr/0001-measure-changes-rank-per-metric.md)): a table sorted by a ranked metric's point values would be a rank without its uncertainty.

## Exit codes

| Code | When |
| --- | --- |
| 0 | At least one repo produced week or still-here facts. This includes partial failure, clone-health skips, and skipped hotspots. For `sync github`, at least one repository synced, a partial sync included: its last line on stdout, printed after every sync that began its run, says how many repositories synced, failed, or are missing pull requests, and how many pull requests it read, so a scheduled sync's log tells them apart (`sync github: 5 of 6 repositories synced, 1 failed; 1464 pull requests read in 1m58s`). |
| 1 | No repo produced facts: every path failed, none was a repo, or `--exclude-repo` left none. The report is still printed, with each repository's error, and a scan stores no run. A read command asked about a run or a person the database does not hold also exits 1, and its error line names the database and says what to do (#71). |
| 2 | A usage error (see below). |
| 128 + n | Interrupted by signal n (SIGINT, SIGTERM or SIGHUP). stillhere stops every git process, prints `stillhere <command>: interrupted` (#71), then ends itself with the same signal, so a shell sees it die by that signal (`$?` is 130 for Ctrl-C) and stops a loop. Where a process cannot signal itself (Windows), it exits 130. A scan interrupted after it began writing marks its run failed, which no reader sees. |

Usage errors:

- missing paths, or an unreadable policy file;
- a policy file over 1 MiB, an empty one, or an implicit `./stillhere.toml` or `./.mailmap` that is a symbolic link, which a clone can supply (#71; a file `--policy` or `--mailmap` names may be one);
- a facts.db a read command (`report`, `explain`, `who-knows`, `me`, `identities`, `validate`) is pointed at that does not exist, which it never creates, or one, or its directory, that `scan` or `sync` cannot write, before any git work (#71); the message names the path;
- a `sync github --org` that is no GitHub login, or a `--repo` that is not `OWNER/NAME` with GitHub names, refused before the sync begins its run; `--org` and `--repo` together, or neither; a `--since` that is not in the past; a `--repo` GitHub has no repository for, or does not show the token, and an `--org` it does not know, which begin no run either and print no closing line; and a `--db`, `--mirrors` or `STILLHERE_HOME` that is a URL or holds a credential where a local path belongs (#71, #111);
- a user policy that lacks a required table: `headline`, `week`, `blame`, `bots`, `ai`, `roles`, `paths`, plus `hotspots` once M5 ships, and `gearing` only if open decision #2 is approved;
- `--ignore-revs-file` on a multi-repo run, or one that cannot be read;
- a malformed `--exclude-repo` glob, `--rank` on a metric that is never ranked, or a metric id the registry does not know;
- git older than the supported floor ([git-invocation.md](git-invocation.md#version-floors)).

There is one ordered classifier. The week collector and the blame collector both call it; there is no second, looser filter.

The scanned SHA is the commit the run reads: the repository as it stood at `--now`, the newest first-parent commit of the default branch committed before then ([run model](codebase.md#run-model)). Paths, sizes, attributes and headers are those of that commit, not of a newer head the clone has fetched.

## Order

1. **Denied path**, decided by the [deny list](#deny-list) and then [.gitattributes](#gitattributes): adds 0 to `lines_added`, is not blamed, and counts toward `skipped.denied_path`.
2. **Too big**, size greater than `[blame].max_bytes` (400000 in the packaged policy): same, counts toward `skipped.too_big`. Sizes come from `git ls-tree -r -l -z <sha>` for paths present at the scanned SHA. A path the history touched (week or scan) that is absent at that SHA is sized with one batched `git cat-file --batch-check='%(objecttype) %(objectsize)' -Z` over NUL-terminated `<commit>:<path>` lines (`-Z`, Git 2.42+, makes the output NUL-terminated too, which a path holding a newline needs), where the commit is the newest that added lines to the path; a path missing from that tree has an unknown size (`-1`) and skips this check. In a blobless partial clone `ls-tree -l` prints `BAD` for a missing blob's size (verified on 2.50.1), which is also unknown. No blame is spawned just to learn a size.
3. **Generated header**, from the [header sniff](#header-sniff): same, counts toward `skipped.generated_header`, unless `.gitattributes` turns `linguist-generated` off for the path ([.gitattributes](#gitattributes)). Only a path that step 4 would count can be generated: one a rule gives a role, or skips by a path rule's `max_bytes`. A path no rule gives a role is step 5's whatever its header says, so how many files the sniff reads decides what it costs, never a class.
4. **Role assigned**: the path survives. Any role counts toward week `lines_added`; only `prod` counts toward the still-here headline. Only a regular file gets a role. A [path rule](#roles) with `max_bytes` bounds the files it gives its role to: a file the rule admits whose known size is larger is skipped as `too_big` by that rule instead, as step 2 skips any file over `[blame].max_bytes` (the packaged policy's large test data).
5. **No role**: adds 0, is not blamed, and counts toward `skipped.unclassified`. That includes a symbolic link (mode `120000`), whose content is its target's name, and a submodule (a gitlink), which has no lines, although numstat counts a link's target and a submodule bump as a changed line (verified on 2.50.1). A path the scanned SHA no longer has is classified as a file: `cat-file --batch-check` has no `%(objectmode)` (verified on 2.50.1), so it cannot tell a deleted link from a file.

## Patterns

Every path pattern is a Go `regexp` (RE2), applied with `MatchString` to the full repo-relative path with forward slashes. RE2 has no lookaround and no backreferences, so Linguist's Ruby patterns are translated, not pasted. A pattern that `regexp.Compile` rejects fails the policy loader test.

Match path **segments**, not substrings. `(^|/)tests(/|$)` matches `tests/test_service.py`. A naive check that prepends a slash and searches for `/tests/` misses that path, because the characters `/tests/` never occur in it. `(^|/)test(/|$)` does not match `tests`. A multi-segment directory needs the whole sequence in one pattern, `(^|/)bootstrap/cache(/|$)`: comparing one path component to the string `bootstrap/cache` never matches `bootstrap/cache/config.php`.

## Deny list

Exactly one policy file governs a run: `--policy FILE`, else `./stillhere.toml`, else the packaged default. A `./stillhere.toml` that is a symbolic link is a usage error (exit 2) that says to pass it with `--policy`, since the working directory is often a clone's root and a clone can commit a link to `/dev/zero` or a FIFO there; a file `--policy` names may be a link. A policy file that is not a regular file, or is over 1 MiB, is a usage error too (#71). That file replaces the packaged file as a whole. There is no union and no deep merge. A missing required table, or a missing key in one, is a usage error (exit 2), never filled in from the package; the values these specs call defaults are the packaged file's.

- **Packaged default.** `[paths] package_file = "generated_paths.txt"`, with no `deny` key. That embedded text file is the whole deny list. Its header says each non-comment line is an RE2 pattern translated from GitHub Linguist's `vendor.yml` and generated-file rules (MIT, attributed), and records the upstream commit the curator actually read; no SHA is invented. The policy hash covers the TOML bytes, a length prefix, and this file, so editing a pattern changes the hash ([codebase.md](codebase.md#package-apis) gives the exact bytes).
- **What the packaged list holds.** The curator read Linguist at `73ee9a3b277f398c37ca4ab0dea0193849de6460` (main on 2026-10-14):
  - every `vendor.yml` pattern, copied unchanged: Linguist's own CI checks each one against Go's engine, and its allowlist of exceptions is empty;
  - the `generated.rb` rules that read only the path, with Ruby's delimiters removed and `/i` written `(?i)`; `go_vendor?` uses lookaround and is rewritten without it, as an equivalent DNS-label pattern;
  - none of the `generated.rb` rules that read file content, which the [header sniff](#header-sniff) covers in part;
  - six `vendor.yml` rules left out on purpose, commented in place with the reason. `(^|/)cache/` and `(^|/)env/` match directories that usually hold a team's own code, such as a Go `internal/cache` package. Linguist only drops such files from a language bar; stillhere would silently drop their authors' lines from every ownership and durability number. Laravel's generated `bootstrap/cache` and virtual environments (`venv`, `.venv`) are denied by the minimum contents below. A repository that keeps third-party code there marks it with `linguist-vendored`. Since [revision 3](#packaged-policy-revisions), `(^|/)\.github/`, `(^|/)Jenkinsfile$` and `(^|/)\.teamcity/` are left out too: continuous integration is the team's own infrastructure, which the `iac` role is for, as it is for a `Makefile` or a `Dockerfile`. Denied, who wrote and who knows the release and test automation could not be answered (round 2: 153 lines of one person's release workflow vanished from `landed@2` in django-rest-framework). Workflows and actions are `iac` by their extensions, code under `.github/` by a [path rule](#roles), and GitHub's contribution templates `doc`; the bundles an action commits (`dist/`, `node_modules/`) stay denied by their own rules. So is Fabric's `(^|/)fabfile\.py$`: a project's Fabric tasks deploy and release it, as a `Makefile`'s targets do, and a [path rule](#roles) gives `fabfile.py` the `iac` role (until revision 3's review the deny rule came first, so that path rule never matched);
- **Two segments of stillhere's own are left out for the same reason**, as the file's last section records; Linguist has neither. Across the 175,079 files with a role in 1,120 Go modules (a module cache, 2026-10-14), the files under either segment were the modules' own packages, scripts and test data, never vendored code or build output:
  - `(^|/)build(/|$)`: 221 files, such as Go's `go/build` package and Thrift's `build/docker` scripts. Build output is in every common `.gitignore` template, and a repository that commits it marks it `linguist-generated`.
  - `(^|/)storage(/|$)`: 1,083 files, such as go-git's `storage/` and Kubernetes' `storage/v1` API types. The rule was for Laravel, so the list denies Laravel's `storage/framework` (compiled Blade views, caches, sessions) and `storage/logs` instead.
- **User file.** `[paths] deny = [...]` is the whole list. Setting `package_file`, setting both keys, or setting neither exits 2, because a user file's hash would not cover a packaged text file. A user who wants the packaged patterns copies them into `deny`: `stillhere policy > stillhere.toml` writes the packaged policy out as such a file, every packaged pattern in `deny` in order, with Linguist's license notice (#71).
- **Minimum packaged contents:**
  - single directory segments, each written as `(^|/)<segment>/`: `node_modules`, `vendor`, `dist`, `coverage`, `\.next`, `out`, `third_party`, `__pycache__`, `\.venv`, `venv`;
  - Laravel's generated directories, as consecutive segments: `(^|/)bootstrap/cache/` and `(^|/)storage/(framework|logs)/`;
  - lock and sum files, including `go.sum`;
  - minified assets (`\.min\.js$`, and `.min.css`: Linguist's `(\.|-)min\.(js|css)$`);
  - generated suffixes (`\.pb\.go$`, `_pb2\.py$`);
  - mock and `gen/` directories;
  - generated PHP under protobuf output (`gpbmetadata`).

  A rule for a directory ends at the directory's slash, so it matches a directory only, never a file of that name: until [revision 3](#packaged-policy-revisions) each ended `(/|$)`, which also denied httpx's `scripts/coverage`, a shell script beside `scripts/test`, as coverage output. Lockfiles, vendor directories and generated suffixes live only here, never in a second hardcoded set. Protobuf `.proto` sources stay `prod`.

- **The deny list comes first.** Linguist's test-fixture rule, `(^|/)[Tt]ests?/fixtures/`, denies `tests/fixtures/x.py` before any role rule reads it, so the precedence among path roles below decides what `classify.Role` reports for such a path, not what a scan counts.

## .gitattributes

After the deny patterns, one batched call per repo, so git does the reading. Attribute macros and `info/attributes` are never reimplemented.

```
git <common> check-attr -z --source=<sha> --stdin linguist-generated linguist-vendored
```

Stdin is NUL-terminated paths: every path at the scanned SHA, plus each touched path that SHA no longer has, which is matched against the attributes at the scanned SHA too. The output is `path\0attribute\0info\0`, where info is `unspecified`, `unset`, `set`, or a value. An attribute is **on** when info is `set` or any value other than `false`, and **off** when info is `unset` or the value `false`. That is how GitHub Linguist reads a boolean attribute (`boolean_attribute` in `lib/linguist/lazy_blob.rb`), so `linguist-vendored=false`, a common way to un-vendor a path, means what it means on GitHub. An empty value (`linguist-generated=`) is on too: check-attr prints it as an empty info (verified on 2.50.1), while libgit2, which Linguist reads attributes with, leaves an assignment with an empty value set. Per path, in this order:

1. `denied` starts true if any deny pattern matched.
2. If either attribute is off, `denied` becomes false. An explicit `-linguist-generated` or `-linguist-vendored` (or `=false`) is the only un-deny.
3. If either attribute is on, `denied` becomes true. On wins over off on the other attribute.

`linguist-generated` turned off also skips the [header sniff](#header-sniff) step: in Linguist an explicit `linguist-generated` decides whether a file is generated, ahead of every content heuristic, and without it a team could never count a hand-maintained file whose header says `DO NOT EDIT`, because the marker list is source, not policy. `linguist-vendored` says nothing about generated code, so turning it off leaves the sniff in place.

`linguist-documentation` is not read. Linguist leaves documentation out of a repository's language bar, but stillhere does not drop documentation: a Markdown file has the `doc` role, which week `lines_added` counts and the still-here headline does not. Since [revision 3](#what-counts-as-product-code-revision-3) the packaged policy gives example code and the code under a top-level `docs/` the `doc` role with path rules, as Linguist's `documentation.yml` reads such paths; a team whose layout differs writes its own path rule. Reading the attribute as the `doc` role is a possible extension, for the owner to decide.

`--source=<sha>` (Git 2.40+) is required. Without it, a bare mirror reports `unspecified` for every attribute (verified), and a work-tree clone reads the checked-out files instead of the scanned SHA, which makes the result depend on whatever branch the user has checked out. `<common>` pins `core.ignoreCase=false`, which makes patterns match the same way on every machine (until #13 it was set on this command alone): a clone on macOS or Windows sets `core.ignorecase=true`, under which `*.PY linguist-generated` marks `a.py` (verified on 2.50.1), while a Linux clone, like GitHub's servers, matches case-sensitively. A repository's `attr.tree` does not change the answer, because `--source` takes precedence over it: verified on 2.50.1, and in git 2.45.0's source `check-attr --source` sets the same source as `git --attr-source`, which `attr.tree` fills only when nothing set it. `TestAttributes` sets `attr.tree`, so CI checks this on both git versions it runs. The runner points `core.attributesFile` at `/dev/null` and sets `GIT_ATTR_NOSYSTEM=1`, which drops only the per-user and system files; the repository's `.gitattributes` and `info/attributes` still apply ([git-invocation.md](git-invocation.md#analysis-commands-offline)). In a blobless partial clone the `.gitattributes` blob is absent and lazy fetch is off, so every attribute reads `unspecified` (verified); a partial clone has no line facts, so nothing depends on it.

## Header sniff

Once per repo, at the scanned SHA. This is cheaper than opening every file:

```
git <common> grep --no-color --no-column -n -o -z -a -i -E -m 1 -e '<gate>' \
  --and \( -e '<described>' -e '<do not modify>' -e '<declared>' \) <sha> -- \
  ':(icase)*<ext>' ... '<name>' '*/<name>' ...
```

A header marks a file generated in one of two ways. Both are matched case-insensitively, and each marker ends at a word boundary, so the identifier `AutogeneratedPos` is none:

- **A declaration**: `do not edit`, `@generated`, or `<auto-generated` (also `<autogenerated`, .NET's convention). It counts anywhere in a line's first 100 characters, unless a quote (`"`, `'`, a backtick) comes before it there, because then it sits in a string literal: a generator program that prints its output's header, such as `fmt.Fprintln(&b, "// Code generated by mkbuiltin.go. DO NOT EDIT.")`, is no generated file. `do not modify` is a declaration only as a line of its own (`// DO NOT MODIFY!`, `Do not modify this file by hand.`); in a sentence it is advice, as in `Do not modify a Record after handing out a copy to it` (Go's `log/slog`).
- **A description**: `code generated`, `generated by`, `auto-generated`, `autogenerated`, `auto generated`, `automatically generated` or `machine generated`, or a subject that says so: "this file (or code, class, header, module, program, source, document) is (or was, has been) generated", with optional words such as "entire", "(mostly)", "auto-" or "automatically", and "this is a generated". It counts only as the first words of a line's text: after at most 32 characters of indentation and comment punctuation, the characters of `//`, `#`, `/*`, `*`, `<!--`, `--`, `;` and Haskell's `{-` (`[[:space:]/#*;<!{-]{0,32}`), and optionally after a warning word such as `WARNING:`, `NOTE:` or `DO NOT MODIFY.`, whose colon or full stop is optional. A docstring line starts there too, and so do the template comments `{#` and `{{!`, which those characters spell. In mid-sentence the same words describe something else: `Random numbers are generated by a [Source]` in Go's `math/rand`. Any other punctuation is text, so a hand-written generator script whose template, in a string, writes an rST comment (`.. Note this file is autogenerated by ...`) keeps its role: until #70 the line start took any punctuation but a quote, which matched that line, while the two forms differed on one other file of 305,008 in a module cache, a false positive too (the review's measurement, 2026-10-15). That cache held Go modules only, so it could not show what the narrower start loses in the other languages the policy gives a role. `{-` was added after #70's review, because `.hs` is `prod` since #57 and proto-lens opens every module it generates with `{- This file was auto-generated from ... -}`, which #70's first narrowing missed. A description after any other comment punctuation is not seen: Haddock's `-- |` and `{-|`, Lua's `--[[`, rST's `..`, the `%` of MATLAB, ERB and EEx, and a batch file's `::` or `REM`. Such a generated file is skipped only through a declaration (`DO NOT EDIT`, `@generated`) or a `linguist-generated` attribute ([.gitattributes](#gitattributes)).
- **The gate** is `generated`, `do not edit` or `do not modify`, which every match of a rule contains. git tests the rules only on lines that match the gate (`--and`), so the sniff is faster than the plain marker list it replaced: 0.8 s on Go's source tree (8,393 files with a role, git 2.50.1 on macOS), against 1.8 s for the old list and 3.2 s for the rules without the gate. Gated and ungated runs gave the same paths and lines on Go's tree and the macOS SDK headers.

The rules were chosen on the files with a role that the packaged deny list keeps, in Go's source tree, Python's standard library, the macOS SDK headers and 1,120 Go modules (a module cache, 2026-10-14). git's ERE engine and Go's RE2 agreed on every file checked.

- No design missed any of the 21,220 files that follow Go's convention, `^// Code generated .* DO NOT EDIT\.$`.
- On Go's tree, the old list matched 67 other files, 60 of them hand-written (prose, identifiers, generator programs); these rules match 12, 7 of them generated (cgo's `defs_*.go`, an `instgen` table).
- The alternative, every marker at the start of a comment, misses a header that opens with a warning or a subject: 4,842 more files in the module cache, such as the 3,338 files of Pulumi's AWS SDK (`*** WARNING: this file was generated by`), 1,118 of the Azure SDK for Go (`This code was auto-generated by:`) and the 68 generated `.proto` files of Kubernetes, and 76 macOS SDK headers (Perl's `DO NOT EDIT THIS FILE`, autoconf's `This file is automatically generated by configure`).

- The sniff reads every file at the scanned SHA that the policy can give a role, so its reach and the role rules are one statement: the pathspecs are the policy's role extensions, matched at any depth and ignoring case as the classifier does, its exact role names at any depth, glob characters escaped, and `:(literal)<path>` for each regular file that only a path rule without `when` gives a role (`classify.RoleByRuleAlone`), such as the packaged requirements rule's `requirements.txt`. More than 256 such files are not named one by one, since git matches every path against every pathspec: then every file is read, which changes no class, because only a path a rule counts can be generated ([order](#order)). With no file that can get a role the sniff does not run. Until revision 3's review a file whose only role came from such a rule was never sniffed, so pip-compile's output, whose header says it is autogenerated, counted as `iac` (flask's `examples/celery/requirements.txt`).
- `-a` reads every file as text, so no attribute changes the sniff. `-I` would decide what is binary from the `diff` attribute, which git grep reads from the work tree, not from the scanned SHA, while a bare mirror reads none: a generated file marked `-diff` or `binary` was sniffed in a bare mirror but not in a work tree of the same SHA, and an uncommitted `.gitattributes` edit flipped the result (verified on 2.50.1). `git --attr-source=<sha>` (Git 2.41+) would make `-I` read the scanned SHA, but then a file marked `-diff`, often a generated one, would never be sniffed. The pathspecs keep binary files out in practice.
- `-m 1` (Git 2.38+) stops at a file's first matching line, the only one that can decide the line-40 rule, and `-o` prints only what matched, which the rules bound, so a minified file's megabyte-long line never reaches stillhere.
- Output records are `<sha>:<path>\0<line>\0<match>\n`, one for each match on the line, the gate's included (verified, also in bare mirrors); a path may hold a newline, so a record ends at the first newline after its second NUL. Strip the `<sha>:` prefix before using the path.
- `--no-column` is a call-site rule like `--no-color`: a repo-local `grep.column=true` adds a column field to the output (verified on 2.50.1).
- A path counts only when its matched line number is 40 or less.
- Exit status 1 means no hits, not a failed repo.
- The markers are source, not policy: the patterns are constants in `internal/collect`, and the blame cache keys on them.
- A path absent at the scanned SHA gets no header sniff, because the sniff reads that SHA. The deny list, attributes, size and roles still apply to it.

An extension or name gets the role of what its files are for, which is not always GitHub Linguist's type for its language: source code is `prod` (a component file too, as `.vue`, `.svelte` and `.astro` are, though Linguist types them markup); shell scripts and build and deployment definitions are `iac`, as `Makefile` and `Dockerfile` are, though Linguist types Shell, Batchfile, PowerShell, CMake and Nix programming; views and templates are `markup`, as HTML is. So one language's extensions can take different roles: Kotlin's `.kt` is `prod` and its `.kts` `iac` (below), and of the extensions Linguist gives XML, `.xml` is `iac` while Interface Builder's `.storyboard` and `.xib` are `markup`.

The list holds each language's common extensions, not every one Linguist knows (checked against `languages.yml` at `73ee9a3b277f`, the commit the deny list was curated from). An extension stays out when no one role fits most of its files: when common files of languages with different roles share it (`.inc`, which C++, PHP, HTML and SQL all use; `.cgi` and `.fcgi`, Perl's and Python's as much as Shell's; `.spec`, Python's, Ruby's and RPM's), or when a language keeps its tests in it (Perl's `.t`). One that languages of one role share is in (`.h`, `.hh`, `.m`, `.pl`, `.r`, `.s`), and so is one whose other claimants are rare beside its main language, as `.ts` is although Linguist's XML also lists it for Qt's translation files, and `.md` although GCC's machine descriptions use it. Less common extensions are out too, and their files get no role: among the languages listed, C++'s `.ino`, `.ipp`, `.inl`, `.tpp`, `.cppm` and `.ixx`, Haskell's `.hsc` and `.hs-boot`, Tcl's `.tm`, the Korn shell's `.ksh` and OpenTofu's `.tofu`, with a longer tail for JavaScript, Ruby and PHP ([#65](https://github.com/IHaveASegway/stillhere/issues/65), which weighs mapping roles from Linguist's data instead of a hand list).

Two cases decided by what their files are for rather than by their language, added by #57:

- **Kotlin script (`.kts`) is `iac`.** Its files are Gradle builds: of the 430 `.kts` files in seven Kotlin repositories (`square/okhttp`, a corpus repository of #16, and kotlinx.coroutines, nowinandroid, ktor, koin, detekt and leakcanary, at HEAD on 2026-10-14), 426 are `*.gradle.kts`, build scripts and convention plugins; the other four are a Spotless license header, a test resource and two `*.main.kts` automation scripts. Linguist names `.gradle.kts` a language of its own, Gradle Kotlin DSL, of type data. Gradle's Groovy scripts (`.gradle`, Linguist's Gradle, also data) had no role, so they take the same one: a build whose scripts move from Groovy to Kotlin keeps its classification.
- **EEx and ERB templates are `markup`.** Linguist types HTML+EEX (`.html.eex`, `.heex`, `.leex`) and HTML+ERB (`.erb`) markup, and a server-side view is what `.html` already is for Django, Jinja and Angular templates. ERB had no role before #57 either, so Rails views counted nowhere. A template that generates code, such as Phoenix's generators (`priv/templates/*.ex.eex`), is `markup` too.

Path roles override extension roles. The 2026-10-07 plan left the precedence among path roles implicit (for example `tests/fixtures/x.py`). The precedence is test, then migration, then seed, pinned by `TestClassify`; revision 3 slots its rules in as test (configuration and data under a test directory, bounded by size; test code; test names), doc (examples), the Go exception, test (benchmarks), doc (`docs/`, GitHub's templates), migration, seed, then iac (CI, build tooling, configuration as code, packaging, build scripts, requirements); revision 4 extends the two test-directory rules to Gradle's test source sets and slots in doc (a documentation site) after `docs/`, and iac (a workspace package's scripts, Gradle build logic, dot-directories) after the top-level build tooling, so `tests/examples/x.py` is `test`, `examples/app/migrations/0001.py` is `doc` and `examples/bench/x.rs` is `doc`. Path rules are tried in that order, and the first rule whose pattern matches **and** whose condition admits the extension or name role wins: `db/migrations/seeds/x.sql` (extension role `sql`) is `seed`, because the migration rule admits only `prod`. An exact name wins over the extension, and the extension is the file name's last dot suffix, lowercased, so a policy may list only extensions with one dot (`.gz`, never `.tar.gz`, which a path rule can match). A rule without a condition admits any path. A rule may also set `max_bytes`, optional as `when` is, so a policy file written before it still reads: a whole number of bytes, 1 or more (anything else exits 2, as a bad `when` does), which bounds the files the rule decides: one it admits whose known size is larger is `too_big` by that rule instead of getting its role, and one of unknown size gets the role. A rule's reason, which `stillhere paths` prints, is the first sentence of its comment ([which rule decided a path](#which-rule-decided-a-path-stillhere-paths)); the comment is optional and changes nothing a run counts, though the policy hash covers it. The test-segment rule has a condition: a file under a test directory is `test` when it is code or configuration, while data there gets no role (`tests/data.csv`, golden files, Jest's `__snapshots__/*.snap`, which Jest writes itself) and documentation stays `doc` (`tests/README.md`, and `docs/spec/`, a specification rather than an RSpec suite). Without it, every such file would count toward week `lines_added` as test code, and the header sniff would never read it. (Under the packaged deny list `tests/fixtures/` is denied anyway, by Linguist's test-fixture rule, so the precedence matters for what `classify.Role` reports.)

## What counts as product code (revision 3)

The headline, the made-of line, ownership, knowledge loss and concentration, `durable@1` and `simplifying@1` all read `prod` lines, so a path that is not the product but takes the `prod` role moves every one of them. Round 2 (five new-user personas on Python, TypeScript and Rust repositories and two organizations, 2026-10-15) found that on three of five codebases: in tokio-rs/axum, `examples/` and `benches/` were 16% of the 37,329 prod lines; in pallets/werkzeug, `examples/` and `docs/conf.py` were 12% of the prod lines and a third of the lines gone quiet, so knowledge loss read 19.4% where the library alone gives 14.6%; in honojs/hono, `benchmarks/`, `build/` and the `vite.config.ts` files were 8%. Revision 3 of the packaged policy draws the line by what a file is for, as the [roles](#roles) already do for extensions: example code documents the product, benchmarks measure it, and build, packaging and CI tooling builds and ships it; none of them is the product.

Prior art, checked at the Linguist commit the deny list was curated from (`73ee9a3b277f`): Linguist's `documentation.yml` counts `^[Ee]xamples/`, `^[Dd]ocs?/`, `^[Dd]emos?/` and `^[Ss]amples?/` as documentation, which revision 3 follows for examples at any depth (Cargo's workspace members and Go's `_examples/` keep them below the top) and for a top-level `docs/` but not `doc/`; its `vendor.yml` denies CI, which revision 3 leaves out ([deny list](#deny-list)); Cargo's own layout fixes `benches/` and `examples/` beside `src/`, and its build script is `build.rs` at a package's root; the Go project layout names `/build` for packaging and CI and `/scripts` for build and release scripts; pytest loads `conftest.py` and nothing else does.

Each rule was checked on two corpora before it shipped, as the deny list's exceptions were (`TestClassify` pins the cases):

- **53 repositories** (round 2's and the earlier dogfood's clones: httpx, hono, axum, the pallets and encode organizations, cli/cli and the rest of the cli organization, ripgrep, vite, fzf, cobra, go-git and go-billy, and go-chi's 21 repositories), classified at HEAD under revision 2 and revision 3. 457 of 3,454 prod files left `prod`, 25,912 of 491,561 non-blank lines (5.3%): 279 files to `doc`, 127 to `iac` and 51 to `test`, and no file entered `prod`. Every file that left was read by path, and each was an example, a benchmark, documentation tooling, a build or release script or a tool's configuration; the closest call is create-vite's template `vite.config.ts` files, a few lines each, which the tool copies into new projects.
- **1,130 Go modules** (a module cache, one version each, 86,324 prod files). 1,651 files left `prod`, 1,548 of them examples. The first draft took three Go packages from their authors: google.golang.org/api's `docs/v1` and `script/v1`, the Google Docs and Apps Script clients, and a library's `build` package for build information; nats.go's public `bench` package would have been fourth. In Go every directory is a package and its name is the import path's, so Go code keeps its role under a top-level `docs/`, `build/` or `script/` and under any `bench/` or `perf/`; Go keeps its benchmarks in `_test.go` files, `test` already. `perf/` is read at the top only, so a product such as Linux's `tools/perf` keeps its role, and `doc/` not at all, because cobra's `doc/` package writes man pages.

What the rules leave alone, as false negatives, rather than risk product code: vite's `playground/` (934 prod files, 11,687 lines), which is its end-to-end test suite but in other repositories a sandbox or a product; hono's `perf-measures/` and `runtime-tests/workerd/index.ts` (5 files, 133 lines), names no convention shares; cli/cli's `script/*.go` and other Go tooling under `script/`; a `setup.py` below the top, since a Python package can have a `setup` module of its own (Home Assistant's `homeassistant/setup.py`); a `testing/` directory that is a library's public test helpers (hono's `hono/testing`), which the test rule takes; and hand-written TypeScript declarations, which Linguist's `.d.ts` rule denies. A team whose layout differs writes a path rule in its `stillhere.toml`.

Large test data. JSON, YAML and XML under a test directory have the `test` role, as configuration there should; but test vectors and recorded responses are data a tool wrote or someone copied in, and one such file can dwarf the test code (httpx's `tests/models/whatwg.json`, WHATWG's URL-parsing cases, 9,746 non-blank lines, 58% of the repository's test lines and two thirds of one person's). The first `[[roles.path]]` rule decides every `iac` file under a test directory: `test` up to 100,000 bytes, and `too_big` above, by its `max_bytes`, so its reason, "Configuration and data under a test directory are test up to 100 KB", fits a 9-byte `tests/small.json` as well as `whatwg.json` (until revision 3's review it read "Large data under a test directory is test data", which `stillhere paths` printed beside small files too, and its comment said the next rule took them, which it never did, since the first rule that matches decides). Code there is not bounded: click's 134 KB `tests/test_options.py` is a test suite. CSV and text files under a test directory have no role already.

The four names the round-3 finding listed (`.changeset/`, `.husky/`, `.vscode/`, `.devcontainer/`) would have missed its own example, `.eslint/`; Linguist's deny list already denies `.vscode/`, `.idea/`, `.yarn/`'s releases and plugins, and `.mvn/wrapper/`.

## Rust inline tests

Rust keeps unit tests inside the source files they test, in a module gated by `#[cfg(test)]`, so a path-level role counts them as `prod`. On axum at HEAD (2026-10-16) 63 of its 112 prod files hold such items, 7,020 of 31,282 surviving prod lines (22.4%), and one person's ranked `durable@1` cluster was 64% test lines. Telling them apart line by line would give lines a role of their own and change the input of every metric that reads lines, so it is out of scope for revision 3; a scan says how much instead. After blame, `collect.InlineTests` finds the prod `.rs` files at HEAD that hold the attribute (one `git grep -l -E` for `#[cfg(test)]` or `#![cfg(test)]` with any spacing, `-a`, at the scanned commit, pathspec `:(icase)*.rs`) and reads those (one `git cat-file --batch`), and counts the non-blank lines from each attribute to the end of the item it gates: the brace that closes the item's block, or the semicolon that ends it (a `use`, a `mod tests;`), or for an inner `#![cfg(test)]` the end of the block it is in, the whole file at the top. The count skips comments (nested), strings, raw strings and character literals, so a brace or an attribute inside one counts for nothing; an attribute inside an item an earlier one gates is that item's. It is a count, not a parser: an attribute on a field or an argument runs to the end of the block around it, `#[cfg(any(test, ...))]` and a test module in a file of its own (`mod tests;`, whose file is a prod path) are not counted, and a macro that writes a test module is not seen. The repository gets an `inline-tests` warning, which its card and every section with its numbers carry as a caveat, with the files, the lines and their share of the surviving prod lines.

**Debt** ([#120](https://github.com/IHaveASegway/stillhere/issues/120)). Line-level roles: blame and the history's patches would classify a line by the item it is in, not only by its path, which changes every line metric's inputs (a new version of each, and the oracles with them). The caveat states the size of the error until then.

## Which rule decided a path: stillhere paths

`stillhere paths [PATH...]` lists every path a stored run classified, at HEAD or touched by its history, with its class and the rule that decided it: the step of the [order](#order), the rule as the policy writes it (a pattern, `.go`, `Dockerfile`, `max_bytes = 400000`), where the policy holds it (`generated_paths.txt line 478`, `[paths] deny pattern 3`, `[[roles.path]] rule 4`, `[roles.extensions] prod`, `[blame] max_bytes`) and where that lives (the packaged policy, the run's policy file by the name the scan recorded, a linguist attribute, a generated header, the file type), with the rule's own reason: the comment above its group in the deny list ("Minified JavaScript and CSS"; a group translated from Linguist's `generated.rb`, which the list heads with its Ruby method's name, reads "Linguist's generated.rb marks it generated (cargo_lock?)") or the first sentence of the comment in its `[[roles.path]]` table ("Example code documents the product; it is not the product"), else of the comment right above the table's header (its last paragraph, when it follows a comment about something else with only a `#` line between; a comment a blank line parts from the header is no rule's). What a path adds to its rule, its size under a size bound or the deny pattern `.gitattributes` overrode, is the row's `detail`, never the rule's reason, so a legend that lists each rule once with how many paths it decided prints a reason true of all of them. `--role` and `--skipped` filter, PATH prefixes keep what is under them, and a PATH no repository holds carries a `no-values` caveat that says how the run writes paths (relative to a repository's root), as who-knows does. The heading names the packaged policy's revision beside its hash. A card's "skipped paths" line points to it, by run (`--run N`, so the hint still lists the card's paths after a newer scan) and, in a run of several repositories, by `--repo KEY`, and says how many of the paths it counts only the history touched.

The rule is not stored: `classify.Explain` finds it again from the run's own policy, which the run keeps, and the stored class, with the functions `Classify` decides with (`Paths.Denying` for the deny list, one role search for both), so every stored run is explained, whenever it was scanned, and the reason a reader sees cannot drift from the decision. What the class does not record is told apart by what it says: a denied path no pattern matches was denied by an attribute; a path with a role that a pattern matches was un-denied by one; a skipped path with no role that a rule would give one is a link or a submodule; one at HEAD with no size and no rule is a submodule (git prints no size for a gitlink), or, in a blobless partial clone, where git reads no size, a file no rule gives a role, which the answer says. A link no rule gives a role reads as a file with no rule, whose answer says a role would make it count unless it is a link. Which of the two linguist attributes did it is not stored, so the answer names both. A class this classifier would not give under the run's policy, as a stillhere older than a change to the classifier may have stored, is `unknown`, and a new scan names its rule.

## Packaged policy revisions

A change to the packaged policy is a configured input, not a metric definition ([metrics.md](../metrics.md)): no metric version changes, and every run records the policy's hash, so two runs that differ only in their policy say so. The schema `version` stays 1 while the file's shape does: a policy file written for an older stillhere still reads, and a stored run's policy rebuilds from its own source. The design asked for a version bump on every packaged policy change; the revision is that version, kept out of the file's schema: `internal/policy/revisions.go` maps every hash the packaged files have had to its revision (`policy.PackagedRevision`), reports print it beside the hash (`policy v1 86bd8e7f838d (packaged revision 4)`, JSON `policy.revision` and each answer's `provenance.policy_revision`, 0 for a policy file), `stillhere policy` names it in the file it writes, and `TestPolicy` fails until a change to `default.toml` or `generated_paths.txt` lists its new hash, under a new revision when a rule changes and under the current one when only a comment does. A key in the file was weighed and left out: a `revision = 3` would travel into every `stillhere.toml` that `stillhere policy` starts and stay there after the user's edits, claiming a revision the file no longer is, and nothing would check that the number moved with the rules; a table keyed by hash names runs an older stillhere scanned too, with no migration. ## Weights and gearing: cut (open decision #2)

Status: **cut** on 2026-10-15 by the owner ([../product.md](../product.md#decided), [#21](https://github.com/IHaveASegway/stillhere/issues/21)): nothing below is built, and no policy table or report field holds it. The candidate design is kept for the record, since gearing could come back as a metric of its own over facts every run stores. It would never have entered a headline, a sort key, or a rank.

- **Role weights:** prod 1.0, sql 0.7, markup 0.4 (`.storyboard` and `.xib` 0.2, as UI-definition XML), iac 0.35, doc 0.0, test 0.35, migration 0.5, seed 0.25. No per-repo tiers: no "ops repo" IaC at 1.0, and no hand-listed toy or legacy repos.

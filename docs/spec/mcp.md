# MCP server

Status: v1 · 2026-10-14 · the tool contract of `stillhere mcp` (#15, [ADR 0006](../adr/0006-ai-mcp-and-narrated-highlights.md)) · server in `internal/mcp`, use cases in `internal/app/mcp.go`, the agent's guide in [plugins/stillhere/skills/stillhere/SKILL.md](../../plugins/stillhere/skills/stillhere/SKILL.md)

`stillhere mcp` is the interface an agent calls for deep detail on a platform (a group of repositories) or one repository: what landed, what lasted, who knows the code, each answer with its provenance and the caveats that could make it wrong. It answers from the same use cases and report types as the command line, so its numbers are the report's numbers. No tool computes a metric.

## The server

```
stillhere [--db FILE] [--mailmap FILE] [--log-level L] mcp [--run ID] [--me EMAIL] [--allow-emails] [--allow-source]
```

| Flag | Effect |
| --- | --- |
| `--run ID` | Every answer reads that run. Without it, each call reads the latest complete or partial scan, so a scan published during a session is seen at the next call, and the first answer that reads it carries a `run-changed` caveat. A run facts.db does not hold (never published, or deleted by retention) is an error on every call that names the latest scan and says how the user restarts the server. |
| `--me EMAIL` | The user's canonical email, after `.mailmap`. Only `person` about that email (an empty `name`) shows the person's own AI-assisted share, through `app.Me`; nobody else's answer ever does ([ADR 0007](../adr/0007-ai-assisted-attribution.md)). `changes` tags AI-assisted commits on the user's own entries only. When no one in the run has the email (another address of the user's, which the mailmap folded), `person` with an empty name says so, and every `person` answer carries a `me-not-in-run` caveat. |
| `--allow-emails` | Answers carry emails. Without it every email is replaced by a stable id. With it, `identity_candidates` also carries each candidate's `.mailmap` lines, which hold, beside the candidates' canonical emails, the emails a `.mailmap` already rewrote (#53): lines a suggestion must follow, since git never chains two. No other field of any answer holds such an email. |
| `--allow-source` | Answers carry commit subjects, and `diff` serves diffs, which needs git: `--mailmap` applies. Without it `diff` refuses and says how to allow it. |

- **Transport.** Local stdio on the official SDK (`github.com/modelcontextprotocol/go-sdk` v1.8.0), newline-delimited JSON-RPC. Only protocol messages go to stdout; the log goes to stderr. The server ends when the client closes stdin, or on a signal. When stdin closes, every call read before it is answered first, then the server ends (#58): a client that pipes its requests (`printf '…' | stillhere mcp`) gets every answer, where the SDK alone ends at once and cancels the calls in flight, as an HTTP server's graceful shutdown finishes the requests it accepted. A call the client cancelled is not waited for. A line from the client that is not a JSON-RPC message is answered with JSON-RPC's own error for it, a parse error (`-32700`) or an invalid request (`-32600`) with a `null` id, logged at warn and skipped: the session goes on, as JSON-RPC 2.0 asks, where the SDK's reader alone would end it. A message with an id but no method, result or error is such a line too (MC-10), which the SDK would take for an answer to a call it never made and drop without a word.
- **The store cannot write.** facts.db is opened with `sqlite.OpenReadOnly` (SQLite's `mode=ro`): nothing is created, migrated or cleaned up, and every write fails inside SQLite. It is opened on the first call that needs it and again after a failure, so a server started before the first scan answers each call with what to run (`stillhere scan PATH...`) until there is one. `metrics` reads no store.
- **One call at a time.** Calls are served in turn, and a published run's facts are read once and kept (a run never changes once published), so an agent's tenth question about a run does not read facts.db again. A call waits for the one before it unless its client cancels it first, and each git command of `diff` has 30 seconds, so no call holds the others for long.
- **Git, for diffs only.** With `--allow-source` the server holds a git runner on the analysis profile: offline, hardened, external diff and textconv off ([git-invocation.md](git-invocation.md)). Without it the server holds none.

Claude Code, with the binary's absolute path, since Claude Code starts the server with its own `PATH` (`command -v stillhere` must print one):

```sh
claude mcp add --scope user stillhere -- "$(command -v stillhere)" mcp --me you@example.com
```

## Every answer

An answer is one text content holding one compact JSON object, in the rules of [report-json.md](report-json.md#rules-that-carry-forward-whatever-the-format): fields in a fixed order, empty lists `[]`, an absent section `null`, invalid UTF-8 as U+FFFD, a number that is not finite as `null`. The object opens with `provenance` and closes with `page` (paged answers only), `caveats` and `withheld`.

| Field | What it holds |
| --- | --- |
| `provenance` | `run_id`, `as_of`, `policy` (sha256), `heads[]` of `{repo, key, branch, sha}`, `metrics[]` (the metric@version of every number in the answer), `heads_total` and `heads_sha256`. `heads` lists every repository the answer covers when it covers 10 or fewer, and in a detailed answer while it fits the budget; otherwise the repositories the answer names (its page, the repositories of its values, changes and picks). `heads_total` counts every repository the answer covers, and `heads_sha256` is the SHA-256 of all their heads as `repo key branch sha` lines, so two answers can be checked against one HEAD set. `forge` dates the GitHub data the run read for those repositories, as in [report-json.md](report-json.md); when `heads` is cut, `forge.repos` is cut with it to the repositories still listed, `forge_repos_total` counts them all (it is absent when nothing was cut), and `forge.as_of` stays the oldest sync over all of them. `metrics` answers with `{source: "registry", version, metrics}` instead: definitions are code. |
| `page` | `{offset, limit, total, next_cursor}`: pass `next_cursor` as `cursor` for the next page; `null` on the last. A cursor names its run, and one from another run is refused. |
| `caveats` | `[{code, message, repos}]`: the report's codes ([report-json.md](report-json.md#caveats)) and the ones below. A caveat goes where the number it qualifies is: every answer that shows a ranked metric's values, ranks or clusters (a rank table, `person`, `explain`, `changes`, `highlights`) carries that metric's `validity` note, and one that shows an AI-assisted share carries `ai-lower-bound`. |
| `withheld` | What this server keeps from the agent: `emails`, `source`. |

**No list grows with the platform.** An answer's main list is paged; every other list in it (a table's rows, a person's repositories, values and ranks, a change's people, the top tiers, the run's warnings) holds its first rows with its count in a `*_total` field beside it. Ordered lists keep their order; lists of values and ranks keep the largest: the scopes whose denominators, then numerators, are largest, and the rank tables with the most eligible people.

**Names, not ids.** People are named by their display name as the reports print it. The field that would hold a person's canonical email (`email`, a person subject's `key`) holds it with `--allow-emails`, and otherwise the person's id: `p-` and the first 10 hex digits of the SHA-256 of the canonical email. The id is stable across answers, sessions and runs, so an agent can join two answers on it and pass it back to `person`. It is a pseudonym, not an anonymisation: anyone who already holds an email can compute its id. An email a `.mailmap` folded into another (an old or a personal address, #53) is no person's key, so no answer gives it an id: it is only in `identity_candidates`' `mailmap` lines, which carry it with `--allow-emails` because a suggested line must name it, and are `null` without. A reviewer the forge could not link to an email is keyed `@login`, the login lowercased, as GitHub compares logins (`identity.LoginKey`, `identity.Directory.Reviewer`), and named as GitHub last showed it (`@Zoe`); an address with an empty local part (`@example.com`) is no login, and gets an id like any other. A person the reports show without a name, because git recorded none or because it gives an address away ([report-json.md](report-json.md#rules-that-carry-forward-whatever-the-format), "Where emails go"), has `name` `""`, and the server's own sentences, and the fields that say whom an answer is about, name them by id.

**Emails are withheld at the egress.** Without `--allow-emails`, every string of every answer and every error message, object names included, passes a filter after the answer is encoded, so a field added later, a warning that quotes an author or an error that names a person cannot carry an email out. The filter has three layers, from the most certain to the least, as data-loss-prevention tools pair transformations by field with detectors over free text (Google Cloud's Sensitive Data Protection; Microsoft's Presidio). Finding an address is one rule, `internal/redact`'s (`redact.Addresses`, `redact.Place`), which the command line's pages apply too ([report-json.md](report-json.md), "Where emails go"); only what replaces an address differs, an id here and a fixed label there:

1. **Where an email is.** A person's canonical email sits only in a member named `email`, or in the `key` of an object whose `kind` is `person` ([report-json.md](report-json.md), and #26's identities). Such a value becomes the id whatever it looks like: a dotless domain (`root@localhost`), an IP literal (`ip@[10.0.0.1]`), a Unicode or quoted local part, an empty one (`@example.com`). Only a login (`@name`, `@name[bot]`) and an id stay as they are.
2. **The run's vocabulary.** Every email of the run's people (`app.Names`) is replaced, as a whole address, wherever it appears: in a caveat or a warning, a commit subject, a patch or a path. An address with an empty local part is replaced only where no local-part character comes before its `@`, so it is never the end of another address.
3. **How an email looks.** In text that is not a path (`path`, `old_path`), what still looks like an address is replaced too: a local part of letters and digits in any script and RFC 5322's atext, and a domain of dotted labels that ends in letters (a top-level domain), or an IP literal. So a version pin (`lodash@4.17.21`, `actions/setup-go@v5.0.1`) or a metric id (`durable@1`) stays as it is, and so does the `user@host:path` of an scp-like remote (`git@github.com:o/r.git`, a repository key): a colon then a path, not a colon then a space or the end. A dotless address the run does not know is left to the first two layers, since `pkg@latest` is far more common in source than a person's address on a host name.

The log at info level never carries an email either way.

**The AI-assisted share of few people stays local.** A share over the landings of one or two people is close to one person's own share, which [ADR 0007](../adr/0007-ai-assisted-attribution.md) shows only to that person, and shares add up over the scopes (a group's landings are its repositories', the whole run's every repository's), so a share withheld on its own could be worked out from those shown around it: a group's less its shown repositories'. One decision per run (`app.AIShares`, [ADR 0007's amendment](../adr/0007-ai-assisted-attribution.md#amendment-the-shares-that-leave-the-machine)) says which shares leave, and every answer reads it, so no two answers about a run from one version of stillhere disagree and none can be subtracted from another (answers about two runs can be, and so can answers about one run from two versions that decide it differently: see [Not yet](#not-yet)):

- A scope's share (the whole run's, a group's or a repository's) is withheld when fewer than three people are credited with a non-merge commit of a landing in its window (365 days). Addresses of one block count as one person (`identity.Blocks`, [identities.md](identities.md#counting-people-for-a-floor)): those `identity_candidates` links at any confidence, those of every hand-off chain however long, and every two that share a name (any name seen with either, as author or co-author, a default one such as John Doe included), a local part or a GitHub account, without the vetoes its rules apply. An empty author address may be any of the other people, so beside them it adds no one; alone it is one person, unless the run takes it for a bot's (#74). So the count errs low: one person who committed from a work address, a laptop's made-up one and GitHub's noreply one, which no `.mailmap` merges, is one person, not three, whenever the three share a name or a local part, even under names spelt differently. Addresses with nothing in common still count apart ([ADR 0007](../adr/0007-ai-assisted-attribution.md#amendment-the-shares-that-leave-the-machine), known limits).
- Bottom-up over the run, its groups and their repositories, when the withheld children of a scope leave a part of it that covers one or two people, more children are withheld, the smallest first, until the part covers three or more; when no child can, the scope's own share is withheld. A shown share less the shown shares below it then covers no one or at least three people, at every level and across levels.
- The whole run's share is decided on only where an answer shows it: in the overview of every repository, which a run scanned with `--scope all`, or without groups, has.

`overview` sets a withheld share to `null`, its `num` and `den` with it, and says so (`ai-few-people`); `explain` refuses it, and no answer's `values` hold it, nor the copy surviving@1's population makeup carries in its `detail` about a repository or a group (`ai_assisted_share`), which leaves only with the share it copies: `report.AIShareIn` names every place a value holds a share. Neither the caveat nor the refusal points at another share. A shown share leaves as its `value`, `num` and `den` alone, its `detail` empty, and an `ai-detail-withheld` caveat says so (#87). That detail is `ai_assisted@1`'s cohort comparisons, `durable_ai` and `durable_other` with their cluster counts `durable_ai_n` and `durable_other_n`, and `reverted_ai` and `reverted_other`, which count narrower populations than the share (changes 90 to 365 days old, reverted landings) that can be one or two people's however many the share covers, and which add up over the scopes as the share does. The rule keeps none of the detail rather than delete the keys known today, so a key a later version adds stays on the machine too (fail closed). The local report keeps showing every share; the comparisons are stored with the run, and no page prints them yet. The egress is stricter than the terminal, as it is for emails.

**Repository text is untrusted.** Names, paths, commit subjects, warnings and patches come from the repositories and can carry prompt injection. Every tool description, the server's instructions and the skill say so, and the server's own sentences quote every name they hold (`"Lena Lead" (id p-…)`), so injected text reads as data rather than as the server's prose; the server does not try to recognise an injection.

**Size.** An answer stays under 40,000 characters (about 10,000 tokens at 4 characters a token): under Claude Code's warning at 10,000 tokens, under the 50,000 characters past which Claude Code saves a result to a file, and well under its 25,000-token cap (`MAX_MCP_OUTPUT_TOKENS`). An answer over it is rendered again, cut a step at a time, the least useful part first: the HEADs of repositories it does not name, then a diff's patch, then half the page, then half the rows of each list. It fails only when one item is still too large, and the error names the arguments of that tool that narrow it.

**`response_format`.** `concise` (the default) carries the numbers needed to answer: lists of repositories as one-line summaries, short SHAs (12 hex digits, which every tool that takes a change accepts), each list cut to 10 rows (5 for who-knows) with its `*_total`. `detailed` carries every field, for follow-up work: whole repository parts, per-section provenance and caveats, full SHAs, 50 rows (25 for who-knows).

**Errors** are tool results with `isError`, so the model sees them, and each says what to pass or run instead: the run's scopes for an unknown scope, and the stored run that holds it when another does; the candidates with their ids for an ambiguous name, a suggestion for a misspelt one, `stillhere scan` for an empty database, how the user restarts the server for a flag set wrong. An argument the tool's input schema refuses is one too (MC-9): a receiving middleware checks the arguments against the schema the tool publishes before the SDK does, and names the argument and what it takes ("overview: limit is a whole number from 1 to 100, not 1000; pass limit: 100, the most a page holds, and follow page.next_cursor for the rest"), where the SDK's validator says only what failed. The SDK's check stays behind it, and a schema keyword the middleware does not enforce fails when the server is built, as does a schema that is not an object with `additionalProperties` false (the middleware refuses every argument a schema does not name), so the two cannot drift apart. What an error or a caveat points the agent to is a tool of this server, called as the skill writes calls (`metrics()`, `identity_candidates(scope)`, `overview(scope, rank: M)`, `explain(metric: M, subject_kind: K)`, `who_knows(path, repo)`), never a command it cannot run; only what the user alone can do (scan, sync, restart the server) names a command. The use cases and the report word every such hint through the reader's vocabulary (`report.Commands`), which this server passes as `app.Deps.Commands` and the command line leaves at its own: one mechanism, not a rewrite of finished sentences.

## Resolving names

| Argument | Accepts |
| --- | --- |
| a person (`person.name`, `changes.person`, `explain.subject`) | a display name as the reports print it, without case; the start of each word when that matches one person only (`lena`), with a `name-match` caveat; an id `p-…`; an email; a GitHub login `@name`, without case: a reviewer the run keys by login, or the person the run links the login to (a commit GitHub attributes to it is theirs in the run: `app.NamedPerson.Logins`, the links every metric that reads reviews counts by). Two matches are an error listing both, with their ids, the logins the run links to them (unless a login is a local part of an address of the run, which would give it away: `identity.Directory.LoginWithheld`), surviving lines and repositories. A name the reports withhold, because it gives an address away, matches no one and is suggested for no misspelling, and every miss says so, so a miss confirms nothing: such a person is passed by id or email. An empty name is `--me`'s person, `changes.person` included (MC-5); `changes` without `person` lists everyone's. The rule is `app.FindPerson`, which the command line's `explain --person` and `me --email` resolve by too (PF-7), so a person named one way here is the same person there. |
| a scope (`overview.scope`, `changes.scope`, `highlights.scope`, `identity_candidates.scope`) | empty for the whole run; a group name; a repository name or key (a remote pasted with its credentials finds its scrubbed key); `group:NAME`, `repo:NAME` or `GROUP/NAME` to say which. Names compare without case, and one spelt exactly as asked wins over another that differs only in case. `overview`'s rows give each scope's `scope_arg`, the exact string that names it alone (MC-4): a group as `group:NAME`, a repository by its name unless a group or another repository shares it, then `repo:NAME`, `GROUP/NAME` or its key, the first that names it alone; an organization whose main repository shares its name (`go-git/go-git`) has both a group and a repository named `go-git`. A name the run does not hold, but another stored run does, is refused with that run, as of when, and how the user serves it (`--run N`, MC-17), since without `--run` one quick scan of a single repository becomes the latest run and hides a platform scanned before it. Where that run holds several scopes of the name (`go-git` there is a group and a repository), the refusal lists each with the `scope_arg` that names it in that run, since the served run's index cannot give it. |
| a repository (`who_knows.repo`, `diff.repo`, `explain.subject` for `repo` and `area`) | a repository name or key, `repo:NAME` or `GROUP/NAME`, so a repository's `scope_arg` works; found as a scope is, among repositories only; a miss names the stored run that holds it, as for a scope. |
| a group (`explain.subject` for `group`) | a group name, or its `scope_arg` as `overview` gives it (`group:NAME`). |
| a path (`who_knows.path`) | repo-relative, any prefix down to one file; or absolute inside a clone the run read, which names the repository too. A path is the repository's, as answers give it (`src/pins/lodash@4.17.21/index.py`): pass it back as it is. |

## Tools

All tools are read-only, idempotent and closed-world (`readOnlyHint`, `idempotentHint`, `openWorldHint: false`). Every tool that pages takes `response_format`, `limit` (1 to 100) and `cursor`.

| Tool | Arguments | Answers | From |
| --- | --- | --- | --- |
| `overview` | `scope`, `rank` | A platform, a repository or the whole run: `run`, `overviews[]` (scope, `scope_arg`, totals, `people` and `week` tables, the latter `landed@2`'s `total` (the scope's landings, commits, merges and lines, each landing once) and rows with `landings`, `commits`, `merged` and the lines (report-json.md), `null` when the scope's history does not cover the window (a shallow clone's boundary inside it), never an empty table, concentration, knowledge loss, AI-assisted and bot shares, `review_coverage`), `repos[]` (paged; each with its `scope_arg`; concise: one row each with size, people, top authors, concentration, shares, `review_coverage`, landings and caveat codes; detailed, and always for one repository: the report's whole repository part, card, still-here and week tables), for one repository `areas[]` with `areas_total` (#106: its top-level directories with their stored `knowledge_loss@1`, people and people gone quiet, `knowledge_concentration@1` and prod files, `lines` the surviving prod lines people hold there, largest first, `report.Areas`; `[]` of 0 when no top-level directory holds a line people hold, and both `null` for a repository without line facts, a shallow or partial clone, whose areas are unknown rather than none), `ranks[]` only when `rank` names a ranked metric, and the run's `warnings` with `warnings_total`. The whole run's answer is an index: one paged list of its groups, then its repositories, the groups in `overviews` (concise: their tables `null`, which `overview(scope=GROUP)` has) and the repositories in `repos`, with the rank tables of the page's groups; an overview of every repository (a run scanned with `--scope all`, or without groups) is on every page. | `app.Overview` over `app.Report` |

A tier stands apart when someone is outside it and the best place anyone outside can take lies below the worst place any of the tier reaches; it is named in a table of any size (MC-16: one person at 1–1 against another at 2–2), and a tier of everyone never stands apart; `lasted[]`: durable@1's cohort clusters that kept the most lines (the cohort window, whatever the period); `removed[]`: the period's simplifying@1 clusters that removed the most prod lines and were not reverted. Concise: each candidate's confidence, rules, suggested name and addresses (each with its commits, first and last activity and the first 3 of its repositories with `repos_total`); detailed adds each rule's evidence (`links`, hand-offs with their files) and 10 repositories per address. A scope lists the run's candidates with an address in it, each with all its addresses: every one that the scope's `unmerged-identities` caveat counts (those holding lines there, the cross-repository ones included), and those whose addresses there hold no surviving line (go-chi's `chi`: 21, of which its card counts 18). With `--allow-emails` each candidate also carries `mailmap`, its suggested `.mailmap` lines exactly as `stillhere identities --format mailmap` writes them (`report.MailmapLines`: each commented out unless high-confidence evidence backs it), the emails a `.mailmap` already rewrote among them (#53). Without it the emails in the answer are ids and `mailmap` is `null`, since the lines are made of emails: the user prints them locally with that command. Each address's `aliases` counts the emails git's mailmap already rewrote to it, and names none: such an email, often a personal or an old-name address a `.mailmap` folded away, is in no field but the lines, so it never reaches an agent as an id it could take for a person's. A link of the `same-forge-account` rule (#103) is high evidence, GitHub's own attribution, but a candidate is high only when every pair of its addresses is (its confidence is the weakest pair's); a weaker candidate's addresses marked `high` are those whose every pair is, and their lines are written as lines. | `app.Identities` with `Mailmap` set to `--allow-emails` |
| `metrics` | `metric` | The registry: concise `{id, question, ranked, ratio}` (`ratio` only when true); detailed, or `metric` for one, every field of the definition. | `app.Metrics` |
| `diff` | `change`, `repo`, `path`, `max_chars` (1,000 to 24,000) | Only with `--allow-source`. One landing against its first parent (a root commit as all added): `files[]` with numstat, the run's class of each path (a role, or why it adds nothing) and `in_patch`, with `files_total`; `patch`, the unified diff of the files with a role, cut at `max_chars` bytes on a line, and cut further, on a line, when its JSON escapes would put the answer over the budget; `truncated`. `change` is a landing SHA or its first 7 or more hex digits; one that is another repository's than `repo` names whose it is (MC-15). It refuses, saying why and what the user can do, the landing where a shallow clone's history ends, whose diff against nothing would be its whole tree, not its change (RB-5: in a shallow clone a parentless commit is the boundary, as the history collector reads it), and a landing whose contents a partial clone lacks, since analysis never fetches (RB-8: only when git says so, `collect.LacksObjects`; any other failure, such as a clone moved since its scan, gets the general error). The partial clone's refusal says what fills it: a clone without `--filter`, or in place `git config --unset remote.origin.partialclonefilter`, `git fetch --refetch origin` and `git config --unset remote.origin.promisor`, since a refetch alone applies the clone's filter again and leaves it a promisor, which discovery reads as partial. Without `--allow-emails` an address in the patch becomes an id, as in every string, and a `patch-emails` caveat counts them (MC-18). | `app.Diff`, git `diff-tree` |

## Choices and their reasons

- **Nine tools around questions, not tables** ([ADR 0006](../adr/0006-ai-mcp-and-narrated-highlights.md); Anthropic, "Writing effective tools for agents", 2025). A tool per table would make an agent stitch rows and ids together over many calls.
- **JSON, compact.** The report types are JSON already, which keeps one published shape; Anthropic's guidance finds no format best for every agent, and JSON lets an agent quote numbers exactly. Indentation would cost tokens and tell the model nothing.
- **Text content only**, no `structuredContent` with an output schema: the model reads the text, and a second copy of every answer would double its tokens.
- **The latest run per call**, not pinned at start: a long session sees the next scan, and `run-changed` says when two answers read different runs. `--run` pins a session.
- **No schema defaults.** SDK v1.8.0 applies a schema's `default` to `arguments: null` by writing into a nil map, which panics and ends the process; the defaults are in the handlers and the descriptions instead.
- **Emails by structure first, by shape last.** A pattern alone either misses addresses (a dotless domain, an IP literal, a Unicode local part) or rewrites what is not one (a version pin in a path, which the agent then cannot pass back). Where a person's email sits is part of the published shape, and the run knows every address it holds, so those two layers are exact; the pattern is left only for addresses no one in the run has, and kept off paths.
- **Bounded lists, with their totals.** A provenance that listed every HEAD, or an index with every group, made the entry tools fail on an organisation of a few hundred repositories; cutting a list keeps the answer and its count says what was left out. The HEAD digest keeps a cut provenance checkable.
- **A tolerant reader on stdin** (Postel's robustness principle, RFC 1122 §1.2.2): one stray line costs one error reply, not the session.
- **The detail of a shown AI-assisted share stays local, fail closed** (#87). Deleting the cohort keys known today would send any key a later version of `ai_assisted` adds, with every test green; sending no detail of a share at all is an allow list of nothing, which a new key cannot slip past. Counting the people behind each comparison and deciding them with the share's secondary rule would keep more for the agent, at the cost of a second suppression over the same tree.
- **A scope another run holds is named, not served** (MC-17). The server could answer from whichever stored run holds the scope asked about, but then one session would read several runs side by side without the user choosing it, and answers about two runs can be subtracted ([ADR 0007's amendment](../adr/0007-ai-assisted-attribution.md#amendment-the-shares-that-leave-the-machine), known limits: two runs). So a miss names the newest run that holds the scope and how the user serves it (`--run N`), from `FactStore.Runs`, which reads a few rows per stored run and no facts.
- **AI-assisted shares by one decision per run, with secondary suppression** ([ADR 0007's amendment](../adr/0007-ai-assisted-attribution.md#amendment-the-shares-that-leave-the-machine); Hundepool et al., *Statistical Disclosure Control*, Wiley 2012, ch. 4). A threshold checked one scope at a time leaks by subtraction, and a decision made per answer lets two answers disagree; withholding the parent of every small scope would cost most groups' shares. Withholding the smallest scope that closes the gap keeps the most shares that cannot give a small one away. People are counted by block (`identity.Blocks`): what `identity_candidates` links, every hand-off chain, and every two addresses that share any name seen with them, a local part or a GitHub account. The candidates' rules lean to precision, since a wrong merge invents a person; a floor needs recall, since a missed link lets one person's share out, while a wrong one only lowers a count and so never lets out a share of fewer than three people; only a missed link can, between addresses with nothing in common (record linkage's blocking step, Christen, *Data Matching*, Springer 2012, ch. 4). Counting addresses would make one person with three unmerged addresses three people.

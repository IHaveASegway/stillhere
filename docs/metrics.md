# Metric catalog

Status: draft v2 · 2026-10-14 · the published language people and agents bind to

Every metric has an id and a version, such as `durable@1`. A change to its definition, or to the facts or the defaults it reads, that can change any value is a new metric version. A change to a configured input, the policy a run reads (the packaged one included: its bots, roles and AI co-author addresses), is not: it bumps that policy section's version where it has one (`[ai] version`) and always changes the policy hash every run records, so two runs that differ only in their policy say so ([run model](spec/codebase.md#run-model)). The old metric version stays computable until a release removes it with a changelog entry. Reports, web pages and MCP answers cite the version they used.

Each entry states: the question, the unit, the definition, eligibility, uncertainty, blind spots, how it can be gamed, its fixture oracle, and its validity status. A metric without all of these does not ship.

## Units

- **Commit**: one git commit, with its author identified by the mailmapped email.
- **Landing**: a first-parent commit on the default branch. A merge landing `M` owns the commits in `git rev-list M^1..M`: the merge itself plus everything it brought in, which also covers octopus merges. A squash or rebase landing owns itself. See [spec/week-collector.md](spec/week-collector.md#landing--commit-map).
- **Change**: a landing in M1. From M2, a pull request when GitHub knows one (its landings grouped together). Moving to pull-request grouping is a version bump for any metric whose values move. The validity check already uses this grain (`metrics.Changes`, #77): a label names a landing or a pull request, and each ranked metric scores the change by what it adds to the metric's clusters ([validity checks](#validity-checks)), so no metric's values move. One grouping in the code makes the changes (`reviewsIndex.changes`), which `review_coverage@1` counts too: a merged pull request with the landings that put it on the default branch, a landing no pull request landed, and (wave 10) a pull request merged into another branch, a maintenance or release branch, whose merge commit a merge landing's map holds, so it reached the default branch when that branch was merged into it. Such a pull request has no landing of its own, so `validate` and `label` keep their list of landings' changes; it claims its merge commit and the commits of its own the map holds.
- **Copy**: a non-merge commit that a merge landing brought, whose patch id (`git patch-id --stable` over its own `-U0 -w` patch, `domain.Commit.PatchID`) a commit of an earlier landing in the run's history has, by landing time, when that commit is not its ancestor: a cherry-pick or a backport that a maintenance branch merged back brings onto the default branch a second time, or a rebased commit a stacked pull request lands again. That is `git cherry`'s rule (and `git log --cherry-mark`'s): it compares the two sides of a fork, so a commit that descends from its twin made the change again on top of it, and is new work, credited to its author. So no first-parent commit (a direct push, a squash, a rebase merge's commit) is a copy: it descends from every earlier landing. The first landing to bring a change is its original; landings of one second are not earlier than each other; a reverted landing is no original, since the revert took its change out. No metric credits a copy again ([change facts](#change-facts-shared-by-durable1-and-simplifying1), [landed@2](#landed2)). The patch id is not git cherry's: with no context lines, a backport onto code that differs around the change keeps its original's id, which git cherry's three-line patch does not (on tokio-rs/axum's year to 2026-10-16, 18 copies against 12, every one carrying its original's pull request number). A backport whose diff was adapted (a conflict resolved) is not a copy: 10 more of axum's maintenance merges' commits carry an earlier pull request's number and a patch of their own. Blind spots: the patch id ignores where in a file lines go and lines of context, so on the other side of a fork the same small change made independently (one line added to the same file in another function), or a change landed again on a branch that forked before a revert whose message names no commit, is taken for a copy; a first draft of this rule, which compared a commit with its own ancestors too, took direct pushes for copies (on ripgrep a changelog's five-line header added again after a release renamed the first, on vite a pull request landed again after a revert that said so only in its title).
- **Person**: a canonical email after `.mailmap`. Bots (policy name patterns) are never people in ranks.
- **A bot's change**: a change or a landing whose every commit brought in, merge commits aside, is credited to a bot; an empty merge by its own commit's credit. Credit is who wrote the commit (an agent's commit counts for its first human co-author, ADR 0007), not who merged it or opened its pull request: a person's merge of a dependency bump is the bot's, and a pull request an agent opened for a person is the person's. One rule in the code (`metrics` `botLandings`): `label` leaves a bot's changes out of its sample, and a metric that leaves bots' landings out reads the same rule.
- **Area**: a top-level directory of a repository (subject `area`, keyed `<repo key>:<dir>/`): what a scan stores `knowledge_loss@1` and `knowledge_concentration@1` for, beside the repository and its group. A deeper prefix, such as `pkg/sync`, is answered per query by `metrics.PathKnowledge`, the same computation over that prefix's files, so `who-knows` and the MCP server can drill into a dominant area without a stored row per directory. CODEOWNERS entries as areas are a follow-up: no code reads CODEOWNERS today.
- **Scope**: a repo or a group of repos. Ranks never mix groups unless asked to.

## Noise (applied before every metric)

Classification follows [spec/classification.md](spec/classification.md): denied paths (vendored, generated, lockfiles), the generated-header sniff, `linguist-generated`/`linguist-vendored` attributes, and roles. Headline metrics count role `prod` only, which since the packaged policy's [revision 3](spec/classification.md#what-counts-as-product-code-revision-3) (2026-10-16) leaves out example code, benchmarks, documentation tooling and build, packaging and CI tooling; `stillhere paths` lists each path with the rule that gave it its role. A role is a path's, so Rust's unit tests inside the source (`#[cfg(test)]` modules) count as `prod`, which a repository's `inline-tests` caveat measures. A change to the packaged policy is a configured input: it moves values without a new metric version, and the run's policy hash, with the packaged revision reports print beside it, says which policy produced them. Lines are non-blank: a line counts when it holds a character outside Unicode's `White_Space` property (Go's `unicode.IsSpace`, which every collector's count uses; Python's `strip()` differs only in also stripping U+001C–U+001F). Blame runs with `-w -M` and the repo's own `.git-blame-ignore-revs`. Pure renames add nothing. Moved lines inside a file keep their original author through `-M`. Moves across files are a known gap (see open decision 6 in [product.md](product.md#open-decisions)).

## Change facts (shared by durable@1 and simplifying@1)

These rules were settled on 2026-10-14, before the first release, so no metric version changed. Their oracles are in [../testdata/fixture/SPEC.md](../testdata/fixture/SPEC.md#change-oracles-m1-testchangeoracles). The fixtures keep every commit at least a day from every window boundary, so no oracle covers the half-open boundary itself.

- **Added and removed lines.** `added(c)` and `removed(c)` count non-blank lines on `prod` paths in the commit's own patch against its first parent (a root commit against the empty tree): `git log -p -U0 -w`, with git's default rename detection, pinned so that no repository's config can change it ([spec/week-collector.md](spec/week-collector.md#own-patches-scan)). A path is classified at the scanned HEAD or, when it is absent there, at the newest commit that added lines to it, without the header sniff ([classification.md](spec/classification.md#order)). Because of `-w`, a whitespace-only change adds and removes nothing; blame `-w` already gives those lines to their earlier author. A pure rename adds and removes nothing.
- **Surviving lines.** `surviving(c)` counts the non-blank lines blame (`-w -M`, with the repository's ignore-revs file) attributes to `c` at HEAD whose path in `c` is `prod`. Blame names that path for every line, whatever renames lie between `c` and HEAD (its porcelain `filename`, `LineOwner.OrigPath`), and `added(c)` classifies the same line by the same path, the path of `c`'s change, so a line counts in both sums or in neither, whatever its path's role at HEAD. A text file added under `vendor/` or `tests/`, or under a name with no role, and later moved onto a `prod` path keeps none of the lines `c` never added as `prod` lines; a `prod` file later moved into `tests/` keeps its lines, since blame reads a `test` file too. A path blame does not read at HEAD, one with no role such as a denied path, gives no line to any commit, so a `prod` file moved there keeps its lines in `Σ added` and none in `Σ surviving` (a [blind spot](#durable1)). A line blamed to a commit the history does not hold, one older than its window, may sit on a path the run never classified, which has no role; that changes nothing, because such a commit has no `added(c)` either and belongs to no cluster.
- **Credit.** Each commit is credited to one person (`identity.Credit`): its mailmapped author or, when an agent is the author ([ai_assisted@1](#ai_assisted1)) and a human is a co-author, the first human co-author in trailer order after `git check-mailmap`. An agent commit with no human co-author stays with the agent, in the bot table. No other co-author is credited, so the co-authors GitHub lists on a squash merge earn nothing. The commits a merge landing brought in are credited to their own authors, never to the person who merged them. Blamed lines are credited by the same rule, over the blamed commit's author and co-authors (`LineOwner.CoAuthors`), so the ownership metrics and `durable@1` agree on who wrote an agent's commit.
- **Time.** A commit takes its landing's time (the landing commit's committer time), not its own dates. Every window is half-open, `[since, until)`, like `domain.Window`, counted in 24-hour UTC days. Git's `--since` and `--until` both include the boundary instant (verified on 2.50.1), so a landing at exactly `until` must be dropped in code.
- **Excluded commits.** These add and remove nothing in either metric and are never part of a cluster. They still count as landings in `landed@1`.
  - A merge commit itself. In v1 it has no patch of its own, which would need a combined diff. `git log -p` prints no diff for a merge, except under `--first-parent`, where it prints the first-parent diff: the side branch's lines, as the merger's. Lines that blame credits to a merge commit still count in `surviving@1`.
  - A commit listed in the ignore-revs file that blame used for the repository ([blame-collector.md](spec/blame-collector.md#ignore-revs-per-repository)), because formatting commits are noise ([product.md](product.md#what-meaningful-means-in-v1)).
  - A revert landing: one whose own message, or the message of a commit it brought in, carries `This reverts commit <sha>.` ([spec/week-collector.md](spec/week-collector.md#subjects-and-reverts)). An undo is not new work. Counting it would let delete-then-revert earn durable lines (blame credits the restored lines to the revert) and let add-then-revert earn removed lines.
  - A [copy](#units) of a change an earlier landing brought (wave 10): its original counts. Blame gives a copy's lines to the original, so `durable@1` scored it 0 (a backport's author looked less durable for backporting their own fix: on axum one person's 44.4%, 4 of 9, is 50%, 4 of 8), and `simplifying@1` counted its removal twice. A landing made only of copies forms no cluster.
- **Reverted landings.** A landing is *reverted* when its commit map contains the SHA that a revert landing names. `durable@1` keeps it: its lines are gone, so it already scores 0. `simplifying@1` drops all of its commits.
- **Clusters.** A cluster is one person's counted commits in one landing. `N`, the number eligibility reads, counts clusters, and the bootstrap resamples them.
- **Missing facts are not zeros.** A repository without the commits' own patch counts (a week run, a partial clone) adds no cluster to either metric, and one without blame (a shallow or partial clone) adds none to `durable@1`: its added or surviving lines are unknown, and counting them as 0 would score its people as removing nothing or keeping nothing. Within a repository, `durable@1` leaves the lines whose survival blame cannot tell out of both `Σ surviving` and `Σ added`, by one rule that both sums ask about a commit's lines by the path they had in that commit: the history's change names it, and so does blame for every line it attributes (its porcelain `filename`, `LineOwner.OrigPath`), whatever renames lie between the commit and HEAD. A cluster whose added lines are all left out is no cluster. Two facts leave lines out:
  - **A binary change** (`FileChange.Binary`). git takes a file for binary when a NUL byte is in its first 8,000 bytes, or when `$GIT_DIR/info/attributes` says so ([week-collector.md](spec/week-collector.md#attributes-none-from-any-tree)), in any diff whose old or new side is binary: numstat prints `-` `-` and the own patch has no hunks. The change's added lines are therefore unknown, while blame still attributes every line of the file. The change is left out of `Σ added`, and the lines blame attributes to its commit from its path are left out of `Σ surviving`, at whatever path HEAD holds them: renamed by a commit the history saw or not (one outside its window, or one with more rename candidates than its limit), and whatever the role of the change's own path (a binary file moved out of `vendor/` onto a `prod` path). The commit's other changes keep their lines, and so do other commits' changes to the same file, which can be text at one commit and binary at the next ([`fixture.Binary`](../testdata/fixture/SPEC.md#binary-files-fixturebinary)).
  - **A failed blame.** Blame is a bulkhead per file: a `prod` file whose blame failed (`RepoFacts.BlameErrors`: a timeout, a failed `git blame`, porcelain that does not parse) has no line owners while the rest of the repository keeps them. Every commit's lines on it, and on each path the history renamed into it, are left out. With no line owners, the renames the history recorded are the only link to the paths its lines had before, so lines added before a rename the history did not record stay in `Σ added` with no surviving line: that lowers a ratio and never raises one.

  `simplifying@1` has no denominator to keep in step: a binary change adds no removed line to it, so its sum is a lower bound where a binary change removed lines.

## Values: what every metric returns

Each metric returns `domain.MetricValue`s. They are a published language: the report, the store, `explain` and the MCP server all read them, so these rules hold for every metric in this catalog, and each entry names its subjects and `Detail` keys. A metric's definition in code declares the kinds of subject a scan stores its values about (`metrics.Definition.Subjects`), and `explain` refuses a question about any other kind, in every run (#69).

- **Scopes and subjects.** A value about a person (subject `person`, the canonical email) is computed in each repository (scope `repo`), each group (scope `group`) and the whole run (scope `all`), over the repositories in that scope. A value about code has the code as its subject: a repository (subject `repo`), a top-level directory (subject `area`, keyed `<repo key>:<dir>/`) or a group (subject `group`), in the scope of its repository or group. A group's code values are recomputed over its repositories, never summed from per-repository values, and code values have no cross-group total. A value about what landed in a scope as a whole, `landed@2`'s totals and `review_coverage@1`, has the scope's own subject: `repo`, `group`, or for scope `all` subject `all` (key `""`), recomputed over the scope's repositories like a group's. A value about one change has subject `change` (the landing SHA).
- **Window.** The metric's own window for `--now`, half-open. A snapshot at HEAD (surviving lines, ownership) has the zero window.
- **HEAD.** In every definition, HEAD is the commit the run read in each repository: the newest commit on its default branch's first-parent chain whose committer time is before `--now`, strictly, as the windows are half-open, found by walking that chain down from the branch's head ([run model](spec/codebase.md#run-model), [ADR 0012](adr/0012-a-run-reads-each-repository-as-it-stood-at-now.md)). Where committer times grow along the chain toward the head, HEAD is the repository as it stood at `--now`: a snapshot and every window describe the same moment, no line written after `--now` is held by anyone, and no landing after it is counted. When the branch's head is newer, the repository's `head-after-now` caveat names the commit read and the landings it leaves out. Where the chain's committer times are out of order (a backdated commit above newer ones, or a clock that ran ahead), the commit read can sit above landings dated at or after `--now`: blame counts their lines while no window counts them, so their authors can look inactive, and the repository's `dated-after-now` caveat counts them ([SPEC.md](../testdata/fixture/SPEC.md#landings-dated-after---now-below-the-commit-read-fixturebackdated)). A repository with no commit before `--now` has no value at all.
- **Value, Num, Den, N.** A ratio sets `Num` and `Den`, and `Value` is their quotient; any other value has `Num = Value` and `Den = 1`. Whether a metric's values are ratios is its definition's to say (`metrics.Definition.Ratio`), never its `Den`'s, since a share of 1 of 1 has `Den = 1` too: `explain` and `me` print a ratio as a percent, `100.0% (1 of 1)`, by that one declaration (#66). `N` is the sample size eligibility reads: clusters for the ranked metrics, landings or clusters for the shares below, and 0 where nothing is sampled.
- **Detail.** Context numbers, never ranked, with the snake_case keys each entry lists. A ratio over nothing is left out rather than written as NaN.
- **Bots** get values like people, so the report can list them in the bot table; `identity.Directory.Bot` tells them apart, and the ranked metrics leave them out of the clusters they hand to the bootstrap.
- **What a value is made of.** `explain` traces every value about a person to the facts behind it (product.md's principle 2): a ranked metric's to its clusters (`metrics.Ranked`), a bot's included, since the bot filter is ranking's, not explanation's (#75); `landed@1` and `landed@2` to the landings they count, `surviving@1` to the blamed commits holding the person's lines, and `majority_owner@1` to their files (`metrics.Traced`, #109), each traced by the metric's own projection and rule, never a second copy of it. A value about code is traced too (wave 10): `landed@2`'s totals of a repository, a group or the run to their landings, with the copies each brought, and `review_coverage@1` to every change of its window with its outcome; `explain --days N` traces `landed@1` and `landed@2` over any window the history holds, such as the 365 days of `surviving@1`'s `landings_365d`. A metric that holds no value about a person the run has other values about says why where the run can tell (#92).
- **Missing facts.** A repository whose collection failed gives no value. One without blame gives no blame-based value, and one without patch counts no change value ([change facts](#change-facts-shared-by-durable1-and-simplifying1)). One without numstat (a partial clone, whose blobs are not local) has no lines in `landed@1` or `landed@2`: their lines keys are absent rather than 0, a scope's total leaves its landings' lines out and counts those landings in `landings_lines_unknown`, and the lines keys are absent when no landing's lines are known (#74). One whose history (`RepoFacts.History`) does not cover a metric's window gives no landing-based number for it, so a week run never yields a 365-day share computed from seven days. A shallow clone whose boundary cuts its history (warning `shallow-window`, [discovery.md](spec/discovery.md#clone-health)) covers a window only when the window lies wholly after the boundary: every boundary commit the history holds (`domain.Repo.Boundary`, a commit with no parent in a shallow clone) was committed before the window starts, and no landing in the window brought one in. The clone then holds every landing of the window and every commit they brought in, so a depth-50 clone has last week's landers, as a full clone does; any other window gets no value, never a count of whatever the clone happens to hold (#74). Activity is the exception: `knowledge_loss@1`'s activity, `who_knows@1`'s recent landers and `surviving@1`'s `landings_365d` count every landing seen in their window, because a landing proves activity however much history is missing.
- **Order.** Values are sorted by metric, scope, subject and window, so two runs over the same facts give the same bytes.

## Context metrics (shown, never ranked)

### landed@1
- **Question**: What landed in the window?
- **Unit and scope**: landings per person, in each repository, group and all.
- **Inputs**: landings, commits (authors and co-authors), file changes (numstat), path classes.
- **Definition**: landings on the default branch with committer date in `[now − days, now)`, walked with `--first-parent --diff-merges=first-parent`, where `days` is `--days`, else the policy's `[week] days`. Per person: the landings whose landing commit is [credited](#change-facts-shared-by-durable1-and-simplifying1) to them: its author, or its first human co-author when an agent wrote it, whether or not the run has GitHub data. Value: landings. `Detail`: `lines_added` (numstat insertions on every path that received a role, blank lines included; a merge landing's are its first-parent diff) and `prod_lines_added` (the `prod` subset), exactly as [landed@1 (main fixture)](../testdata/fixture/SPEC.md#landed1-main-fixture) fixes them; and `landings_lines_unknown`, the landings whose lines are unknown because their repository's history has no numstat (a partial clone), which both lines keys leave out. That key is present only when there are such landings, and when no landing's lines are known the two lines keys are absent, not 0 ([missing facts](#values-what-every-metric-returns)). These are activity numbers and are not comparable to non-blank still-here lines.
- **Eligibility and uncertainty**: none: a count, never ranked.
- **Why not ranked**: volume rewards volume. A dependency bot led every activity table in the proof run.
- **Blind spots**: a merged branch's lines count for whoever landed it, which `landed@2` corrects; numstat counts blank lines and moves; work that never reaches the default branch is invisible.
- **How it can be gamed**: splitting work into many small landings.
- **Fixture oracle**: [SPEC.md, landed@1 (main fixture)](../testdata/fixture/SPEC.md#landed1-main-fixture); without numstat, [SPEC.md, partial and shallow clones](../testdata/fixture/SPEC.md#partial-and-shallow-clones-74).
- **Validity**: context, exact by construction; it says nothing about value.
- **Changelog**: 2026-10-15 (#74): a repository without numstat gives no lines, where it gave 0 lines for every landing and added those zeros to a group's and the run's totals (a partial clone's `week` printed `Bob Brown 5 0 0`). No release had shipped `landed@1`, so it keeps `@1`. It stays registered and computed for continuity; since 2026-10-15 (#108) the report's what-landed tables, `week` and MCP `overview` read `landed@2`, and no table reads `landed@1`.

### landed@2
- **Question**: Who wrote what landed in the window?
- **Unit and scope**: landings per person, in each repository, group and all; and the scope's own totals, about the repository (subject `repo`), the group (subject `group`) and the whole run (subject `all`).
- **Inputs**: landings and the landing map, commits (authors and co-authors), file changes (numstat), path classes.
- **Definition**: the landings in `[now − days, now)` of `landed@1`, each with its non-merge commits (the landing map, `Landing.Commits`; a non-merge landing is its own one commit), each commit [credited](#change-facts-shared-by-durable1-and-simplifying1) by `identity.Credit` as everywhere: its author, or an agent's first human co-author. Per person: Value is the landings that hold at least one commit credited to them, so a merged branch counts for the people who wrote it, as `durable@1` and `surviving@1` credit its lines. A [copy](#units) of a change an earlier landing brought is credited to no one, its lines included: its change was credited when it first landed, so a maintenance branch merged back does not credit each backported fix twice. `Detail`: `commits` (their credited non-merge commits), `lines_added` and `prod_lines_added` (the sum of those commits' own numstat insertions on paths that received a role, blank lines included, and the `prod` subset), `merged` (merge landings whose landing commit is credited to them), and `landings_lines_unknown` under `landed@1`'s rule. A merge commit's own diff is credited to no one's lines; its landing commit's person gets `merged`. A bot's commits count for the bot, in the bot table, even when a person merged them. Per scope (subject `repo`, `group` or `all`): the same numbers over every landing of the scope: Value the landings, `commits` their non-merge commits that are no copy, `merged` the merge landings, the lines, and `copies` (the copies the landings brought). A scope has its totals whenever one of its repositories' history covers the window, 0 when nothing landed there, and none when no repository's does (a shallow clone whose boundary is inside the window, [missing facts](#values-what-every-metric-returns)), so a page tells "nothing landed" from "unknown".
- **Eligibility and uncertainty**: none: a count, never ranked.
- **Why not ranked**: volume rewards volume.
- **Blind spots**: lines are per commit, so a branch that adds lines and later removes them counts both adds (`landed@1` keeps the landing's own diff); a squash merge credits the squash commit's author, whom GitHub sets to the pull request's author, and a rebase merge is already one landing per commit; numstat counts blank lines and moves; work that never reaches the default branch is invisible. A backport whose diff was adapted has a patch id of its own and is credited again, and a copy whose original landed before the history the run read (365 days for a scan, the window for `week`) is credited as an original. A change landed again after a revert took it out is credited again, but in `week`, which reads no reverts, one a merge brought from a branch that forked before its first landing is a copy. A [copy](#units)'s own blind spots apply.
- **How it can be gamed**: splitting work into many small commits or landings.
- **Fixture oracle**: [SPEC.md, landed@2 (main fixture)](../testdata/fixture/SPEC.md#landed2-main-fixture), which the [week oracle](../testdata/fixture/SPEC.md#week-oracle-m0-testweekoracle) prints; without numstat, [SPEC.md, partial and shallow clones](../testdata/fixture/SPEC.md#partial-and-shallow-clones-74); copies, [SPEC.md, merge-back guard](../testdata/fixture/SPEC.md#merge-back-fixturemergeback).
- **Validity**: context, exact by construction; it says nothing about value. On cli/cli (365 days to 2026-10-15), 499 of 602 landings are merges, so `landed@1` credits most of what landed to the few people who merge: in the week to 2026-10-15 one maintainer had 15 of its 17 landings, 13 of them merges. `landed@2` gives that maintainer 7 landings, with 8 commits and 13 `merged`, and dependabot the 8 landings its 8 commits came in, which `landed@1` gave to whoever merged them (#108). On tokio-rs/axum (365 days to 2026-10-16), whose maintainers merge a `v0.8.x` branch back six times, 18 of its 255 non-merge commits are copies: the year's totals are 237 commits and 6,781 lines added, where they were 255 and 7,460, and one person who backported their own two fixes has 3 landings, not 4.
- **Changelog**: 2026-10-16 (wave 10), before the first release, so the version stays 2: a copy of a change an earlier landing brought is credited to no one, and a scope's totals count `copies`. A run stored before holds no patch id, so its readers find no copy in it.

### surviving@1
- **Question**: Whose lines are still on the default branch?
- **Unit and scope**: non-blank lines at HEAD per person, in each repository, group and all; and one value about each repository and each group.
- **Inputs**: line owners (blame with the repository's ignore-revs file), path classes, landings and the landing map.
- **Definition**: non-blank `prod` lines at HEAD, grouped by the person credited for the blamed commit ([credit](#change-facts-shared-by-durable1-and-simplifying1)): its author, or the first human co-author of an agent's commit. A person has a value in a scope only when they hold surviving `prod` lines there, which are the rows of the still-here table; `Detail` then carries their lines on every role.
  - Per person, `Detail`: `repos`, the repositories in the scope where the person has surviving `prod` lines (breadth); `majority_files`, as in [majority_owner@1](#majority_owner1) (depth); `lines_<role>` for each role the person has surviving lines on, such as `lines_prod` and `lines_test`; `landings_365d`, the landings in `[now − 365 days, now)` that [landed@2](#landed2) credits to them, those holding a non-merge commit of theirs that is no copy (activity: who wrote what landed, so `explain landed@2 --days 365` lists them); and `merged_365d`, the merge landings of that year whose merge commit is theirs, `landed@2`'s `merged`, apart. Breadth, depth and activity together show a person's shape: platform-wide author, service owner, or someone who edits widely inside other people's files.
  - Per repository and per group (subject `repo` or `group`): Value `prod_lines`, and `Detail` `prod_lines`, `prod_files` (`prod` files with surviving lines), `people` (distinct humans with surviving `prod` lines), `bot_share` (the share of surviving `prod` lines credited to bots) and `ai_assisted_share` (the share of the landings in `[now − 365 days, now)` tagged [ai_assisted@1](#ai_assisted1)).
- **Eligibility and uncertainty**: none: never ranked.
- **Why not ranked**: it rewards tenure.
- **Blind spots**: blame credits the last author of a line, so a reformat missing from `.git-blame-ignore-revs` moves lines to its author; moves across files credit the mover (no `-C`); a squash merge credits every line of a pull request to its author, and its co-authors get none; shallow and partial clones have no value.
- **How it can be gamed**: rewriting other people's lines (a reformat, a mass rename) moves their blame to the rewriter.
- **Fixture oracle**: [SPEC.md, still-here oracle](../testdata/fixture/SPEC.md#still-here-oracle-m1-teststillhereoracle).
- **Validity**: context, never ranked. Blame as an authorship signal: Avelino, Passos, Petrillo and Valente, "Who Can Maintain This Code?" (IEEE Software 36(6), 2019; first presented at SBES 2018), compared the maintainers developers named in ten systems with three repository-mining techniques. On the two commercial systems, the share of a file's lines a developer owns in the last version (blame) matched them best (a harmonic mean of hit ratios of 67%, against 66% for commit counts and 63% for degree of authorship); on eight open-source systems the three were within 60–63%. Their threshold was relative to a file's top author (best at 10%), not half of the file, so the study supports the signal, not stillhere's exact rule.
- **Changelog**: 2026-10-16 (wave 10), before the first release, so the version stays 1: `landings_365d` follows `landed@2`'s credit, and `merged_365d` counts the merges apart. It counted every landing whose commit map held a commit credited to the person, merge commits included, so whoever merged looked like the most prolific lander beside a what-landed table that credits who wrote (pallets/click: one maintainer's 110 landings in 365 days, of which 22 hold a commit of theirs), and no `explain` could list them. A run stored before is told by its data, person values without `merged_365d`, and its readers compute the metric again from its facts.

### review_coverage@1
- **Question**: How much of what landed was reviewed by someone other than its author?
- **Unit and scope**: a share of changes, per repository (subject `repo`), per group (subject `group`) and for the whole run (subject `all`). Never about a person, and never ranked: a per-person review rate would make reviewing a target for individuals, which is what `reviews_given@1`'s blind spots warn of.
- **Inputs**: landings and the landing map, commits and their patch ids, the GitHub data the run read (`FactSet.Forge`: pull requests, their base branches, merge commits, commits and reviews), and the policy's `[bots]` fragments.
- **Window**: changes that reached the default branch in `[now − 90 days, now)`, `reviews_given@1`'s.
- **Definition**: the unit is the [change](#units), the one grouping `validate` and `label` read: a merged pull request with the landings that put it on the default branch, as `who_knows@1` and `reviews_given@1` map a landing to its pull request (its merge commit, and a rebase merge's commits that share its committer second, [who_knows@1](#who_knows1-per-path)); a pull request merged into another branch, a maintenance or release branch, whose merge commit a merge landing in the window brought (`via_other_branch`: it reached the default branch with that merge, and its own reviews before its merge count); or a landing no pull request landed. `Den` is the window's changes of their own work whose author is human and whose pull request, or its absence, the GitHub data the run read knows. A change's own work is its non-merge commits that are no [copy](#units) and belong to no pull request merged into another branch that it brought; a merge with none, one that only brought such pull requests (each a change of its own) and copies, is left out (`branch_merges`), and so is a change made only of copies (`copies`), which were counted when they first landed. A change's author is its pull request's author; when a coding agent opened the pull request (an `[ai]` agent such as `copilot-swe-agent[bot]`, `identity.Directory.Agent`), the person its commits are credited to, its first commit credited to a human (`identity.Credit`, as `landed@2` credits it), since the agent worked for them; with no pull request, the person its landing commit is credited to. A bot's change is left out (`bot_landings`): one whose every commit of its own is credited to a bot (an app account, or a `[bots]` match, which `identity` decides), such as a dependency bot's pull request or a person's merge of one, by the one rule for a bot's change that `label` reads too ([units](#units)). `Num` is those whose pull request has at least one review submitted before the pull request merged (approved, changes requested, or commented) by a human other than that author and the pull request's, compared as people (`identity.Directory.Reviewer`), so a second account the run links to the author does not count, nor the review of the person an agent worked for. A landing with no pull request in the GitHub data counts as unreviewed (`direct`: pushed straight to the branch, or merged from a private fork as a security advisory is), unless whether it had one is unknown, which leaves it out of `Den`: it landed at or after the GitHub data's as-of, the start of the repository's last sync (`after_sync`: a clone fresher than the sync), or its subject names a pull request the way GitHub's merges write one, `Merge pull request #N from …` or a squash's `… (#N)`, which the data lacks (`unmatched`: a sync that did not finish, or a replica with a hole, #101), or which the data holds merged but not by a merge commit the default branch holds (`named_elsewhere`: merged into another branch and cherry-picked onto the default branch, or the branch rewritten after GitHub merged it; no sync changes it). A subject naming a pull request that landed by its own merge commit, or never merged, is a direct push. `Detail`: `reviewed` (`Num`), `via_pull_request` (pull requests merged into the default branch), `via_other_branch` (pull requests merged into another branch that a merge brought), `direct` (landings with no pull request in the GitHub data), so `Den` is the sum of those three; `approved_no_comment` (reviewed changes whose counted reviews were all approvals with no text and no inline comment); `bot_landings`, `branch_merges`, `copies`, `after_sync`, `unmatched` and `named_elsewhere` (left out of `Den`); and `repos` (the repositories with GitHub data counted). `explain review_coverage@1 --repo NAME` (or `--group`, or the MCP server's `explain` about a repository or a group) lists every change of the window with its outcome, those in `Den` that no one else reviewed first.
- **Missing facts**: a repository without GitHub data has no value, never 0, and the existing `forge-not-synced` caveat says so; a group or the run counts only its repositories with GitHub data, which `repos` says. A share of no change is no value. A landing whose pull request may be missing from the data (`after_sync`, `unmatched`) is left out, not counted as unreviewed: on cli/cli (90 days to 2026-10-15), whose replica lacks most pull requests numbered 13800 to 14000 (#101), 35 of 44 landings without a pull request in it name one, and counting them as direct pushes gave 61.6% (101 of 164) where the landings the data knows give 78.5% (102 of 130). The share speaks for what the data holds: the sync's completeness check (ADR 0013) caveats a repository whose replica is incomplete.
- **Eligibility and uncertainty**: none: it describes how a codebase's changes land, not people.
- **Blind spots**: review outside GitHub, pairing, and conversation comments outside a review are invisible; a direct push is unreviewed whatever happened before it; a rebase merge whose commits GitHub committed in different seconds maps only its last commit to its pull request, so the others count as direct ([#67](https://github.com/IHaveASegway/stillhere/issues/67)), and of a pull request rebased into another branch only its last commit is its own, so the merge that brought it holds the others as work of its own; a pull request the data lacks makes its landing direct unless its subject names it, which a rebase merge's does not; a direct push whose subject ends in `(#N)` for an issue is left out as `unmatched`; a pull request merged into another branch counts only once that branch is merged into the default branch, and a cherry-pick of it onto the default branch is left out as `named_elsewhere`; a merge of another branch that also brought commits pushed straight to it is a change of its own, unreviewed unless its pull request was reviewed, even when those commits cancel out (a change and its revert).
- **How it can be gamed**: a rubber-stamp approval counts as a review, which is why `approved_no_comment` is shown beside the share; an approval from a second account the run does not link to the author counts too.
- **Fixture oracle**: [SPEC.md, review_coverage@1 with reviews](../testdata/fixture/SPEC.md#review_coverage1-with-reviews), the [merge-methods guard](../testdata/fixture/SPEC.md#merge-methods-fixturemergemethods), and the [merge-back guard](../testdata/fixture/SPEC.md#merge-back-fixturemergeback).
- **Validity**: context, unvalidated: it says whether a change had an independent review, not how good the review was. On go-chi (20 repositories, 90 days to 2026-10-15) it was 19 of 40 landings: 39 merged pull requests, 20 of them with no review by anyone but their author (GitHub's own `review:none` search gave 22 in the dogfood that found it, #107), and one direct push. On the pallets organization (90 days to 2026-10-16) it is 31 of 177 changes (17.5%), where counting landings gave 18 of 137: the 42 pull requests merged into `stable` branches, which merges brought, were invisible. For pallets/click it is 28 of 38 (73.7%; landings gave 16 of 22, 72.7%): GitHub's API, asked for every pull request merged in the window that the default branch holds, counts 28 of 39 reviewed, the one more being `Merge main into stable`, a merge with no commit of its own, left out here; in every pallets repository the pull requests counted and those reviewed agree with GitHub's.
- **Changelog**: 2026-10-16 (wave 10), before the first release, so the version stays 1: the unit is the change, not the landing: a rebase merge's landings are one change, a pull request merged into another branch whose merge a landing brought is a change of its own (`via_other_branch`), a merge that brought only those and copies is left out (`branch_merges`), as is a change made only of copies (`copies`), and a landing naming a pull request the data holds, merged elsewhere, is left out as `named_elsewhere`, without the advice to sync again that `unmatched` carries. The merge-methods guard's value moves from 4 / 6 to 3 / 5. A run stored before is told by its data, values without `via_other_branch`, and its readers compute the metric again from its facts ([run model](spec/codebase.md#run-model)), so `report` and `explain` show the share the list beside it counts; a run that kept no pull requests keeps its stored value, with no list.
- **Changelog**: 2026-10-16 (wave 10, #117), before the first release, so the version stays 1: a pull request's author and its reviewers are compared as the people `identity.Directory.Reviewer` says they are, which now reads every link the run holds (the older pull requests' and the links pass's answers for the history's author emails, as the same-forge-account rule does), where it read only the pull requests' own commits the history holds. A reviewer's second account the run links to the author now counts as the author more often, and its review no longer as independent. On the encode, pallets, hono and axum runs of round 2 no value moved.

## Ownership and knowledge

### majority_owner@1
- **Question**: Which files does a person hold most of?
- **Unit and scope**: `prod` files at HEAD per person, in each repository, group and all.
- **Inputs**: line owners, path classes.
- **Definition**: a person credited with at least 50% of a file's non-blank lines owns it. A 50/50 file has two majority owners and counts once in `files_with_majority`; never `max()` alone, which hides the split. Value: the files the person owns. Bots can be majority owners and stay in the bot table.
- **Eligibility and uncertainty**: none: never ranked.
- **Blind spots**: blame's, as in `surviving@1`. A file nobody holds half of has no owner, so highly collaborative files are invisible here.
- **How it can be gamed**: rewriting a file's lines takes its ownership.
- **Fixture oracle**: [SPEC.md, still-here oracle](../testdata/fixture/SPEC.md#still-here-oracle-m1-teststillhereoracle) (`majority_files`, and the 2/2 split of `split.py`).
- **Validity**: context, never ranked. Bird, Nagappan, Murphy, Gall and Devanbu, "Don't Touch My Code!" (ESEC/FSE 2011), found that ownership measures relate to pre-release faults and post-release failures in Windows Vista and Windows 7: components with more minor contributors (under 5% of the commits) failed more, and a higher top-owner share failed less. Their ownership counts commits per component, not surviving lines per file. Greiler, Herzig and Czerwonka (MSR 2015) replicated the link at Microsoft; Foucault, Falleri and Blanc (EASE 2014) found it weak in open source, where module size predicted faults better. For blame as the authorship signal, see `surviving@1`.

### knowledge_concentration@1 (per area)
- **Question**: How few people hold half of the code's majority-owned files?
- **Unit and scope**: people, per repository (subject `repo`), per top-level directory (subject `area`) and per group (subject `group`); for any deeper path prefix on request (`metrics.PathKnowledge`, which a scan does not store), as for an [area](#units).
- **Inputs**: line owners, path classes.
- **Definition**: sort authors by `majority_files` descending, then `prod_nonblank_lines` descending, then email ascending. Walk from the top until the running sum is at least `files_with_majority / 2` (true division). Report the number of authors in that prefix and how many are bots. Labelled "not a truck factor": it is not Avelino's degree-of-authorship algorithm. Value: `authors_in_prefix`. `Detail`: `files_with_majority` (each file once, even with two owners), `bots_in_prefix`, `prod_files`. A group re-runs the walk on its summed columns; it is not the sum of its repositories' prefixes. An area where no file has a majority owner has no value.
- **Unmerged identities** (#104): when the run's identity candidates hold lines in the area, `Detail` also has `identity_candidates` (candidates with an address among the people holding lines there), `identity_candidates_high` (the candidates with high-confidence lines: a high candidate, or a weaker one's high set, `identity.Candidate.High`), and `if_merged` and `if_all_merged`: `authors_in_prefix` with the high-confidence lines merged, and with every candidate merged, into one person each, majority owners found again by `majority_owner@1`'s rule ([identities.md](spec/identities.md#what-unmerged-identities-do-to-knowledge-loss)). The value itself moves for no one, so the version stays 1.
- **Eligibility and uncertainty**: none: it describes code, not people.
- **Blind spots**: only majority-owned files count, so code where nobody holds half of any file looks unconcentrated; it ignores who could take a file over.
- **How it can be gamed**: it is no one's target; it moves when ownership moves.
- **Fixture oracle**: [SPEC.md, still-here oracle](../testdata/fixture/SPEC.md#still-here-oracle-m1-teststillhereoracle), the concentration walk.
- **Validity**: context. Built on `majority_owner@1` (see its evidence). The validated algorithm it deliberately is not: Avelino, Passos, Hora and Valente's truck factor (ICPC 2016).
- **Changelog**: 2026-10-16 (wave 10), before the first release, so the version stays 1: GitHub's link (`same-forge-account`) is high for an address whose commits carry names that differ too ([identities.md](spec/identities.md#rules)), so `identity_candidates_high` and `if_merged` move where such an address holds lines: on the encode organisation (2026-10-16) `identity_candidates_high` moves in 18 values (httpcore's 5 to 6). The value itself moves for no one. A run stored before has its knowledge values computed again when it is read (`knowledge_loss@1`'s changelog).

### knowledge_loss@1 (per area)
- **Question**: How much of the code is held by people who have gone quiet?
- **Unit and scope**: a share of surviving `prod` lines, per repository (subject `repo`), per top-level directory (subject `area`) and per group (subject `group`); for any deeper path prefix on request (`metrics.PathKnowledge`, which a scan does not store), with activity read over the whole run as for a stored value.
- **Inputs**: line owners, path classes, landings and the landing map of every scanned repository, and the commits of their clones' other refs (`RepoFacts.RefCommits`); the pull requests and reviews of their GitHub data the run read (`FactSet.Forge`), and the commits that link logins to people.
- **Definition**: the share of an area's surviving `prod` lines whose credited person has had no activity anywhere in the scanned organization in the last 180 days: no landing, no submitted review, no pull request opened or pushed to, and no commit on another branch or tag ([activity](#knowledge_loss1-per-area), below). `Num` is those lines, `Den` all lines held by people. `Detail`: `people` (humans holding lines in the area), `people_inactive`, and `going_quiet_num` and `going_quiet_people`: the lines of `Den`, and the people holding them, whose last activity is 150 to 180 days old, so they cross the line within 30 days unless they are active again, which a page warns of (a `going-quiet` caveat) before the share jumps, naming those people beside the share (its `going_quiet.holders`, from the section's still-here rows).
- **Unmerged identities** (#104): when the run's identity candidates hold lines in the area, `Detail` also has `identity_candidates` (candidates with an address among the people holding lines there), `identity_candidates_high` (the candidates with high-confidence lines: a high candidate, or a weaker one's high set, `identity.Candidate.High`), and `if_merged_num` and `if_all_merged_num`: `Num` with the high-confidence lines merged, and with every candidate merged, into one person each, a candidate active when any of its addresses is. Merging moves no line out of `Den`, and makes no active line quiet, so `if_all_merged_num ≤ if_merged_num ≤ Num`: the range an unmerged identity leaves the value in ([identities.md](spec/identities.md#what-unmerged-identities-do-to-knowledge-loss)). The same function computes all three. On the go-chi group, 56.6% as keyed, 52.2% and 17.6% (2026-10-15).
- **Activity**: within `[now − 180 days, now)`, a person has been active when (`metrics.LastActivity`, the one rule, which every page's last activity of a person reads too):
  - a commit credited to them, merge commits included, is in a landing in the window. Through the landing map, a side-branch author is active when the branch lands, whoever merged it;
  - they approved, requested changes on, or commented on, in a review submitted in the window, any pull request of the run's repositories (`domain.ForgeJoin`), open, closed or merged, their own included: unlike `reviews_given@1`, which counts the review load, activity asks only whether someone is still around;
  - they opened a pull request there in the window (its creation time), or pushed a commit of their own to one of their own pull requests: a commit of the pull request, written by its author's account, that a clone holds (its author time). Its update time is not their activity: anyone's comment, a bot's label or a maintainer closing it moves it, and on encode/httpx a pull request of 2019 was updated in September 2026;
  - a commit credited to them (`identity.Credit`, so an agent's commit counts for its human co-author) is on another ref of a clone, a branch, a remote-tracking branch or a tag, which the commit the run reads does not hold, written in the window (its author time: a rebase or a cherry-pick by someone else moves only the committer time) and committed before `now` ([week-collector.md](spec/week-collector.md#commits-on-other-refs-scan)): a release prepared on a branch, or work waiting in a pull request's branch.

  A GitHub account is a person as `reviews_given@1` links it (`identity.Directory.Reviewer`); one known only as `@login` holds no line, so only a linked account can change a value. Forge activity comes from the GitHub data the run kept, branch commits from the clone, both bounded by `now`, so a stored run's value is a function of what it read.
- **Bots**: lines credited to bots are left out of both the numerator and the denominator, because knowledge is held by people. `surviving@1` shows the bot share alongside it.
- **Eligibility and uncertainty**: none: it describes code, not people.
- **Blind spots**: people who moved to repos outside the scan look gone, and so does work on a fork's branch, which no clone of the scan holds. Mailmap gaps split one person into two and can make either half look gone: a commit on another branch counts for the address it was written with, so a maintainer committing a release under an address the default branch never saw is active only through their pull request, or once a `.mailmap` line merges the address. Reviews and pull requests count only in repositories whose GitHub data the run read, and only for an account the run links to an address: one GitHub attributes a commit of the run's to, through a pull request's commits or the links pass's answer for the history's author emails (#117). Without GitHub data the value counts landings and branch commits only. Activity is the whole run's, so a repository scanned alone can read far higher than in its organization's scan: on encode/django-rest-framework, 95.2% alone and 37.2% beside its five siblings (2026-10-16), where its top holder reviewed and opened pull requests elsewhere.
- **How it can be gamed**: a quiet expert who lands one trivial change, submits one review, opens a pull request or pushes a commit to any branch resets their clock.
- **Fixture oracle**: [SPEC.md, knowledge_loss@1](../testdata/fixture/SPEC.md#knowledge_loss1-main-fixture), and with reviews, [SPEC.md, reviews in knowledge_loss@1 and who_knows@1](../testdata/fixture/SPEC.md#reviews-in-knowledge_loss1-and-who_knows1-main-fixture).
- **Validity**: context, unvalidated; inactivity stands in for departure, which it is not. Prior art measures the same thing: Rigby, Zhu, Donadelli and Mockus, "Quantifying and Mitigating Turnover-Induced Knowledge Loss" (ICSE 2016), used files abandoned by departed developers as the proxy at Chrome and Avaya, and CodeScene's knowledge-loss view (Tornhill, *Software Design X-Rays*, 2018) does it with history.
- **Changelog**:
  - 2026-10-15 (#38): submitted reviews count as activity. No release had shipped `knowledge_loss@1` without them, so it keeps `@1`, as the 2026-10-14 change-fact rules did.
  - 2026-10-15 (#69): logins link to people without case, as `reviews_given@1`'s do (`identity.Directory.Reviewer`). A login whose pull request commits carry it in one case and whose reviews carry it in another, as after the account changed the case of its login between two syncs, had stayed an unlinked `@login`, which holds no line, so the person's reviews were not their activity; now they are, and the value can fall. No release had shipped `knowledge_loss@1`, so it keeps `@1`.
  - 2026-10-15 (#104): the unmerged-identities `Detail` keys above. `Value`, `Num`, `Den` and the other keys move for no one, so it keeps `@1`; a run stored before has none of the new keys.
  - 2026-10-16 (wave 10), before the first release, so the version stays 1: activity also counts a pull request opened, or pushed to with its author's own commit, and a commit on any other ref of a clone (both above), and a GitHub account links to a person by every link the run holds, the links pass's answer for the history's author emails included (#117: `identity.Directory.Reviewer` reads links as the same-forge-account rule does), where it read only pull request commits the history holds. On encode/httpx scanned alone (2026-10-16), the value was 100% (7,437 of 7,437) while its maintainer prepared a release on a branch through a pull request two weeks before; it is now 29.8% (2,213). At `--now 2026-04-10` it was 100.0% (7,435) and is 29.3% (2,181), 20.6% with the high-confidence identity candidates merged. GitHub's link is high for an address whose commits carry names that differ too ([identities.md](spec/identities.md#rules)), so `identity_candidates_high` moves where such an address holds lines, in 18 values on the encode organisation (2026-10-16, httpcore's 5 to 6), and `if_merged_num` and `if_all_merged_num` move with it and with the activity above in 5 (httpx's 2,213 to 2,185). Also `going_quiet_num` and `going_quiet_people` (above), which move nothing else. A run stored before keeps values computed under the earlier rule, which its pages' per-query activity no longer follows (encode/httpx: a card of 100% beside holders active two weeks before), so its readers compute both knowledge metrics again from its facts, told by the `going_quiet` its values lack (`metrics.Corrected`); such a run kept no commit of another ref, so those count for no one until a new scan, which the reader logs.

### who_knows@1 (per path)
Majority owners of files under the path, the top surviving-line authors, recent landers (90 days), and recent reviewers (90 days) from the GitHub data the run read; the query may name another window for both, at most the history the run read (`who-knows --days N`, the MCP server's `who_knows` `days`), and the answer says which (`days`). It is a routing answer, not a rank, computed per query (`who-knows PATH`, `metrics.WhoKnows`) over a run's facts, its GitHub data included, which the run keeps ([ADR 0011](adr/0011-a-run-keeps-the-github-facts-it-read.md)); a scan stores no values for it, because precomputing every directory of every repository would store more rows than the facts.
- **Which lines**: `prod` lines; under a path that holds no surviving `prod` line, the lines of every other role there (`test`, `doc`, `iac`, ...), which blame reads as it reads `prod` files, so `tests/` or `docs/` is answered for its own lines rather than as nobody's, with an `other-roles` caveat saying the people listed hold tests or docs, not product code. The path's `knowledge_loss@1` and `knowledge_concentration@1` count `prod` lines only, so such a path has neither. A path that holds `prod` lines is answered for them alone, and says which other roles' lines it leaves out (`uncounted_<role>_lines` and `_files`, below); where those of roles other than `test` outnumber the `prod` lines it counts, an `uncounted-roles` caveat says the people listed know its product code, not the rest (werkzeug's `docs/`, 2026-10-16: 53 lines of `docs/conf.py` beside 2,649 doc lines in 37 files and 42 iac lines in 2). Test lines are left out of that comparison, since tests sit beside the code they test, mostly by its own people: cli/cli's `pkg/cmd/pr` holds 18,478 test lines beside 9,983 prod lines and is answered for its code without a caveat. Counting every role there instead would answer such a package for its `_test.go` files. A path with no role at all (unclassified, denied, generated or too big) gets an empty answer whose `no-values` caveat says why and what would make it count: a role for an unclassified path; for a denied one nothing but removing the deny (a deny wins over every role, [classification.md](spec/classification.md#order)): removing the deny list's pattern that matches it, which the caveat names with its place in the run's policy (`classify.Explain`, the rule `stillhere paths` prints), or turning both linguist attributes off for it in `.gitattributes` (`-linguist-vendored -linguist-generated`), which un-denies a path whatever the deny list says, and is the one change when no pattern matches; for a generated header, `linguist-generated=false`; for one too big, a larger `[blame] max_bytes` where its name gives it a role (`classify.Role`), and otherwise a role too, or, for a file larger than its role rule allows (revision 3's test data), that rule's `max_bytes` raised or removed, the rule named; a symbolic link or a submodule gets no role whatever the rules say, since a larger limit alone leaves it unclassified (an image, as encode/httpx's `docs/img/butterfly.png`). Under the packaged policy, which no file holds, the caveat says to write it out first (`stillhere policy > stillhere.toml`).
- **Top authors**: up to five, by the counted lines under the path, then email ascending.
- **Recent landers**: people credited with a non-merge commit whose own patch changed a path under the query, in a landing within `[now − D, now)`, where D is 90 days or the window the query names. A side-branch author counts when the branch lands; the person who merged it does not. Noise first: the change must touch non-blank lines on a path that received a role, as its destination or as a rename's source, and commits in the ignore-revs file do not count.
- **Recent reviewers**: people who submitted a review (approved, changes requested, or commented) within `[now − D, now)`, the recent landers' window, on a merged pull request of the repository, authored by someone else, whose landings changed a path under the query as a recent lander's change does. The review's time makes it recent, whenever the pull request landed. A pull request lands as its merge commit (`PullRequest.MergeCommit`), which GitHub reports for each merge method as the commit the base branch was updated to: a merge commit, whose landing's map holds the pull request's commits; a squash commit; or, for a rebase merge, the last of the commits it put on the branch one by one, with new SHAs the pull request's commit list does not hold and one committer second, so the first-parent landings before the merge commit's that share its committer time belong to it too, up to its commit count, unless one is a merge, which a rebase never puts on the branch, or another pull request's merge commit, which that pull request lands: a merge queue or a bot can land two squashes in one second, and the later one, of several commits, does not take the earlier one's landing ([SPEC.md, merge methods](../testdata/fixture/SPEC.md#merge-methods-fixturemergemethods)). A login is a person as for `reviews_given@1` (`identity.Directory.Reviewer`); one the run cannot link to an email is listed as `@login`.
- **Bots**: listed apart, never mixed into these lists: their top five is ranked among bots.
- **Path**: a repo-relative prefix that matches whole segments, so `src` covers `src/pay.go` but not `srcutil/x.go`; `""` is the whole repository.
- **Values**: per repository with anything under the path, one value about the path (subject `repo` for the whole repository, else `area`, keyed `<repo key>:<file>` or `<repo key>:<dir>/`) whose Value is its counted lines, with `Detail` `prod_files`, `files_with_majority` and, when other roles are counted, `<role>_files` for each (`test_files`, `doc_files`, ...), or, when `prod` lines are counted and other roles hold lines there too, `uncounted_<role>_lines` and `uncounted_<role>_files` for each, what the answer leaves out; and one value per person listed, whose Value is their counted lines under the path, with `Detail` `majority_files`, `recent_landings`, for the top five `top_author` (1 to 5), and, when the run has GitHub data for the repository, `recent_reviews` (the pull requests they reviewed): without it the reviews are unknown, so the key is absent, never 0. The window is the recent landers' and reviewers'.
- **Blind spots**: someone who knows the code but has neither surviving lines, nor a recent landing or review under it, does not appear; moves across files credit the mover. Reviews count only in repositories whose GitHub data the run read, and only on pull requests that landed on the default branch: one merged into another branch, which reached it inside another landing, does not count. A rebase merge whose commits GitHub committed in different seconds counts its last commit only, and a commit pushed straight to the branch, with no pull request, in the same second as a squash of several commits and just before it counts as that pull request's: nothing in the history or the GitHub data tells the two apart. Pairing and review outside GitHub are invisible.
- **How it can be gamed**: it is no one's target; appearing in it earns questions.
- **Fixture oracle**: [SPEC.md, who_knows@1](../testdata/fixture/SPEC.md#who_knows1-main-fixture), and with reviews, [SPEC.md, reviews in knowledge_loss@1 and who_knows@1](../testdata/fixture/SPEC.md#reviews-in-knowledge_loss1-and-who_knows1-main-fixture).
- **Validity**: context. Routing by experience is old: Mockus and Herbsleb, "Expertise Browser" (ICSE 2002), recommended experts from their changes. For blame as an authorship signal, see `surviving@1`.

  - 2026-10-15 (#69): logins link to people and are keyed without case, as `reviews_given@1`'s are (`identity.Directory.Reviewer`). A reviewer whose login two pull requests carry in two cases is listed once (`@zoe`, named `@Zoe`), with the pull requests of both, where they were two reviewers; one whose login its commits carry in another case than its reviews is listed as the person, not as `@login`. ## Ranked metrics

### durable@1
- **Question**: Did the code a person wrote last?
- **Unit and scope**: a ratio of non-blank `prod` lines per person, in each repository, group and all; ranked one scope at a time.
- **Inputs**: landings and the landing map, commits, the commits' own patch counts and binary flags, line owners with the path their lines had in each commit, blame errors, ignore-revs SHAs, reverts, path classes.
- **Cohort**: landings in `[now − 365 days, now − 90 days)`. A landing exactly 90 days old belongs to the simplifying window, not to this cohort.
- **Definition**: for each counted commit `c` ([change facts](#change-facts-shared-by-durable1-and-simplifying1)), `added(c)` comes from its own patch, and `surviving(c)` is the non-blank lines at HEAD that blame (`-w -M`, with the repo's ignore-revs file) attributes to `c` whose path in `c` is `prod`. Per person, `durable = Σ surviving / Σ added` over their commits in the cohort: `Num` and `Den`, with `N` the clusters. Both sums classify a line by the path it had in its commit, so a file whose path changes role on the way to HEAD moves neither sum alone ([surviving lines](#change-facts-shared-by-durable1-and-simplifying1)), and both leave out the same lines, those whose survival blame cannot tell: the lines of a file whose blame failed, and of a change git takes for binary, are in neither ([missing facts](#change-facts-shared-by-durable1-and-simplifying1)). That keeps the sums in step; it does not bound the ratio by 1, because blame can give a commit lines its own patch did not add (blind spots). Lines blamed to a merge commit itself (conflict resolutions) count toward `surviving@1` for the merge's author. They are excluded from `durable@1` in v1, because a merge's own added lines need a combined diff.
- **Clusters**: a cluster needs at least one added line in the ratio. A landing that adds no `prod` line (a pure rename, a whitespace-only or a test-only change) says nothing about durability, so it is not a cluster and does not count toward eligibility; nor does one whose added lines are all left out, on files whose blame failed or in changes git took for binary.
- **Reverts**: a reverted landing stays in the cohort and is flagged: `Detail` `reverted_landings` counts the person's clusters in reverted landings. Its lines are already gone, so it already counts as not durable. A revert landing is excluded.
- **Uncertainty**: a Ratio cluster bootstrap ([ranking rules](#ranking-rules)): `Clusters` hands each person's clusters, `(landing, surviving, added)`, to `rank.Intervals`.
- **Eligibility**: at least 10 clusters in the cohort (open decision 5).
- **Blind spots**: a planned replacement of correct code looks "not durable"; moves across files credit the mover; a move inside one file counts as lines the mover added, which blame then gives back to their first author, so the mover scores 0 on them (open decision 6); a copy inside one file credits its original author with more lines than they added, so a value can pass 1 (Ann's 2-line block pasted twice more by Bob: Ann 6 / 2, [#63](https://github.com/IHaveASegway/stillhere/issues/63)); so can a reformat listed in the ignore-revs file that splits a line into several, because blame gives every part to the line's author (a call split over five lines, as a formatter does, gave the 2-line commit that wrote it all 6 lines on git 2.50.1: 6 / 2); a revert that restores deleted lines takes their blame from the original author; a `prod` file later moved to a path blame does not read, such as a denied path under `vendor/`, keeps its lines in `Σ added` and none in `Σ surviving`, so its author looks as if they kept nothing (Pat 0 / 4 in the [binary-file guard](../testdata/fixture/SPEC.md#binary-files-fixturebinary)); changes younger than 90 days are not scored; a change git takes for binary scores none of its lines, and the repository's `binary-changes` caveat counts the changes to `prod` files left out that way ([#64](https://github.com/IHaveASegway/stillhere/issues/64)): leaving them out is complete-case analysis, unbiased only when whether a file is binary has nothing to do with how long its code lasts (Little and Rubin, *Statistical Analysis with Missing Data*, ch. 3); a backport whose diff was adapted, merged back from a maintenance branch, is no [copy](#units), so blame gives its lines to the original and it scores about 0.
- **How it can be gamed**: writing in stable, low-traffic code; avoiding risky areas. Load-bearing (M5) is the counterweight.
- **Fixture oracle**: [SPEC.md, change oracles](../testdata/fixture/SPEC.md#change-oracles-m1-testchangeoracles). Bob's move and Ada's rename in the main fixture; the revert, requote, re-indent, squash, Copilot and eligibility cases in the sibling; binary files, and text files moved across roles, in the [binary-file guard](../testdata/fixture/SPEC.md#binary-files-fixturebinary).
- **Validity**: beta: not yet checked against a lead's labels (`stillhere label`, then `stillhere validate`: AUC ≥ 0.7 on at least 50 scored labels, [validation.md](validation.md)). A change is scored by Σ surviving / Σ added over its clusters, in this cohort. Reference (model panel, 4 public repositories, 2026-10-15): does not separate meaningful from routine changes: AUC 0.42 (0.30–0.55) on 76, while change size alone gives 0.82. The model panel is three AI models that labelled public changes without seeing any metric value: evidence, not a lead's judgment.
- **Changelog**:
  - 2026-10-14 (#54), before the first release, so the version stays 1: a change git takes for binary leaves both sums ([missing facts](#change-facts-shared-by-durable1-and-simplifying1)), matched to the lines blame gives its commit by the path they had in that commit. Until then those lines counted in `Σ surviving` and not in `Σ added`, so a binary file made a person keep more lines than they added (5 over 2, a durability of 2.5). `ai_assisted@1`'s `durable_ai` and `durable_other` read the same sums and changed with it.
  - 2026-10-15 (#70), before the first release, so the version stays 1: a value passing 1 that way was a bug. `Σ surviving` classifies a blamed line by the path it had in its commit, as `Σ added` classifies a change ([surviving lines](#change-facts-shared-by-durable1-and-simplifying1)), where it took the role of the line's path at HEAD. A text file moved onto a `prod` path from `vendor/`, `tests/` or a name with no role kept lines that were never added (Uma 5 / 2, Tess 5 / 1 and Nate 6 / 1 in the binary-file guard), and a `prod` file moved into `tests/` kept none (Kim 0 / 3). A file whose blame failed now leaves its lines out whatever its role at HEAD, since a `test` file can hold surviving lines. `ai_assisted@1`'s `durable_ai` and `durable_other` read the same sums and changed with them.

Blame gives a copy's lines to its original, so a maintenance branch merged back scored every backport 0: on tokio-rs/axum one person who backported their own two fixes had 44.4% (4 of 9) and has 50% (4 of 8), and the one ranked person 94.3% (682 of 723) where they had 92.3% (682 of 739). A backport whose diff was adapted still scores what blame gives it, mostly 0 (both of axum's examples in the finding that led here are such backports). `ai_assisted@1`'s `durable_ai` and `durable_other` read the same sums.

### simplifying@1
- **Question**: Did a person remove code, and did the removal stick?
- **Unit and scope**: non-blank `prod` lines removed per person, in each repository, group and all; ranked one scope at a time.
- **Inputs**: landings and the landing map, commits, the commits' own patch counts, ignore-revs SHAs, reverts, path classes.
- **Window**: landings in `[now − 90 days, now)`.
- **Definition**: per person, the sum of `removed(c)` over their counted commits in the window ([change facts](#change-facts-shared-by-durable1-and-simplifying1)), leaving out every commit of a reverted landing. A landing is *simplifying* when the net change of its counted commits, everyone's together, `Σ added − Σ removed`, is −20 lines or fewer; −20 counts. The count of simplifying landings is shown as context: `Detail` `simplifying_landings`, the person's clusters in simplifying landings.
- **Clusters**: every cluster counts, including one that removed nothing, because for a sum a zero is evidence.
- **Uncertainty**: resampling a person's own clusters would always return the same sum, so the bootstrap resamples week blocks shared by everyone ([ranking rules](#ranking-rules)): `Clusters` tags each cluster with its block, the week counted back from `--now` (0 is `[now − 7 days, now)`), and passes the 13 blocks the 90 days span.
- **Eligibility**: at least 10 clusters in the window.
- **Blind spots**: deleting a feature looks like simplifying (deleting its tests does not, because only `prod` lines count, except Rust's tests inside the source, which count as `prod`: the `inline-tests` caveat); a move counts its lines as removed, though its net is 0, so it is never a simplifying landing by itself; removed code that comes back later is not detected in v1.
- **How it can be gamed**: deleting then re-adding. Revert detection catches the plain case: neither the reverted landing nor the revert counts.
- **Fixture oracle**: [SPEC.md, change oracles](../testdata/fixture/SPEC.md#change-oracles-m1-testchangeoracles). Erin's rename and Bob's merge in the main fixture; the −20 boundary, blank lines, a test deletion, the revert pairs and the requote in the sibling; a shallow clone of the sibling in [SPEC.md, partial and shallow clones](../testdata/fixture/SPEC.md#partial-and-shallow-clones-74).
- **Validity**: beta: not yet checked against a lead's labels (`stillhere label`, then `stillhere validate`: AUC ≥ 0.7 on at least 50 scored labels, [validation.md](validation.md)). A change is scored by the `prod` lines its clusters removed, in this window. Reference (model panel, 4 public repositories, 2026-10-15): separates, but no better than change size: AUC 0.76 (0.63–0.88) on 65, while change size alone gives 0.87, a difference of -0.11 (-0.22 to 0.01). The model panel is three AI models that labelled public changes without seeing any metric value: evidence, not a lead's judgment.
- **Changelog**:
  - 2026-10-15 (#74): a shallow clone whose boundary is older than the 90-day window has values there, exactly the full clone's, where a boundary anywhere in the history gave none ([missing facts](#values-what-every-metric-returns)). No release had shipped `simplifying@1`, so it keeps `@1`; `landed@1`, `landed@2` and `review_coverage@1` read the same rule.
  - 2026-10-16 (wave 10), before the first release, so the version stays 1: a [copy](#units) of a change an earlier landing brought is no counted commit, so its removal is not counted twice (one person's two clusters removing 3 lines each in the merge-back guard, the original and its cherry-pick, are one removing 3).

### reviews_given@1 (M2)
- **Question**: Who carries the review load?
- **Unit and scope**: merged pull requests reviewed, per person; values for scope `all`, for each group and for each repository, so every scope a scan ranks in has the values its table lists bots from. Only the pull requests of the run's own repositories count, in every scope, `all` included: the replica outlives runs and holds whatever any sync copied into facts.db, such as another organization, while a scope describes repositories the run scanned. A forge repository is one of the run's when its clone URL and the origin of a repository the run collected name the same host, owner and name, whatever the protocol and case (`https://github.com/acme/widget.git` matches `git@github.com:acme/widget.git`; `domain.ForgeJoin` over `domain.RemoteRepo`), so a user's SSH clone counts like a managed mirror. A repository whose collection failed joins no forge repository: it adds nothing to any number, its reviews included. A pull request belongs to its repository's scope and to the groups that hold it.
- **Inputs**: the forge replica the run read (`FactSet.Forge`: pull requests and their reviews), the run's repositories and commits (to link logins to people), and the policy's `[bots]` fragments.
- **Definition**: per person, distinct merged pull requests authored by someone else on which they submitted at least one review (approved, changes requested, or commented) in the last 90 days. Precisely: a review counts when it was submitted in `[now − 90 days, now)`, by an account with a login, on a pull request merged before `now` by another person (another login, and another person once logins are linked). A review after the merge counts. Shown with it (`Detail`): `reviews` (the reviews counted), `review_comments` (their inline comments), `approvals`, `approvals_no_comment` (approvals with no text and no inline comment), and `no_comment_share` (their share of approvals, present only when there are approvals).
- **People**: a login is a person when GitHub attributes to it a commit whose address the run shows: a pull request's commit or merge commit, a link of an older pull request, or the links pass's answer for an author email of the history (#117); the person is the run's mailmapped author of that commit, history or blamed, else the email GitHub read when the facts show that address (the most such commits, then the smallest email), so the mailmap stays the only identity store. Any other login is `@login` ([ADR 0004](adr/0004-github-behind-sync-boundary.md)); an app's is `@login[bot]`. Logins are compared and keyed without case, as GitHub compares them: `@zoe` whether a pull request says `Zoe` or `zoe`, shown as GitHub last showed it (`identity.Directory.Reviewer`, the rule `knowledge_loss@1` and `who_knows@1` read too).
- **Clusters**: one per person and pull request, `Num` 1, in the week (counted back from `now`) of the person's first counted review of it: a Sum over 13 week blocks.
- **Eligibility**: at least 10 reviewed pull requests. Bots (an app account, or a subject a `[bots]` fragment matches, which `identity` decides, so a User-typed machine account such as `@renovate-approver` is one) get values and are never ranked.
- **Uncertainty**: the week-block bootstrap of Sum metrics, as for `simplifying@1`.
- **Blind spots**: reviews of pull requests closed unmerged or still open; dismissed reviews; conversation comments outside a review; pairing and review outside GitHub. A reviewer GitHub links to no address the run shows (no commit of theirs in the run, nor an address the links pass answered for) shows as `@login`, apart from their email row. A clone through a host alias (an `~/.ssh/config` Host, or `ssh.github.com`) names another host, so its repository's pull requests do not count, and neither do those of a repository whose collection failed. The replica holds each pull request's latest state, so a review dismissed after `now` is already gone from an older `now`.
- **How it can be gamed**: rubber-stamp approvals. The no-comment share is shown next to the count for that reason. Reviewing many trivial pull requests, such as dependency bumps.
- **Fixture oracle**: [testdata/github/README.md, reviews_given@1](../testdata/github/README.md#reviews_given1), asserted by `TestGitHubSync` over the recorded responses.
- **Validity**: beta: not yet checked against a lead's labels (`stillhere label`, then `stillhere validate`: AUC ≥ 0.7 on at least 50 scored labels, [validation.md](validation.md)). A change is scored at this metric's grain, its pull request (#77): the people other than its author, bots aside, who submitted a review of it that this metric counts, at any time before `now`, for a change that landed in the window (the window selects the change, not its reviews, so a pull request merged early in the window keeps the reviews it got before the window began). A pull request no one else reviewed scores 0. A change that is no pull request of the run's GitHub data is not scored: a direct push, a merge GitHub's API does not list (a security advisory's "Merge commit from fork") and a pull request a sync missed look alike in the replica, so a 0 for them would read a gap in the data as no review. Reference (model panel, 4 public repositories, 2026-10-15): cannot tell yet: n 49 is under 50, and AUC 0.55 (0.40–0.71) spans chance, while change size alone gives 0.89. The model panel is three AI models that labelled public changes without seeing any metric value: evidence, not a lead's judgment.
- **Changelog**: 2026-10-15 (#69): logins compare without case, so one account whose login a pull request carries in another case, after the account changed its case, is one subject (`@zoe`, not `@Zoe` and `@zoe`), and is linked to its person whatever case its commits carry it in. This mends a split no definition meant: a login names one GitHub account, which GitHub compares without case. No release had shipped `reviews_given@1`, so it keeps `@1`. A run stored before kept the case in its keys, and is read with them lowercased ([run model](spec/codebase.md#run-model)), unless it holds one login in two cases: those stay two subjects, as they were ranked, until a new scan. 2026-10-16 (wave 10, #117), before the first release, so the version stays 1: a login links to a person by every link the run holds, as the same-forge-account rule reads them, so a maintainer whose only commit is older than the synced pull requests is their email's row, not `@login` (encode/httpx: its two top line holders reviewed as `@login`).

### load_bearing@1 (M5)
- **Definition**: the share of a person's landings in the window that touched a top-decile hotspot, with hotspots computed from the 12 months *before* the window so a person's own changes cannot make a file hot.
- **Hotspot**: change frequency overlapping size (revisions in 12 months, and current non-blank lines), as Tornhill and CodeScene define it. Revisions alone are change frequency, not a hotspot.

## Ranking rules

- One metric at a time, within one scope and window.
- **Uncertainty**: a bootstrap with B = 1,000 replicates (Efron and Tibshirani, *An Introduction to the Bootstrap*, 1993). How a replicate is drawn depends on the metric's kind:
  - **Ratio metrics** (`durable@1`) resample each person's clusters, their *landings*, with replacement. Lines inside a landing are not independent, so resampling lines would give falsely narrow intervals.
  - **Sum metrics** (`simplifying@1`, `reviews_given@1`) resample *weeks*. The window is cut into 7-day blocks counted back from now, the oldest one shorter when the window is not a whole number of weeks (a 90-day window holds 13), and each replicate draws as many blocks as the window holds, with replacement, the same blocks for every person: a block bootstrap (Künsch, "The Jackknife and the Bootstrap for General Stationary Observations", Ann. Statist., 1989). Block k holds `[now − 7(k+1) days, now − 7k days)`, half-open like every window: a change at time t is in block ⌈(now − t) / 7 days⌉ − 1, so one exactly a week old is in block 0 and one at the window's start in the oldest block. `domain.Window.Week` and `Weeks` are the one definition of the rule, which every Sum metric and the bootstrap's own check use; ⌊(now − t) / 7 days⌋, the other reading, would put a change exactly k weeks old in block k, and in a window of whole weeks a change at its start in a block the window does not have. A total depends on how many changes a person landed, and resampling their own clusters would hold that number fixed, which hides most of a total's uncertainty: for a pure count, such as pull requests reviewed, every replicate would return the observed count. Drawing the same weeks for everyone keeps what a week did to the whole team, such as a holiday, out of the comparison between people.
- **Intervals**: a person's value interval runs from the 25th to the 975th of their 1,000 sorted replicate values (the percentile interval). In every replicate the eligible people are ranked, the largest value first, and a person's rank interval runs from the 25th to the 975th of their 1,000 ranks, shown as "1–3". Two value intervals can overlap while the two rank intervals do not, because swapping ranks needs both values at their unlikely ends in the same replicate (Schenker and Gentleman, "On Judging the Significance of Differences by Examining the Overlap Between Confidence Intervals", Am. Statist., 2001).
- **Ties**: tied values share the best rank they cover, as in "1, 1, 3" (standard competition ranking), in every replicate, so a tie never ranks anyone below the people they tie with. Values are compared exactly: sums of counts are exact, and equal ratios of counts are equal numbers. For a sum metric, people with the same totals in every week are drawn from the same weeks, so they tie in every replicate and get equal intervals. For a ratio metric, each person is drawn from their own stream, so people with equal data get intervals that agree only up to Monte Carlo error (see Reproducibility): an end can differ.
- **Eligibility**: below the metric's minimum number of clusters, a person is listed with their value and N, and not ranked. They take no rank in any replicate, so they move nobody else's rank, and no value or rank interval is reported for them: the store keeps 0, and every published shape gives `null` (wave 10: a JSON row with `rank_lo` 0 read as an interval of 0 to 0), as for a bot's row, which no bootstrap draws either. A bootstrap of a few clusters understates its own uncertainty; a ratio over one cluster always gets a zero-width interval. A table with one eligible person compares them with no one, so it prints their rank as "1 of 1" and says so under the table.
- **Reading a table**: two people can be told apart only when their rank intervals do not overlap; their value intervals can overlap while their rank intervals do not (above). A table's footer says that people whose rank intervals overlap are not ordered only when two of its ranked people's do, so it never states a rule the rows beside it seem to break (wave 10).
- **Reproducibility**: the seed is derived from `metric@version`, scope and window. Each person's random stream (ratio metrics) and the week blocks' stream (sum metrics) are derived from the seed, so a person's value interval does not move when someone joins the scope. Draws come from PCG-DXSM (Go's `math/rand/v2` PCG) through stillhere's own unbiased bounded draw (Lemire, "Fast Random Integer Generation in an Interval", ACM TOMACS, 2019), and each person's clusters are sorted first. The same `metric@version`, scope, window and clusters give the same intervals on every platform and Go release. A new window is a new seed, though, and the window moves with `--now`. Each end is one of 1,000 draws, with a Monte Carlo error of about half a percentage point of probability, so a later scan can move an end even when a person's clusters did not change: usually to a neighbouring value, and further where the bootstrap distribution has a gap. On the sibling fixture, Lena's `durable@1` interval starts at 20/30 for 62% of seeds, at 19/30 for 37% and at 18/30 for 1%.
- **Stored with the run**: a scan ranks every ranked metric in every rank scope and stores the intervals with the run; `--rank` chooses which tables a report prints, at scan time or later. Readers use the stored ranks, one rule for every metric, and bootstrap only a table the run did not store, such as a newer metric version's: over the run's own facts, with the seed a scan derives from the metric, scope and window, so it is the table a scan would have stored. A run stored since schema version 4 keeps the pull requests it read ([ADR 0011](adr/0011-a-run-keeps-the-github-facts-it-read.md)), so a rank of GitHub data could be computed again from it, as a newer metric version's is; the stored ranks also serve the runs stored before it, which kept only the watermarks of the replica they read ([run model](spec/codebase.md#run-model)). A rank table of a metric that reads GitHub data says when that data was synced.
- **Limits**: each interval is about one person, not a joint statement about the whole table. Bootstrap rank intervals are least reliable for people who are tied or nearly tied (Hall and Miller, "Using the Bootstrap to Quantify the Authority of an Empirical Ranking", Ann. Statist., 2009). A person whose clusters all have the same value gets a zero-width value interval, because a bootstrap shows only the variation its sample holds. At the sample sizes ranks start at, a 95% percentile interval covers less than 95%. In simulation ([ADR 0010](adr/0010-rank-intervals-bootstrap-per-kind.md#consequences)), value intervals covered about 87% of true values at 10 landings and 88–91% for 13-week sums, and rank intervals covered 91–97% of true ranks, 88% in a team of near-equals.
- Bots are never ranked. AI-assisted work is included, with a filter.
- Canonical reading on why rank intervals matter: Goldstein and Spiegelhalter, "League Tables and Their Limitations" (J. R. Statist. Soc. A, 1996).

## Validity checks

`stillhere label` samples a stored run's changes and asks a lead to label each `meaningful`, `routine` or `noise`, blinded to every metric value and to the author; `stillhere validate` reads the labels (change, label, labeller) and reports, per metric version, how well the metric separates meaningful from routine changes: the AUC, with a 95% bootstrap interval, and n, beside the AUC of change size alone over the same changes (`--scores` writes each change's numbers). The protocol, the rubric with worked examples, and the reference result are in [validation.md](validation.md).

- **The grain.** A labelled change is a landing, or a pull request with the landings that put it on the default branch (`metrics.Changes`), named by a landing's SHA or a prefix of at least 7 digits, or by `#950`, `pr:950` or `owner/name#950`. Each ranked metric scores it by what the change adds to its clusters, in scope `all` (`metrics.Scorer`): a ratio by its clusters' Σ numerator over Σ denominator, a sum by their sum. `durable@1` and `simplifying@1` find its clusters by its landings; a change with none is not scored. `reviews_given@1`'s clusters are a reviewer's in its window, so it measures the change itself: its pull request's reviewers (#77), and a change that is no pull request of the run's GitHub data is not scored. Only a change that landed in the metric's window is scored. Each entry's Validity line says what its measure of a change is.
- **A change counts once.** Each labeller's last row for it counts, whether the rows name it by a SHA, a prefix or its pull request; over several labellers, the label most of them gave, and a tie is left out. So n counts changes, and the interval resamples changes. `validate --labeller NAME` scores one labeller's labels alone, so two leads' AUCs can be compared.
- **The bar.** A ranked metric stays marked "beta" until a lead's labels give it an AUC ≥ 0.7 on at least 50 of its scored labels. Noise is in no AUC. `validate` says whether the labels it reads clear the bar; that is evidence about the code they judge, and the beta mark in stillhere's output changes only when the metric's published Validity line does (a lead who clears it can report the result).
- **The reference.** Until then, a result from a panel of model raters on public repositories is shown beside the mark, never in its place ([ADR 0014](adr/0014-labels-are-evidence-not-the-gate.md)).
- **The labels** hold judgments about colleagues' work, so the file is kept beside the facts database, outside every repository, by default.

The Validity line of a ranked metric takes one of these forms, with the repositories the labels come from and their date (the `--now` of the runs they label):

```
- **Validity**: beta: not yet checked against a lead's labels (...). Reference: the model panel has not run yet.
- **Validity**: beta: not yet checked against a lead's labels (...). Reference (model panel, k public repositories, date): VERDICT: AUC x.xx (lo–hi) on n, while change size alone gives x.xx[, a difference of d.dd (lo to hi)]. The model panel is three AI models that labelled public changes without seeing any metric value: evidence, not a lead's judgment.
- **Validity**: AUC x.xx (lo–hi) on n lead labels (date; one organization). Reference (model panel, k public repositories, date): VERDICT: ...
```

The numbers are `validate`'s: the AUC, its interval in parentheses, n, the labels the metric scored, and the AUC of change size alone (the lines a change added and removed on paths with a role) over the same changes, its "size alone" column. Whether a metric beats size is a question about one sample, so it is answered by a paired comparison: each of 1,000 bootstrap replicates resamples the changes once and takes both AUCs over the very changes it drew, which gives a 95% interval of the metric's AUC less size alone's (`size_diff_lo` and `size_diff_hi`; `rank.AUCDiffInterval`). Two separate intervals would ignore that both AUCs rank the same changes, and setting one's lower end against the other's point can call a difference real that could be 0 (DeLong, DeLong and Clarke-Pearson, "Comparing the Areas under Two or More Correlated Receiver Operating Characteristic Curves", Biometrics 1988, give the closed form). The verdict says what the numbers mean, so a reader need not interpret them, by the first of these that holds (`rank.Separation.Verdict`):

- **cannot tell yet**: n is under 50, the bar's labels; "spans chance" is added when the interval holds 0.5.
- **does not separate meaningful from routine changes**: the AUC's interval holds 0.5.
- **separates in reverse (meaningful changes score lower)**: the interval lies below 0.5.
- **separates weakly, below the bar**: the interval lies above 0.5, and the AUC is under 0.7.
- **separates, beyond change size**: the AUC is 0.7 or more, and the paired interval of its AUC less size alone's lies above 0.
- **separates, but no better than change size**: the AUC is 0.7 or more, and that paired interval holds 0 or lies below it: a metric that grows with size can separate the classes through size alone. These two verdicts give the difference and its interval.

`validate` prints each metric's verdict with its numbers under its table, for any labels, a lead's included, and the verdict is not the bar: "clears the bar" says the AUC is 0.7 or more on 50, whatever size alone gives. Whether beating size alone should be part of the bar is an open question for the owner ([ADR 0014's amendment](adr/0014-labels-are-evidence-not-the-gate.md#amendment-the-published-form-and-size-alone-2026-10-16)).

A reference is the metric's `Definition.Reference`: the numbers, from which the verdict and its words follow by that one rule, so the two cannot drift apart. The rank tables', `explain`'s and the MCP server's validity caveat says the line's words (`report.ValidityNote`; a page that shows several ranked metrics says the mark, the source and what a model panel is once, then each metric's result, `report.ValidityCaveats`), and `TestChangeOracles` checks that each line here holds its metric's reference word for word.
